# CONTINUE HERE — editor-core / editor-impl 拆分与代码风格

> 给下一个对话：本文件是问题清单 + 交接说明。用户要「详细讨论」，**不要**先动手改代码。

## 一、这个任务的真正目的（用户重申，之前没抓住）
把编辑器拆成两个包：
- **`@motajs/editor-core`**：底层，纯接口 + 管理（能力登记、撤销操作栈）。**用户层直接用底层引擎来高度自定义。**
- **`@motajs/editor-impl`**：默认实现（表格/地图/代码编辑、资源层、编辑层）。

**唯一硬约束：改前改后画面看起来一样。**
明确否定：接口**不为适配 `@motajs/editor` 本身而设计**；设计思路**不要求与 editor 相同**。之前所有「让编辑器最小跟随」「与编辑器一致」的取向都偏了。

## 二、核心不满（下次先谈这个）
1. **`editor-core` 体量失控**：用户预期 < 5000 行（大概率 < 3000），现在刚开始就 1000+ 行 → 说明设计过度、写了「不知道为什么要写」的代码。
2. **计划/简报不在点子上**：反馈没有围绕「拆分 + 用户可高度自定义」这个目的。

## 三、仍未解决的代码风格问题（用户逐条指出）
1. **变量/常量**：若需注释，**必须用 jsDoc**，不能用单行 `//`。
2. **jsDoc 是给「用代码的人」看的**，只说明「这个接口是干什么的」；**不得解释实现细节**（执行逻辑、内部规则清单、`D-xx`、`Phase xx`）。实现细节属于使用文档 / API 文档。
3. **注释要短**：一句话能说完就一句。参考项目的长注释都有其特定原因；不要为长而长。
4. **jsDoc 主体只有一行时，结尾不加标点**。
5. **jsDoc 主体与 `@param` 之间不写空行**。
6. **反例（用户点名）**：`defineEngine` 现有注释（8 行规则清单 + 实现说明）应简化为一行，例如：
   ```
   /**
    * 输入编辑器引擎描述对象，若描述对象符合规范，那么返回编辑器引擎适配器，否则抛出错误
    * @param descriptor 编辑器引擎描述对象
    */
   ```
7. **`ContentUtils` 不应导出对象**：裸函数直接 `export function`，不要聚合成对象/常量。
8. **成员空行**：功能相近的成员**不空行、写在一块**；不相近才空行；**方法之间必须空行**。现在成员之间空行过多。

## 四、设计层面的根本质疑（下次详谈，不要只改格式）
- 需要重新审视 `editor-core` 的最小接口面，**砍掉过度设计**，目标 < 3000–5000 行。
- 接口服务于「用户用底层引擎自定义」，不是服务 editor 适配。
- 用户希望：读代码的人以**最少认知**理解代码；用代码的人从 **jsDoc 一眼**知道接口能干什么。
