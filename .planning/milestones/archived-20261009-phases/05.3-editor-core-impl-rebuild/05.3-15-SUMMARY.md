# Phase 05.3 Plan 15: 撤销与资源缺陷修复（gap closure） Summary

## Accomplishments

- **WR-03 修复：** `UndoSystem.undo` / `UndoSystem.redo` 先读取栈顶、`await` 操作成功后才把条目在两栈间迁移；操作抛错时条目留在原栈，历史链不断裂、可重试。
- **IN-04 修复：** `UndoSystem.addUndoContext` 在 `maxUndoStep <= 0` 时直接返回，不记录任何历史；`IUndoInjection.maxUndoStep` 与 `IUndoSystem.maxUndoStep` 的 jsDoc 写明「0 或负数表示禁用撤销」。

- **WR-09 修复：** `ResourceSystem.updateResource` / `updateResourceList` 把每个钩子调用包成「异步化 + 兜底」，单个钩子同步抛错或返回被拒绝的 Promise 都不中断其余钩子；失败经集中日志 `resource.hookFailed` 记录。

## Decisions Made

- **撤销历史迁移的原子性**：以「读取栈顶 -> await -> 成功后才出栈并压入另一栈」取代「先出栈再 await」，异常不再导致条目从两栈同时消失。
- **`maxUndoStep <= 0` 语义**：明确为「禁用撤销」，并在接口 jsDoc 与测试中双背书；裁剪分支随之无需再判断正数上限。
- **dispose 生命周期**：释放即置空后端引用，使六个方法语义一致地命中同一未初始化守卫，复用 `system.notInitialized`，不新增日志 id。
- **钩子广播隔离**：每个监听者单独兜底（同步抛错与拒绝 Promise 统一转成被捕获的拒绝 Promise），失败只记录、不中断其余监听者。
- **日志 id `resource.hookFailed`**：经用户确认后写入消息表；计划原文将其记为「提案待确认」，此处按确认结果记录。
