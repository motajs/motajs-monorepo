<objective>
Add the pull-request CI gate — lint, per-package typecheck, unit tests and production build across every workspace package — and make it block merges by registering the four job names as required status checks.

Purpose: the repository has no pull-request CI today, so nothing prevents a regression from merging; and the "blocking" half of that guarantee is repository configuration, not workflow content. D-03: a separate `.github/workflows/ci.yml` triggers on `pull_request` and push to main, kept independent of the manual deploy workflow; D-04: it blocks merges from day one with no advisory period. D-02 requires the gate to cover all workspace packages rather than an affected-only subset, because this refactor moves code between `libs` and `apps`.
Output: `.github/workflows/ci.yml`, a structural verifier for it, and the repository required-check configuration applied outside git.
</objective>

    Create `.github/workflows/ci.yml` mirroring `deploy-editor-h5test.yml`'s toolchain pinning exactly: `actions/checkout@v4`, `pnpm/action-setup@v4` with version 11.10.0, `actions/setup-node@v4` with node-version 24 and `cache: pnpm`, then `pnpm install --frozen-lockfile`. Add a `concurrency` group keyed on the workflow and ref with `cancel-in-progress: true`. Do not modify `deploy-editor-h5test.yml` and do not add coverage, e2e or visual checks — D-01 keeps e2e out of this gate. Then create `scripts/verify/ci-workflow.js`, an ESM Node script that reads the workflow file as text and asserts every structural rule above: the two triggers and the main-branch restriction, the four job ids and their mapping to the four root scripts, the recursive submodule checkout on exactly the unit and build jobs, read-only contents permission on every job, and the absence of a secret reference, an environment binding, a path filter, and the fork-reachable trigger. <threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Fork pull request → CI runner | Untrusted contributor code executes in the runner with the workflow token's permissions. |
| Workflow file → repository settings | The job ids are merely a contract; the merge gate itself lives in settings and needs admin rights. |
| CI job → third-party actions | Every job executes publisher-supplied action code. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07-01 | Elevation of Privilege | fork pull request reaching secrets | high | mitigate | Trigger on pull requests only; carry no secret and no environment binding; keep the deploy workflow's secrets exclusively in its own file. |
| T-07-02 | Elevation of Privilege | over-broad workflow token | high | mitigate | `permissions: contents: read` on every job; the verifier asserts it. |
| T-07-03 | Repudiation | a required check silently un-gated | high | mitigate | Forbid a path filter on the workflow, so a pull request can never be left waiting; the verifier asserts the trigger shape and the four job ids, and Task 2 confirms the gate on a real pull request. |
| T-07-04 | Tampering | mutable third-party action tags | medium | accept | Stay on the first-party actions and the pnpm action the repository already uses, at the same major tags, rather than introducing SHA pinning as a silent divergence; a deliberate decision recorded here. |
| T-07-05 | Tampering | build scripts from untrusted packages | medium | mitigate | Do not widen `pnpm-workspace.yaml` `allowBuilds`; install with `--frozen-lockfile` so the lockfile cannot drift. |
| T-07-SC | Tampering | package installs (supply chain) | low | accept | This plan adds no package; it references only the actions already used by the deploy workflow. |

</threat_model>
