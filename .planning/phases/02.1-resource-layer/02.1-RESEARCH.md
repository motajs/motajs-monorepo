## User Constraints (from CONTEXT.md)

### Locked Decisions

以下为 CONTEXT.md `## Implementation Decisions` 的**逐字**拷贝（锁定，不得再议）。

#### A. 资源标识与资源系统

- **D-01:** `IResourceIdentifier` = **纯文件路径**（删除 `type` 类型号与 `id` 标识串）。资源「相等」即路径相等。 — **Reversibility:** costly — 标识形状是所有读写、面板目标、列表与索引的基础，后改要动全线调用点。
- **D-02:** 路径形态 = **相对项目根、以 `/` 分隔、不带前导斜线**（如 `tables/demo.json`）；越界（`..`）安全**由注入的文件系统 / 宿主负责**，core 只拼接不校验。
- **D-03:** 资源系统升级为**项目文件索引**：**初始化时递归 `readdir` 全扫项目建一棵内存文件树**，之后**新建 / 删除 / 移动时增量更新**；索引**只存结构**（路径、文件 / 目录），**不预读文件内容**。 — **Reversibility:** costly — 索引是面板浏览与「打开」入口的数据来源。
- **D-04:** **取消「按类型列资源」接口**（`requestResourceList(type)` 及其缓存）。列资源 = 读索引 / 列目录。 — **Reversibility:** costly — 这是一条已对外暴露的契约，Phase 3 素材曾依赖它。
- **D-05:** 支持**外部配置忽略项**：注入一个**模式列表**（字符串数组，可含通配），索引遇到匹配的**目录 / 文件**即跳过（如 `node_modules`、`.git`）。

#### B. core 与文件系统

- **D-06:** 初始化**只注入文件系统实现**（`IEditorFileSystem`）；**删除 `IResourceInjection`**，`IEditorCoreInjection` 不再包含资源注入。 — **Reversibility:** one-way — 这是已发布的注入契约，删除后每个宿主（dev 宿主、未来 `@motajs/editor`）都必须改注入方式。
- **D-07:** 文件系统接口**增加二进制读写方法**（如 `readBinary` / `writeBinary`，`Uint8Array`），现有文本方法保留。 — **Reversibility:** costly — 面向所有宿主的接口扩充。
- **D-08:** **core 不解析文件格式**：资源层只提供**原文（string）/ 原始字节（Uint8Array）**；JSON / JSONC 的解析与序列化**由调用方自己做**。
- **D-09:** 资源内容读取带**缓存池**：设**总字节数上限**，**LRU 淘汰**；写入时同步更新缓存，新建 / 删除 / 移动时失效。（避免内存占用过大。）

#### C. 表格 打开 / 新建 / 删除

- **D-10:** 「打开表格」= **一个列表**，分两块：**上半 = 预设表**（外部注入的快捷方式），**下半 = 目录树**（只列 `json` / `jsonc`，且**排除 `*.schema.json` / `*.schema.jsonc`**——它们是 schema 约定文件）。
- **D-11:** **预设表 = 外部注入的静态清单**（每项含显示名 + 数据文件路径）。
- **D-12:** 「新建表格」= 在**用户当前选中的目录**下**一次建一对**文件：`name.json`（数据，初始空对象）+ `name.schema.json`（schema，初始 `{ type: 'object', properties: {} }`）。
- **D-13:** 「删除表格」= 删**数据 + schema 一对**文件；删前**二次确认**；**不可撤销**（与 Phase 3 素材「删字节不可撤销」的方向一致）。 — **Reversibility:** costly — 不可逆的数据丢失路径，一旦放开需引入回收 / 屏障机制。
- **D-14:** 表格面板**目标 = 只给数据文件路径**；schema 路径一律按约定推导，不允许单独指定。 — **Reversibility:** costly — 替换 Phase 2 的 `ITablePanelTarget`（`{ data, schema }`）形状，迁移所有打开器 / 预设 / 测试。

#### D. 约定与迁移

- **D-15:** schema 识别与推导 = **纯文件名约定**：数据 `xxx.json` / `xxx.jsonc`，schema `xxx.schema.json` / `xxx.schema.jsonc`（把 `.schema` 插在扩展名前）；文件名以 `.schema.json` / `.schema.jsonc` 结尾即视为 **schema 视图**。 — **Reversibility:** costly — 该约定同时决定表格与素材（Phase 3）的 schema 文件身份。
- **D-16:** **本阶段全部收口**旧契约：修正 `REQUIREMENTS.md` 的 `CORE-01` 与门禁 `scripts/verify/coreFsSurface.js`（原文要求「fs 接口只定义、core/impl 不得引用」，现须反转）；迁移表格命名；回改 `.planning/phases/03-asset/03-CONTEXT.md` 中受影响的条目（D-04/D-05/D-06 等）。

## Summary

本阶段把 `editor-core` 资源层从「**类型号 + 标识串认资源、只定义 fs 接口不实现**」重构为「**以纯文件路径为唯一标识、core 真正驱动注入的文件系统、并维护一棵项目文件索引 + 一个带字节上限的 LRU 内容缓存池**」，并在此基础上给 `editor-impl/table` 补上**打开 / 新建 / 删除表格**三个用户入口。研究结论全部以本仓当前源码为准（附行号），不引用外部框架行为。

**当前健康状态（本会话实测，作为迁移起点）：** 三个包的**单元测试全绿**（`editor-core` 9 文件 / 70 用例、`editor-impl` 21 文件 / 163 用例、`editor-dev` 2 文件 / 12 用例，合计 245 用例）；`editor-core` 的 `tsc -b` 退出 0；但 **`editor-impl` 与 `editor-dev` 的 `tsc -b` 均红**——commit `1fc0760` 给 `IResourceIdentifier` 增加了**必填** `path`，而 `resourceType.ts` 的两个构造器与 `demoPanel.ts` 的 `DEMO_RESOURCE_ID` 未补 `path`，报 2 + 1 处 TS2741。这是本阶段必须先结清的**已破损状态**，且与 D-01 的接口重写天然收敛（删掉 `type`/`id` 后该错误自然消失）。

**两条与设计正面冲突的旧门禁（不止 CONTEXT D-16 点名的那一条）：** (1) `scripts/verify/coreFsSurface.js` 现强制「`IEditorFileSystem` 只能出现在 `fs/types.ts`」——core 一旦引用即红，D-16 已点名须反转；(2) **`scripts/verify/coreBoundaries.js` 的 (e)「底层 IO 清零」** 现扫描 `packages/libs/editor-core/src` 的**调用形态**（`this.fs`、`.readFile(`、`.writeFile(`、`.readdir(`、`.mkdir(`、`.moveFile(`、`.deleteFile(` 等），要求 0 命中——core 一旦调用注入的 fs，该门禁同样变红。CONTEXT **未点名这条**，但它与 D-06/D-07 直接冲突，本阶段必须一并收口，否则 core 的 fs 驱动代码无法落盘。此外 `editor-core` 的 `coreImportType` / `coreModuleState` / `coreEngineNeutral` 三条门禁对**新核心文件**同样生效（禁 `import type`、禁模块级 `let`/`Map()`、禁引擎术语），LRU / 索引实现必须满足。

**Primary recommendation:** 按「**先接口、后实现**」（AGENTS.md 强制）分波推进：①先结清破损 typecheck 并把接口层一次性定稿（`IResourceIdentifier` 路线、fs 接口、索引 / 缓存 API、面板上下文、`ITablePanelTarget`/`Param`/`Opener`），②再改 core 实现（索引 + 缓存 + fs 驱动），③同波反转两条门禁，④再迁移 editor-impl 表格与全部测试替身，⑤最后接 dev 宿主并把 `CORE-01` / `coreFsSurface` / Phase 3 CONTEXT / 表格命名收口。**迁移期最大风险是「测试替身巨浪」**：`IResourceInjection` 被 4 类假实现 + 20 余个表格测试直接构造，删接口会让整片测试树编译断裂——应尽早建立一个**共享的内存文件系统测试替身**（Wave 0）以收敛改动面。

## Architecture Patterns

### System Architecture Diagram

```text
宿主 / 组合根（dev 宿主；未来 @motajs/editor）
  │  EditorCore.initialize({ ...undo, ...shell, fs: IEditorFileSystem })   ← D-06：只注入 fs
  ▼
EditorCore
  ├─ undoSystem (不变)
  ├─ shellSystem ── registerPanelType / openPanelInTab / 切入切出钩子（不变）
  └─ resourceSystem（本阶段重写为「文件索引 + 内容缓存 + fs 驱动」）
        │  initialize(fs, { ignore: string[] })                 ← D-03 / D-05
        │  递归 listDirectory 全扫 → 内存文件树（只存结构）
        │  read / write / create / delete / move
        ▼
   IEditorFileSystem（注入实现）
        readFile / writeFile / readBinary / writeBinary
        listDirectory / makeDirectory / moveFile / deleteFile
        │
        └─(越界安全由实现负责，core 只拼接)                    ← D-02

面板侧（IEditorPanelContext，按路径）
  ▲ request(path) → IResource（request() 返回 string | Uint8Array）  ← D-08
  │  （无 requestResourceList）                                        ← D-04
  │
editor-impl/table（TablePanel）
  ├─ 打开列表：预设表（注入）+ 目录树（读 core 索引，过滤 json/jsonc，排除 *.schema.json(c)）
  ├─ 新建：写 name.json + name.schema.json（当前选中目录）→ 索引增量更新
  ├─ 删除：删数据 + schema 一对（二次确认、不可撤销）
  └─ 目标 = 数据路径；schema 路径按 ???.schema.json(c) 约定推导
```

### 当前端到端接线（研究问题 Q1 答案）

以下为**实测**的调用链与全部落点（本会话逐文件读取确认）。

**1. 标识产生点（唯一）**
- `packages/libs/editor-impl/src/table/resourceType.ts:16-26`：`tableDataResourceId(name)` → `{ type, id: 'table.<name>' }`；`tableSchemaResourceId(name)` → `{ type, id: 'table#schema.<name>' }`。
- `packages/apps/editor-dev/src/demo/demoPanel.ts:17`：`DEMO_RESOURCE_ID = Object.freeze({ type: DemoResourceType.Sample, id: 'sample' })`。
- schema 识别：`packages/libs/editor-impl/src/table/model/schemaPresentation.ts:15,169-171`，`SCHEMA_RESOURCE_PREFIX = 'table#schema.'`，`isSchemaResourceId(id: string)` 判 `id.startsWith(prefix)`。

**2. `requestResource` 链路**
- 面板侧：`IEditorPanelContext.requestResource(id)`（`panel/types.ts:10`）→ `PanelContext.requestResource`（`panel/panelContext.ts:16-18`）→ `IResourceAccess.requestResource` → `ResourceSystem.requestResource`（`resource/resourceSystem.ts:45-57`）→ `injection.requestResource` → `new Resource(id, this)`。
- 生产调用点：`tablePanel.ts:730-736`（`readResource`）、`:878`（写数据）、`:912` / `:936`（写 schema）；`demoPanel.ts:48`；`shellSystem.ts:830`（`ShellPanelHooks.onUpdateResource`）。
- 句柄读写：`Resource<T>.request()` → `store.readContent`（`resource.ts:14-20`）→ `ResourceSystem.readContent`（`:59-76`，按 `id.type` / `id.id` 二级缓存）→ `Resource.write` → `writeContent`（`:78-88`）。

**3. `requestResourceList` 链路（须删除，D-04）**
- `panel/types.ts:16`、`panelContext.ts:20-22`、`resourceSystem.ts:30-43`（按 `type` 缓存 `listCache`）、`shellSystem.ts:842`（`ShellPanelHooks.onUpdateResourceList` 转投面板 `onUpdateResourceList`）。
- 面板接口 `IEditorPanel.onUpdateResourceList(type, list)`（`panel/types.ts:97`）——D-04 删除列表接口后该成员须同步处置。

**4. `createResource` / `deleteResource`**
- `resourceSystem.ts:90-114`；`panelContext.ts:24-30`。**当前生产代码无调用方**（仅测试用）；本阶段「新建表格」/「删除表格」将成为其真正消费者（但按 D-13 删除走 fs + 索引，具体是否复用 `createResource` 属实现选择）。

**5. 注入形状**
- `IEditorCoreInjection extends IUndoInjection, IResourceInjection, IShellInjection`（`types.ts:5`）。
- `EditorCore.initialize` 并行 `undoSystem.initialize` + `resourceSystem.initialize(injection)`，再 `shellSystem.initialize(injection)`（`core.ts:25-41`）。
- `EditorCore` 构造函数把同一个 `resourceSystem` 交给 `ShellSystem`（`core.ts:22`；`shellSystem.ts:433-435` 保存为 `IResourceSystemAccess`）。

### Anti-Patterns to Avoid

- **在 core 里解析 JSON / JSONC**：违背 D-08。core 只返回原文 / 原始字节；解析属调用方。
- **在 core 里校验 / 规范化路径边界**：违背 D-02。core 只拼接；`..` 拦截归注入 fs。
- **给表格面板指定 schema 路径**：违背 D-14。schema 一律按 `???.schema.json(c)` 推导。
- **把表格文件的删除接入统一撤销**：违背 D-13（不可撤销）。
- **在 `editor-core` 新建模块级 `let` / `new Map()` / 可变导出**：会被 `coreModuleState` 门禁拦红；LRU 与索引必须是**实例字段**，只有 `Object.freeze(...)` 常量豁免。
- **在 `editor-core` / `editor-impl` 新增 `import type`**：会被 `coreImportType` 门禁拦红（AGENTS.md §Code style 亦禁）。
- **在 `editor-core` 出现 `tower`/`floor`/`loc`/`prefab`/`mota`/`commonEvent` 等术语**（含注释）：会被 `coreEngineNeutral` 拦红。

## Common Pitfalls

### Pitfall 1: 两条旧门禁与设计正面冲突（CONTEXT 只点名了一条）
**What goes wrong:** `coreFsSurface.js`（D-16 已点名）与 **`coreBoundaries.js` 的 (e)「底层 IO 清零」**（**未点名**）都会因 core 驱动 fs 而变红。
**Why it happens:** `coreBoundaries.js:74-97` 的 `BOTTOM_LAYER_IO_TOKENS = ['this.fs', '.readFile(', '.readFileBinary(', '.writeFile(', '.deleteFile(', '.readdir(', '.mkdir(', '.moveFile(']`，扫描 `packages/libs/editor-core/src` **全部 .ts/.tsx（含测试）**，要求 0 命中——语义是「底层只允许定义接口、永不调用」。D-06 后 core 必然调用注入 fs，该语义作废。
**How to avoid:** 把 (e) 的意图从「禁止任何 fs 调用形态」改为「**禁止 core 直接触达真实文件系统**」（如禁 `node:fs` / `from 'fs'` / `require('fs')` / 全局 `fetch`），同时保留两极性 fixture（合成违规必须被拦）。**注意**：token `.readFile(` 连**测试替身**的 `x.readFile(...)` 调用也会命中，故若只放宽生产路径、不放宽测试路径会连带 20 余个测试全红。`coreFsSurface.js` 的反转见 §Pitfalls 2。
**Warning signs:** 落盘 core 的 fs 驱动后，`node scripts/verify/coreBoundaries.js` 在 (e) 段报「底层出现 N 条文件读写调用」。

### Pitfall 2: `coreFsSurface.js` 反转后必须仍「可失败」
**What goes wrong:** 直接删掉 (a)/(b) 两极性断言会得到一条**空转**门禁（永不报错 ≈ 无门禁，Phase 2 的教训，见 `coreModuleState.js:26` 的注释）。
**Why it happens:** 现门禁（`coreFsSurface.js:1-347`）三段：(a) 真实树 `IEditorFileSystem` 仅在 `fs/types.ts`（现 95 文件 0 命中）；(b) 合成 `implements IEditorFileSystem` 必须被逐行拦下；(c)/(d) 包根导入正极性（tsc 退 0）/ 负极性（TS2305）。
**How to avoid:** 反转后应断言**相反命题**且保留可失败性，建议保留 (c)/(d)（接口仍须经包根 `./index` 可导入，供宿主 `implements`——这条反转后**依然成立且有意义**），把 (a)/(b) 改为「core 的 fs 驱动文件**确实引用** `IEditorFileSystem`」（正极性），并用一个「远离驱动、误引用」的合成 fixture 证明它能被区分。**具体形态属 discretion，规划阶段定并经 `INTERFACE-NAME.md` 记录。**
**Warning signs:** 门禁改造后删掉全部 fixture 写入逻辑；或断言恒真。

### Pitfall 3: 路径分隔符 / 大小写在 Windows 与 POSIX 上的差异
**What goes wrong:** 索引与缓存以字符串精确比对为键（`Map`），若某宿主实现返回 `a\\b`（Windows）或大小写不同的路径，会与 `/` 规范化路径**不匹配**，产生重复条目 / 查不到。
**Why it happens:** D-02 规定路径为「相对根、`/` 分隔、无前导斜线」，但 `coreFsSurface` 相关实现（尤其未来真 fs）可能带平台特征；core 按 D-02 **不校验**。
**How to avoid:** 在**注入 fs 的契约注释**中明确「`listDirectory` 返回的条目名 / 路径一律 `/` 分隔、无前导斜线」；索引与缓存键直接使用该契约输出。测试替身（Wave 0）须用 `/`。**大小写**：Windows 不敏感但 `Map` 敏感——规划阶段应决定是否在索引去重时做大小写折叠（discretion）。
**Warning signs:** 同一文件在目录树里出现两次；或 dev 宿主（内存后端）与真实 fs 行为不一致。

### Pitfall 4: 索引一致性（create / delete / move 的增量更新）
**What goes wrong:** 只更新文件而忘记更新其**父目录条目**，或删除一对文件时只删数据不删 schema，导致目录树残留幽灵节点 / 缺节点。
**Why it happens:** 索引是结构树，任何写操作都同时是「fs 变更 + 索引变更」两步；两步不同步即漂移。
**How to avoid:** 所有变更收敛到 core 的少数入口（新增 / 删除 / 移动），在这些入口内**同事务式**更新索引与缓存池（D-09 要求写入同步更新缓存、新建 / 删除 / 移动失效）。导入 / 外部改动**不在本阶段范围**（Deferred）。
**Warning signs:** 新建表格后目录树不出现；删除后目录树仍显示；移动后缓存返回旧路径内容。

### Pitfall 5: `readdir` 递归与忽略匹配的语义
**What goes wrong:** 忽略模式（如 `node_modules`）匹配的是**目录名**还是**完整相对路径**未定，会导致漏忽略（仍扫 `node_modules`）或误忽略；递归进入目录时若 fs 返回符号链接可能死循环。
**Why it happens:** D-05 只说「模式列表（字符串数组，可含通配），匹配的目录 / 文件即跳过」。
**How to avoid:** 规划阶段明确匹配目标（建议**以名 / 路径段匹配目录**为主，与用户原话「忽略文件夹」一致）；递归实现只信任 `listDirectory` 返回的、声明为条目的项（接口当前无类型信息区分文件 / 目录，见 `fs/types.ts:16-21` —— `listDirectory` 只返回 `readonly string[]`）。
**Warning signs:** 全扫耗时异常（扫进了被忽略目录）；或某个应可见目录消失。

### Pitfall 6: `verbatimModuleSyntax` 与 AGENTS.md「禁 `import type`」是否冲突
**What goes wrong:** 猜测冲突而误改 tsconfig 或违反项目风格。
**Why it happens:** `packages/apps/editor/tsconfig.app.json` 开了 `verbatimModuleSyntax: true`（STACK 记载），而 AGENTS.md §Code style 禁 `import type`。
**How to avoid:** **实测结论：无冲突。** `editor-core` / `editor-impl` 的 tsconfig 均 extends `tsconfig.lib.base.json`（`[VERIFIED: packages/libs/config/tsconfig.lib.base.json:1-31]`，**未设** `verbatimModuleSyntax`），且 `coreImportType.js` 门禁已强制两包禁 `import type` 且当前为绿；`editor-impl/tsconfig.json` 亦只覆盖 `paths` / `include`（`[VERIFIED: packages/libs/editor-impl/tsconfig.json:1-10]`）。故新文件照 AGENTS.md 写普通 `import` 即可。
**Warning signs:** 有人在 `editor-core`/`editor-impl` 里写 `import type` 并声称「是 verbatimModuleSyntax 要求」。

### Pitfall 7: 测试替身巨浪会让迁移期长期红住
**What goes wrong:** 删 `IResourceInjection` 的瞬间，4 类假实现 + 20 余个表格测试 + dev 宿主全部编译断裂，若逐个修会长时间无法回归验证。
**Why it happens:** `implements IResourceInjection` 出现于 `fixtures.ts:3`、`memoryBackend.ts`、`core.test.ts`、`shell/__tests__/{shellSystem,shellSwitch,shellTitle,shellUndoShortcut,shellOpenParam}.test.ts`；`ResourceSystem.initialize(injection)` + `new ShellSystem(undoSystem, resourceSystem)` 出现在几乎所有 `table/__tests__/*.test.tsx`。
**How to avoid:** Wave 0 先建**共享 `FakeFileSystem`**（实现新 `IEditorFileSystem`，含 `seed` / `listDirectory` 返回树）与一个共享的「装配 ResourceSystem + ShellSystem」测试工厂，再开始删接口。
**Warning signs:** 迁移中途 `pnpm -r test` 大面积红且无法定位。

## Open Questions

1. **[门禁改造形态]** `coreFsSurface.js` 反转后具体断言什么？
   - What we know: 现门禁三段（真实树零引用 / 两极性 fixture / 包根导入正负极性），且 `coreBoundaries.js`(e) 也冲突。
   - What's unclear: 反转后的正 / 负命题与保留哪些 fixture。
   - Recommendation: 保留包根导入极性（接口仍须可被宿主实现）；把「零引用」反转为「驱动文件确实引用」，并保留一个可失败的合成 fixture。属 discretion，须 `INTERFACE-NAME.md` 确认。

2. **[JSONC 解析]** `.jsonc` 如何解析与序列化？
   - What we know: D-08 要求调用方解析；D-10/D-15 涉及 `.jsonc`；catalog **无** `json5` 条目，仅 `file2x` 直接依赖 `json5@2.2.3`。
   - What's unclear: 是否引入 `json5`、是否只支持 JSON（拒绝注释）。
   - Recommendation: 若支持 `.jsonc`，把 `json5` 加入 catalog 并作 `editor-impl` 依赖（`implExports.js` 只断言必需的 `@motajs/editor-core` 依赖在、未禁止新增依赖，`[VERIFIED: scripts/verify/implExports.js:239-243]`）；否则明确「只支持严格 JSON」。

3. **[索引条目类型]** `listDirectory` 只返回 `string[]`，core 如何区分文件与目录？
   - What we know: `fs/types.ts:21` 返回 `readonly string[]`。
   - What's unclear: 改 fs 契约返回带类型条目，还是 core 试列目录判定。
   - Recommendation: 规划阶段定形；倾向让 fs 返回带类型条目（一次 `listDirectory` 即可建树）。

4. **[`createResource` / `deleteResource` 是否保留]** 面板上下文现有的这两个成员是否随 D-01 改形或删除？
   - What we know: `panel/types.ts:23,29`；当前生产无调用方，本阶段「新建 / 删除表格」将成其消费者。
   - What's unclear: 是复用为核心写入入口，还是由表格直接走 fs + 索引 API。
   - Recommendation: 规划阶段二选一，避免两套写入路径并存。

5. **[打开列表 UI 形态]** 面板还是弹窗？
   - What we know: D-10 只要求「一个列表，上下两块」；CONTEXT 明示该形态属 discretion。
   - Recommendation: 规划阶段定；若独立面板，则新增 `IEditorPanelType` 注册（沿用外壳）；若弹窗，则经能力接缝注入。
