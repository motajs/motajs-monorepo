# Phase 02.1 Plan 05: 门禁反转（coreFsSurface + coreBoundaries 底层 IO 段）Summary

**把两条与「核心驱动文件系统」正面冲突的旧门禁收口——`coreFsSurface` 由『fs 接口只允许出现在声明文件』反转为『核心的驱动文件确实引用它』、`coreBoundaries` 的底层 IO 段由『禁任何文件读写调用形态』改写为『禁直接触达真实文件系统』——两条门禁都保留可失败的两极性证据，核心的 fs 驱动代码（Plan 03 / 04）在门禁下合法**

## Accomplishments

- `coreFsSurface.js` 语义反转：(a) 真实树从「`IEditorFileSystem` 只允许出现在 `fs/types.ts`、其余 0 命中」改为「驱动文件集合（`resourceSystem.ts` / `fileIndex.ts`）必须引用它」；(b) 两极性从「单一 `implements` fixture 被拦」改为「fixture A（`implements`）必须命中 + fixture B（近似名 `IEditorFileSystemLike`）不得计入」，双向证明扫描能区分『有 / 无』；(c)/(d) 包根导入正 / 负极性原样保留（接口仍须经 `./index` 导出供宿主 `implements`）；扫描文件数非空转下界（editor-core 全量 42 文件，下界 30）与 fixture 已删断言保留。
- `coreBoundaries.js` 的 (e) 段改写：`BOTTOM_LAYER_IO_TOKENS` 由调用形态（`this.fs` / `.readFile(` / `.writeFile(` …）换成真 IO 形态（`node:fs` / `node:fs/promises` / `from 'fs'` / `from "fs"` / `require('fs')` / `require("fs")` / `fetch(`），不再误伤测试替身的 `x.readFile(...)`；合成 fixture 改为写一个 `import fs from 'node:fs'` 的文件，仍须被同一条断言拦下；(`a`)~(d)、(f)、(g) 段与 core 全量扫描、非空转下界均保留。
- 五条门禁全绿：`coreFsSurface` / `coreBoundaries` / `coreImportType` / `coreModuleState` / `coreEngineNeutral` 均退出 0。
- **可失败性受控反证**：分别临时构造「驱动文件不含标识符」与「底层出现 `node:fs`」两种违规，两条门禁各退出 1 并报出对应失败前缀，随后清理临时产物——证明反转 / 改写后的门禁不是恒真空转。

## Decisions Made

- `coreFsSurface` 反转后**只扫 `packages/libs/editor-core/src`**（旧门禁扫 core + impl 两包）：新语义是「core 驱动注入 fs」，`editor-impl` 的引用属后续计划（06~10）语义；下界随之由 `20` 调为 `30`——editor-core 全量 42 文件、排除测试树为 28，故 `30` 仍钉住「含测试树」，不削弱为 `> 0`。
- 驱动文件集合取 `resource/resourceSystem.ts`（读写 / 增删移驱动注入 fs）与 `resource/fileIndex.ts`（递归列目录驱动注入 fs）——两者都真实驱动注入 fs，且由断言逐个要求「必须引用」，比只断言单一文件更能钉住「core 资源层驱动 fs」这一事实。
- `coreFsSurface` 两极性用 A（`implements IEditorFileSystem`）与 B（只含近似名 `IEditorFileSystemLike`）**双向**证明：A 证明扫描能命中，B 证明词边界不误命中近似名、扫描能区分『无』，避免恒真空转。
- `coreBoundaries` (e) 的判据从「是否出现某调用形态」改为「是否触达真实文件系统」——这是语义反转的必然：D-06 后 core **必须**调用注入的 fs，旧 token 连测试替身一并误伤（RESEARCH Pitfall 1 / A4）。
