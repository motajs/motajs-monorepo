## User Constraints (from CONTEXT.md)

### Locked Decisions

#### A. 结构：底层 vs 包内默认实现
- **D-01:** `editor-core` 包分两层。**底层（core 本身）** = 接口 + 管理（能力登记、撤销操作栈等）；**包内默认实现** = 表格/地图/代码编辑等基本编辑功能，依赖底层、自己持有内容。引擎实现（mota-js）在更上层，本阶段不动。 — **Reversibility:** costly —— 这是整个包的骨架，一旦定下，后面所有能力都按它组织；改它等于重组整个包。
- **D-02:** **底层不读文件**。它只**定义**「文件读写」的接口，**现阶段不调用**；数据来源完全由上层负责。
- **D-03:** **底层不知道编辑内容**。不定义任何「被编辑内容」的统一抽象；内容由包内的默认实现各自持有（表格编辑系统存表格数据，地图编辑系统存地图数据）。

#### B. 撤销
- **D-04:** **底层只提供「撤销管理器」，只管操作栈**（记录先后、撤销时调该操作的撤销、重做时调重做）。**每个操作自带它怎么撤销/重做**，core 不认识操作细节、**不保存快照**。
- **D-05:** 移除现有的**快照式**撤销（现在上层状态靠 `capture()/restore(snapshot)`，并把前后快照存进历史条目）。外部系统的撤销也改为「保存操作」而非「保存快照」。

#### C. 内容来源
- **D-06:** 底层不管内容从哪来；由包内默认实现自己持有内容、由使用者喂入。（与 D-03 一体两面。）

#### D. 编码规范（套到 `editor-core` 包全部，含测试）
- **D-07:** 会被 `implements` 的接口统一加 **`I` 前缀**；每个类必须 `implements` 对应接口，不能有裸类。
- **D-08:** 对外导出的类型（接口/类型别名）集中到各自的 **`types.ts`**，不与实现写在同一文件。
- **D-09:** **接口本身写「它是干什么的」中文注释**；公共成员注释写在**源头（声明处）**；私有/受保护成员也要写注释；**所有成员显式声明类型**。注释只在源头出现，源头之外除非说明行为变化，否则不加注释。
- **D-10:** **文件第一行是 `import`**，禁止文件头注释；`import` 之间不得有空行或注释；想写文件说明就放在所有 import 之后。
- **D-11:** **`editor-core` 禁止 `import type`**（用普通 import；类型再导出用 `export type`）。
- **D-12:** **尽量减少裸函数**：只有「与实例无关的纯工具」可以留裸函数（如路径解析、等待工具）；有状态/可实例化的都要用类。
- **D-13:** **保留行为关键路径的 `try/catch`**（撤销回滚、持久化失败隔离、诊断订阅隔离）；只在新写/整理代码时不新增 `try/catch`。
- **D-14:** **换行符保持 LF**（不采用 dev.md 的 CRLF；仓库已是 LF）。
- **D-15:** 其余按 `E:\github\template\dev.md`（命名、注释风格、类型规则、模块无副作用、无循环引用等）。

#### E. 流程
- **D-16:** **第一批计划只做接口定义**（接口 + `INTERFACE-NAME.md` 命名清单），经用户确认后，再排写实现的计划；**严禁**把「接口设计与定义」和「实现」放进同一个计划。 — **Reversibility:** costly —— 接口是后续所有实现的依据，先定后改会推翻实现。
- **D-17:** 重要命名先写入本阶段的 `INTERFACE-NAME.md`（每个 Plan 一节，说明用途），经用户确认才落盘。

## Summary

本阶段是把 `packages/libs/editor-core` 从「Phase 3–5 增量堆出来的单层包」整改为**两层结构**：底层只放接口 + 管理（能力登记、撤销操作栈），文件读写实现与具体编辑设施上移为「包内默认实现」，并全包按用户编码规范重写。三条主轴互相咬合：(1) 撤销从「快照 + capture-all 委托」改为「底层只管操作栈、每个操作自带撤销」；(2) 文件 IO 类从 `lib/resources/*` 退出底层（底层只留 `ports/fs.ts` 这类纯接口）；(3) 表格专用的字符串字段路径与 DOM 属性转换退出底层。

现状清点（本会话逐文件阅读）：`lib/` 共 **61 个 git-tracked 文件**，其中 **37 个生产源文件**（不含 `__tests__`）。生产面覆盖 `kernel/`(4) + `ports/`(5) + `resources/`(14) + `edit/`(5) + 四个能力空 barrel + `react/`(2) + 根 `index.ts`。当前对外只有一个真实公开面 `.`（根 barrel 汇总 kernel + resources + edit + ports），`./react` 携带 `CoreProbe` 探针，`./code|table|map|asset|shell` 是 `export {}` 空 barrel。

**最大的风险不是重构本身，而是「编辑器不动」与「公开面改名」的冲突。** 编辑器通过 18 个 `// SHIM(phase4)` 转发文件 + `src/adapter/*` + `src/appInstances.ts` 消费了几乎整个 core 公开面；`D-07` 的 `I` 前缀会重命名 `EditorOperation`、`ResourceView`、`LoadableResource`、`FsPort`、`EngineAdapter` 等被 `implements`/结构使用的接口，`coreApiSurface.test.ts` 与编辑器一侧都会变红。另外 `D-05` 移除快照撤销会改变编辑器一个已钉住的 observable 行为（数据补丁的 undo 是否顺带恢复视口，见 `packages/apps/editor/src/project/history/__tests__/operationHistory.test.ts:62-70`）。研究给出两种收敛策略（见 `## Undo Redesign` 与 `## Impact on @motajs/editor`），需用户在接口定义阶段拍板。

**Primary recommendation:** 先由「接口定义计划」产出 `lib/core/**`（新底层）的接口集与两层目录契约并存进 `INTERFACE-NAME.md` 待确认；实现阶段**优先保 `editor-core` 包根 `.` 的导出名兼容**（两层拆分是包内重组，对外名字尽量不变），仅在用户明确要求的点上改形（撤销接口），并把编辑器侧不可避免的最小机械改动（`src/appInstances.ts` 去掉 `registerUndoSystem`、若干操作类接口改名跟随）作为「适配层机械跟随」显式列计划——不新增功能、不改 UI/宿主协议。

**关键取舍：** 只把 `lib/kernel/*` 与 `lib/ports/*`（+ 新撤销模块）收进 `lib/core/`；其余目录**保持原路径**。这样 `package.json` 的 7 个 `exports` 目标、`subpathStatus.json`、`coreExports.js` 的 `SUBPATH_CONTENT` 大多不用动，门禁面最小。把能力目录也塞进 `lib/default/` 会级联改动 exports/status/verifier 三处（Pitfall 8），收益低、风险高，研究**不推荐**。

### Pattern 1: 两层依赖方向（默认实现 → 底层，绝不反向）

**What:** 底层 `lib/core/**` 只能 import `lib/core/**`；默认实现目录可 import `lib/core/**`；底层**永不** import 任何兄弟目录。
**When to use:** 每次新增/搬迁文件后由 `.dependencyCruiser.cjs` 强制。
**Example（建议新增的规则，路径以最终确认为准）:**

```js

  to: { path: '^packages/libs/editor-core/lib/(resources|edit|table|code|map|asset|shell|react)/.+' },

```

### Pattern 2: 撤销管理器以「操作」为单位（无快照）

**What:** 管理器只存不可变操作对象；`undo` 调 `inverse.apply()`，`redo` 调原操作 `apply()`；失败回滚复用 `CompositeOperation` 已有的「按已成功子操作的 inverse 逆序回退」逻辑。
**When to use:** 取代 `edit/operationHistory.ts` 的 `captureSystems`/`restoreSystems`/`OperationCheckpoint` 与 `edit/undoSystem.ts` 的 `UndoSystem`。
**Example（形状建议，最终签名进 `INTERFACE-NAME.md`）:**

```ts
// 底层接口：只声明「能撤销的操作」与「管栈」两件事
interface IUndoableOperation<T = void> {
  readonly meta: OperationMeta;
  apply(): Promise<AppliedOperation<T>>;   // 成功时返回 inverse 操作
}

interface IUndoManager {
  execute<T>(operation: IUndoableOperation<T>): Promise<T>;
  undo(): Promise<void>;
  redo(): Promise<void>;
  clear(): void;
  readonly store: Store<OperationHistoryState>;
}
```

### Anti-Patterns to Avoid

- **底层 import 具体编辑实现**：例如 `lib/core/` import `lib/resources/fileHandler` —— 直接违反 D-01/D-02，必须由 dependency-cruiser 拦住。
- **在底层保留任何 `capture()`/`restore(snapshot)`**：`UndoSystem` 与 `OperationTarget.capture/restore` 都是快照式，D-04/D-05 明确删除。保留一个「过渡用」等于没改。
- **把 `Content<T>`/`IContentView` 当作底层契约**：D-03 禁止底层定义「被编辑内容」统一抽象；它们属默认实现。
- **只改配置不改 verifier 期望值**：`coreExports.js` 的 `SUBPATH_CONTENT`、`subpathStatus.json` 的 `content`、`coreModuleState.js` 的 `CORE_COMPOSITION_ROOT`、`.dependencyCruiser.cjs` 的路径正则是一对多契约，必须同次变更同步演进（Phase 3 Pitfall 8）。
- **给 `editor-core` 加 `verbatimModuleSyntax`**：会与 D-11「禁 `import type`」冲突（该开关要求类型导入必须显式 `import type`）。core 的 lib 基础配置**未**开启它，不要为「规范化」而加。

## Two-Layer Split: 目录划分与依赖方向

### 判定规则（研究建议）

**属于底层的充要条件**（三条同时满足才进 `lib/core/`）：
1. 不读文件、不写文件（最多**定义**文件接口）；
2. 不持有任何被编辑内容、不认识内容的形状；
3. 要么是**接口**，要么是**管理机制**（登记/调度/生命周期/诊断）。

**判定结果：**
- 进 `lib/core/`：`lib/kernel/*`（4 文件）、`lib/ports/*`（5 文件）、新的撤销模块；以及（待确认）`ResourceRegistry` 与「操作接口」的类型。
- 留默认实现：`lib/resources/*`（14）、`lib/edit/*`（5）、`lib/table/`（fieldPath 迁入）、`lib/{code,map,asset,shell}/`、`lib/react/*`。

### 依赖方向（硬规则）

```
lib/core/**            →  只能 import lib/core/**
lib/resources/**       →  可 import lib/core/**
lib/edit/**            →  可 import lib/core/**
lib/table/**           →  可 import lib/core/**
lib/{code,map,asset,shell}/** → 可 import lib/core/**
lib/react/**           →  可 import lib/core/**
lib/index.ts           →  可 import 全部（唯一汇总出口）
```

### `.dependencyCruiser.cjs` 需如何表达（逐条现状对照）

现状规则（`.dependencyCruiser.cjs:13-84`，全部 `forbidden` + `severity: 'error'`）：

| 现有规则 | 现状 from/to | 目录改动后的处理 |
|----------|-------------|------------------|
| `core-must-not-import-consumers` | `lib/**` → editor/service-worker/mota-js | **不变**（作用域是整个 lib） |
| `kernel-must-not-import-capabilities` | `lib/(index\.ts\|kernel/.*)` → 四能力 | `kernel` 段须改为新的底层路径（如 `lib/(index\.ts\|core/.*)`） |

## Undo Redesign

### 现状（快照式，D-05 要移除）

`OperationHistory` 有三条快照通道，全部要拆：
1. **`OperationTarget.capture()/restore()`** —— `execute()` 前采集所有 target 快照（`captureTargets`, edit/operationHistory.ts:43-50），失败时逆序恢复（`restoreTargets`, :52-64）。
2. **`UndoSystem.capture()/restore()`** —— `capture-all` 委托：每个 `execute()` 同步采集**所有注册系统**快照（`captureSystems`, :72-74），undo/redo 时按逆序恢复（`restoreSystems`, :81-98）。
3. **历史条目里的 `systemsBefore`/`systemsAfter`** —— 前后两份快照存进 `HistoryEntryInternal`（`projects` 见 `:16-24`）。

### 目标形状（研究建议）

底层提供「操作栈管理器」，只管顺序；操作自带撤销/重做。两种候选签名：

**候选 A（保持现有 `inverse` 语义，改动最小）**

```ts
interface IUndoableOperation<T = void> {
  readonly meta: OperationMeta;
  apply(): Promise<AppliedOperation<T>>;   // 成功返回 inverse 操作
}
interface IUndoManager {
  execute<T>(operation: IUndoableOperation<T>): Promise<T>;
  undo(): Promise<void>;   // = 对当前条目 inverse.apply()
  redo(): Promise<void>;   // = 对当前条目 operation.apply()
  clear(): void;
  readonly store: Store<OperationHistoryState>;
}
```

**候选 B（每个操作显式 `undo()/redo()`，字面贴合用户「操作自带撤销/重做」）**

```ts
interface IUndoableOperation<T = void> {
  readonly meta: OperationMeta;
  apply(): Promise<T>;
  undo(): Promise<void>;
  redo(): Promise<void>;
}
```

研究**推荐候选 A**：它与现有 `AppliedOperation.inverse`、「组合操作按已成功子操作 inverse 逆序回滚」的既有逻辑（edit/operations.ts:99-107）完全同构，实现改动最小、行为等价最易证明；候选 B 需要每个编辑器操作类额外写 `undo`/`redo`，且会推翻已被测试钉住的 inverse 语义。最终由用户在 `INTERFACE-NAME.md` 拍板。

### 具体替换清单（实现阶段）

| 现状 | 替换为 |
|------|--------|
| `edit/undoSystem.ts` 整个文件（`UndoSystem`） | **删除**；`registerUndoSystem` 从管理器移除 |
| `OperationTarget` / `dataResourceTarget` / `operationPathTarget` | **删除**；失败回滚改由 `CompositeOperation` 的 inverse 逆序（已存在）承担 |
| `OperationHistory` 的 `registry` / `captureSystems` / `restoreSystems` / `captureTargets` / `restoreTargets` / `systemsBefore` / `systemsAfter` | **删除**；`execute` 只 `apply()` 后记录 `inverse` |
| `OperationHistory.applyWithCheckpoint` | 简化为「apply → 记录」；失败不记条目（`CompositeOperation` 自会回滚已成功子操作） |
| `OperationHistoryEntry`（对外） | 保留 `id/label/timestamp/paths`（`paths` 目前来自 `targets`，删除 target 后需从 `meta` 或操作自报路径；**这是需确认的新形状**） |
| `lib/react/index.ts` 的 `useOperationHistory` | 保留（读 `store`），随管理器改名同步 |

### `EditorOperation`/`inverse` 如何映射

现有 `EditorOperation` 已是「操作式撤销」的一半（`apply()` 返回 `inverse`）。整改 = **去掉 `targets` 字段**（快照载荷）→ `IUndoableOperation` 就是 `EditorOperation` 减去 `targets`。编辑器侧的 5 个操作实现类（`viewportOperations.ts`、`materialOperations.ts`、`textFileOperations.ts`、`commandOperations.ts`、`animationCommands.ts`、`schemaOverrideCommands.ts`）大多 `targets = []` 或仅用 `operationPathTarget`（no-op），因此**删字段对它们近乎零行为影响**，只是类型名/字段名跟随。

## Table-Specific Code（fieldPath + Action）

### 用户反馈的精确含义

`fieldPath.ts` 的字符串路径（`"['main']['floorIds']"`）与 `fieldToDataAttr` 是**表格寻址 + DOM 属性**，用户原话：「这些不应该是表格编辑才应该包含的内容吗？」。`action.ts` 的 `Action = [ActionType, string, unknown]` 用同一套字符串路径，二者强耦合。

### 耦合链（决定搬迁边界）

```
fieldPath.ts ── 被 ──> action.ts (applyActionsWithInverse 调 parse/build/get/set/delete)
action.ts ── 被 ──> operations.ts (ResourcePatchOperation 调 applyActionsWithInverse)
operations.ts ── 被 ──> 编辑器 (patchResourceOperation/compositeOperation)
editor 侧 ── patch(actions) ──> DataResource.mutate ──> applyActions (utils/action shim)
```

因此 `fieldPath` 不能单独搬走而不动 `Action`；`Action` 不能搬走而不动 `patchResourceOperation`。

### 三个搬迁方案（研究建议方案 1）

| 方案 | 内容 | 代价 |
|------|------|------|
| **1（推荐）** | `fieldPath.ts` + `action.ts` 迁 `lib/table/`（表格层）；`operations.ts` 的 `patchResourceOperation` 改为**接受一个「变更应用器」窄接口**而非直接依赖 `Action`；`Action` 的逆运算产物由表格层提供 | 需为 `patchResourceOperation` 重新定义窄契约；`table/index.ts` 是否 re-export 影响 `./table` 公开面 |
| 2 | 只把 `fieldPath.ts` 迁 `lib/table/`，`action.ts` 留 `lib/edit/`（因 `patchResourceOperation` 依赖它） | 半搬，`Action` 仍用表格字符串路径，耦合未真正解除 |
| 3 | 二者留 `lib/edit/`，仅**移出底层**（`lib/edit/` 本就是默认实现），不改路径 | 最小改动，但未回应用户「属表格层」的判断 |

**方案 1 的开放点：** `./table` subpath 当前是空 barrel，`subpathStatus.json` 记 `content: "empty-barrel"`，`coreExports.js` 期望 `empty-barrel`。若 `fieldPath` 经 `lib/table/index.ts` re-export，`./table` 公开面与 status 都要改；若只从根 `.` re-export（`lib/table/fieldPath.ts` 内部文件、`lib/index.ts` 直接再导出），则 `./table` 保持空 barrel、status 不变。**研究推荐后者**（保 `./table` 空 barrel），并在接口计划确认。

**`cloneActionValue`（用户反馈 #1）：** 它在 `applyActionsWithInverse` 里深拷贝「原值」以便生成 inverse（action.ts:124）。用 `structuredClone` 替代**不安全**：`cloneActionValue` 处理 `Date/RegExp/Map/Set`、保留属性描述符与原型，且遇到函数原样返回；`structuredClone` 会抛 `DataCloneError` on 函数/DOM 节点，且不保留原型。研究结论：**不替换**；若认为代码量值得，只把它收进类/私有方法并补注释，或随新操作接口整体改写。

## Standards Mechanics（D-07..D-15 ↔ 机器门禁）

### D-11 禁 `import type` 的机制

core 的 tsconfig（`packages/libs/editor-core/tsconfig.json:1-10`）extends `@motajs/config/tsconfig.lib.base.json`（`:1-31`）并只加 `paths` + `include`。lib 基础配置的 `compilerOptions` 全文只有：`target/useDefineForClassFields/lib/module/skipLibCheck/moduleResolution/allowImportingTsExtensions/isolatedModules/moduleDetection/noEmit/jsx/strict/paths/plugins` —— **不含 `verbatimModuleSyntax`**（只有 `packages/apps/editor/tsconfig.app.json` 开它）。[VERIFIED: packages/libs/editor-core/tsconfig.json:1-10 + packages/libs/config/tsconfig.lib.base.json:1-31]

因此：
- `import { SomeInterface } from './types'`（普通 import）在 `isolatedModules` + 无 `verbatimModuleSyntax` 下会被编译器**擦除**，不引入运行时依赖。[ASSUMED: TypeScript 标准行为，本会话未跑探针]
- **类型再导出**必须用 `export type { X } from './types'`（D-11 也这么要求）：`isolatedModules` 下用普通 `export { X } from` 再导出类型会报 TS1205。
- **陷阱：** 若某文件只做类型再导出（如 `ports/index.ts` 现状全是 `export type`），D-11 不禁 `export type`，所以这些文件**无需改**。

### D-07 `I` 前缀 ↔ 公开面（最大破坏点）

「会被 `implements` 的接口」清单（研究判定，最终以用户确认的 `INTERFACE-NAME.md` 为准）：

| 现名 | 是否会被 `implements` | 建议新名 | 破坏面 |
|------|----------------------|----------|--------|
| `EditorOperation` | 是（core 私有类 + 编辑器 6 处） | `IEditorOperation`（或 `IUndoableOperation`） | 编辑器 5+ 文件 + core 测试 |
| `ResourceView<T>` | 是（`ComputedResource`/`FileResource`） | `IResourceView<T>` | 编辑器 `project/resources.ts` shim + `DataResource` |
| `LoadableResource<T>` | 是（同上） | `ILoadableResource<T>` | 同上 |
| `RecoverableResource<T>` | 是（编辑器 `HandlerDataResource`） | 已带 I，**不动** | — |
| `IContentView`/`IContentHandler`/`IDataHandler` | 是 | 已带 I，**不动** | — |
| `PatchableResource<T>` | 结构满足（无 `implements` 关键字） | 倾向 `IPatchableResource` | 编辑器 `DataResource` 类型位置 |
| `FsPort` | 是（宿主/测试替身/编辑器 `fs.promises` 结构赋值） | `IFsPort`? | 编辑器 `appInstances.ts:30` |
| `HostPort` / `EngineAdapter` / `PreviewAdapter` | 是（适配器实现） | `IHostPort`/`IEngineAdapter`/`IPreviewAdapter`? | 编辑器 `src/adapter/motaEngine.ts:22`、`motaFloor.ts:14` |
| `OperationTarget` | 是（编辑器对象字面量） | **删除**（随快照一起去掉） | 编辑器 3 文件 |
| `UndoSystem` | 是（编辑器 `appInstances.ts`） | **删除** | 编辑器 `appInstances.ts` |

**关键结论：** 若 D-07 一刀切套到 ports 与资源视图，编辑器一侧将出现 10+ 处改名。**研究建议：** 在接口定义计划里明确区分——底层的 `I` 前缀先落到**新引入/重写**的接口（撤销、操作），而 ports 与资源视图的改名列为一个单独的、用户可见的破坏性决策；若用户坚持全量 `I` 前缀，则把它与「编辑器最小机械跟随」绑定为同一批计划。

### D-08 `types.ts` 落点

每个模块把**对外**接口/类型别名迁到同目录 `types.ts`；实现文件只 import 类型（普通 import）并 `export type` 转发或由 `index.ts` 汇总。需迁的典型：`kernel/core.ts` 的 `CapabilityRegistrar`/`EditorCoreConfig`/`EditorCore`；`edit/operations.ts` 的 4 个 interface；`edit/operationHistory.ts` 的 2 个 interface；`resources/interfaces.ts`（本就近 types）；`ports/*`（本就是纯接口文件，是否再拆 `types.ts` 需确认——研究建议**不拆**，port 文件本身就是契约文件）。

### D-10 文件头注释

现存几乎每个文件都有中文文件头块注释（如 `kernel/core.ts:1-16`）。D-10 要求：有 import 的文件第一行必须是 `import`；文件说明放到**所有 import 之后**。空 barrel（`lib/code/index.ts` 等）无 import，头部注释应删除。`lib/resources/errors.ts`（首行是 `interface`）无 import，也删头注。

### D-09 成员显式类型 ↔ ESLint

- `@typescript-eslint` 默认 `recommended` **不含**成员显式类型规则；需靠人工/评审（D-09 是约定）。
- 私有/受保护成员注释同理，无机器强制；`coreModuleState.js` 只查模块级可变绑定。
- `@typescript-eslint/no-explicit-any: warn`、`no-unused-vars: warn`（根配置）已存在；改造成 `warn` 不阻断 `pnpm lint` 退出码（`lint-severities.js` 要求 `eslint-disable` 带原因）。

## Common Pitfalls

### Pitfall 1: 门禁「绿但没在守」（配置与期望值漂移）
**What goes wrong:** 目录改名后 `coreModuleState.js` 的 `CORE_COMPOSITION_ROOT` 仍指旧路径，`--print-config` 采样到一个不存在的文件而静默通过；`.dependencyCruiser.cjs` 的 `kernel/.*` 正则匹配不到新路径，底层依赖规则空转。
**Why it happens:** 门禁硬编码路径；`coreBoundaries.js` 只 cruise core，规则不匹配＝不触发＝「通过」。
**How to avoid:** 用 Phase 2/3 的**两极性**范式：每条新/改规则都要有「合成违规必须失败」的证明；门禁常量与目录改动同次提交。
**Warning signs:** `coreBoundaries` 报 `error 违规 0 条` 但 `totalDependenciesCruised` 很小；`coreModuleState` 丢失「组合根 0 条受限消息」日志。

### Pitfall 2: 公开面改名击穿编辑器而无人察觉
**What goes wrong:** 只跑 `pnpm --filter @motajs/editor-core typecheck` 会绿，但 `pnpm typecheck`（全仓）红——编辑器 18 shim + `src/adapter/*` + `appInstances.ts` 引用旧名。
**Why it happens:** 编辑器通过 shim 间接消费，core 单包 typecheck 看不到消费方。
**How to avoid:** 任何公开面改动计划都必须把 `pnpm typecheck` + `pnpm lint` 列为验证命令；并明确 S1/S2 策略。
**Warning signs:** `editorShims.js` 报缺/多标记文件；`pnpm typecheck` 报 TS2305（模块无导出成员）。

### Pitfall 3: 删快照后「撤销恢复视口」行为静默改变
**What goes wrong:** 删 `UndoSystem` 后，纯数据操作 undo 不再恢复视口；`packages/apps/editor/src/project/history/__tests__/operationHistory.test.ts:62-70` 变红。
**Why it happens:** Phase 4 的 capture-all 是唯一承担该行为的机制（`appInstances.ts:58-61`）。
**How to avoid:** 把「数据 undo 不再恢复视口」作为**有意的行为变更**单独提请用户确认，并同批处置该编辑器测试。
**Warning signs:** 编辑器全仓测试红在 `operationHistory.test.ts` 的 `expect(currentViewport.floorId).toBe('sample0')`。

### Pitfall 4: `import type` 误判与类型再导出
**What goes wrong:** 为满足 D-11 把 `export type { X } from` 也改成普通 `export`，触发 `isolatedModules` 的 TS1205；或误以为普通 import 类型会进运行时。
**Why it happens:** D-11 只禁 `import type`，**不禁** `export type`；core 未开 `verbatimModuleSyntax`，普通 import 的类型会被擦除。
**How to avoid:** 只改 `import type` → `import`；保留所有 `export type`。
**Warning signs:** `tsc` 报 TS1205「Re-exporting a type when 'isolatedModules' is enabled requires using 'export type'」。

### Pitfall 5: `core.react` 探针被误当作「默认实现可删」
**What goes wrong:** 认为 `CoreProbe.tsx` 是 Phase 2 脚手架、顺手删掉，导致 `corePandaClass.js`（期望 `.display_block`）与 `coreReactCompiler.js`（硬编码该路径）双红。
**Why it happens:** 探针无产品用途，但在两个门禁里是承重件。
**How to avoid:** 本阶段**保留** `lib/react/CoreProbe.tsx` 与其 `css\`display: block;\``。
**Warning signs:** `coreReactCompiler: transformRequest(...) 未返回转换结果`。

### Pitfall 6: `fieldPath` 搬迁触碰 `./table` 公开面
**What goes wrong:** 把 `fieldPath` 从 `lib/table/index.ts` re-export，`./table` 从空 barrel 变成有内容 → `subpathStatus.json` 的 `content: "empty-barrel"` 与 `coreExports.js` 期望不符。
**Why it happens:** `exports` 映射把 `./table` 指向 `lib/table/index.ts`。
**How to avoid:** 只从根 `.` re-export（`lib/table/fieldPath.ts` 为内部文件），保 `./table` 空 barrel。
**Warning signs:** `coreExports: subpathStatus.json 的 "./table" content 应为 "empty-barrel"`。

### Pitfall 7: `coreEngineNeutral.js` 误伤新代码
**What goes wrong:** 新写的注释/名字含 `floor`/`loc`/`tower` 等词即判红（扫描**原始源码含注释**，大小写敏感）；`MIN_EXPECTED_SOURCES = 30` 在目录重排把文件数压到 30 以下时红。
**Why it happens:** 门禁设计如此（Pitfall D）。
**How to avoid:** 新代码与注释用引擎中立措辞；重排时保持生产文件数 ≥ 30（当前 37）。`Math.floor` 因成员访问豁免不误报。
**Warning signs:** `coreEngineNeutral: 真实树出现 N 条引擎标识违规`。

## Open Questions

1. **公开面改名 vs 编辑器不动（S1/S2）**
   - What we know: `D-07` 若全量 `I` 前缀会重命名编辑器实际使用的 10+ 个接口；编辑器 18 shim + adapter + appInstances 会红。
   - What's unclear: 用户是否接受「旧名以别名保留到 Phase 12」。
   - Recommendation: 接口计划里把「哪些名字改名、旧名是否保留别名」列成一张表请用户逐项确认；默认 S1。

2. **撤销接口的最终形状（A/B）**
   - What we know: 现有 `apply() → inverse` 已能满足 D-04。
   - What's unclear: 用户要「操作自带 undo/redo 方法」还是「操作返回逆操作」。
   - Recommendation: 推荐 A（改动最小、行为等价最易证）；在 `INTERFACE-NAME.md` 呈现两种签名供选。

3. **`ResourceRegistry` 是否入底层**
   - What we know: 它是纯登记管理；但登记值为 `ResourceView`。
   - What's unclear: 用户是否要求它也进底层。
   - Recommendation: 进底层但泛型化解耦（`register<V>` 或 `IRegistry<V>`），否则留默认实现。

4. **`OperationHistoryEntry.paths` 的新来源**
   - What we know: 现在 `paths` 来自 `targets`（operationHistory.ts:190），删 target 后无来源。
   - What's unclear: 是让操作自报路径（`meta.paths`）还是删掉该字段。
   - Recommendation: 若编辑器 UI 不消费 `paths`（需核）则删；否则移到操作元数据。

5. **「数据 undo 不恢复视口」的行为确认**
   - What we know: D-05 直接导致；编辑器一个测试钉住旧行为。
   - What's unclear: 是否视为可接受的行为变化。
   - Recommendation: 单独提请确认，并在编辑器的「机械跟随」计划处置测试。
