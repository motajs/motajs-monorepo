<objective>
在现有底层目录上（**不新建 `lib/core/`、不搬任何文件**）让机器门禁守住两件事：底层**不依赖上层**、
底层**不读文件**。行为零变化，只做两处内容归位（内核接口收拢进 `lib/kernel/types.ts`、
`isValidResourceId` 改为底层自持）与门禁规则更新。

Purpose（说人话）：现在这些代码混在一起，分不清「谁是底层、谁是上层功能」。其实底层不用新建文件夹——
它本来就是现有的 `lib/kernel/`（内核、能力登记）加 `lib/ports/`（引擎/宿主/文件读写接口）。这一步用自动
检查把门关死：以后谁想在底层里读文件、或者让底层反过来依赖表格/地图那些功能，机器立刻报错，不靠人自觉。
顺带把两个历史遗留理顺：内核的对外类型收拢到一个文件，逻辑 id 的判定归到底层（别让底层反过来问上层要）。

Decisions implemented here — D-01 (two layers with a one-way dependency), D-02 (the bottom layer only
*defines* file IO and never calls it), D-08 (exported types centralized), D-14 (LF), D-15 (dev.md
conventions where touched).

**Open decisions resolved here (research flagged them; names are provisional pending the user's briefing):**
- **Layout (D-01, user-directed):** the two layers are a *logical* split. The bottom layer is physically the
  existing `lib/kernel/**` + `lib/ports/**`; the package default implementations stay in
  `lib/resources/`, `lib/edit/`, `lib/table/`, the capability dirs and `lib/react/`. **No `lib/core/` folder
  is created and no file is moved.** The only new thing is the one-way dependency rule below.
- **File IO disposition (D-02):** `lib/resources/fileHandler.ts` / `fileHandlerManager.ts` /
  `persistExecutor.ts` / `persistenceMonitor.ts` / `binaryFileHandler.ts` / `fileResource.ts` all **stay
  in `lib/resources/`** (the package default-implementation layer). The bottom layer keeps exactly one
  file-IO artefact: `lib/ports/fs.ts` (`IFsPort`) — the interface only. The bottom layer must never
  call it; Task 3 makes that a two-polarity gate.
- **`ResourceRegistry` home (research open decision c):** it **stays in `lib/resources/`** (default
  implementation), not the bottom layer. Rationale: it registers content views (`IResourceView`), and D-03
  forbids the bottom layer from knowing anything about edited content. The bottom layer's registration
  mechanism is `EditorCore.registerCapability` (already there). The only change this plan makes is the
  direction of the shared logical-id predicate: `isValidResourceId` (with `LOGICAL_ID_PATTERN`/`RESERVED_IDS`
  and the prototype-pollution guard) becomes bottom-owned in `lib/ports/engine.ts` and `resourceRegistry.ts`
  imports it from the bottom layer (default impl → bottom). The user may veto and ask for the
  generic-registry variant instead.
- **Type-only edge scope (checker warning — resolved as the "record it" route, not "sink it"):**
  `lib/ports/engine.ts` holds two **type-level** imports from `lib/resources/` (`ResourceView` from
  `resources/combinators`, `FileHandlerManager` from `resources/fileHandlerManager`).
  dependency-cruiser 18.2.0 keeps only imports that are used in a **value** position (verified by probe:
  its TS transpile elides type-only usage whether or not `import type` syntax is used), so the value-level
  rule reports 0 while these type annotations remain. Sinking those interfaces into the bottom layer is
  rejected here: it would contradict D-03 (the bottom layer must not define a unified edited-content
  abstraction) and this plan's encoded file-IO disposition (§ above: all file-IO artefacts stay in
  `lib/resources/`, the bottom keeps only `lib/ports/fs.ts`). Instead this plan **explicitly narrows
  the gate's declared claim to value-level edges** and closes the blind spot with a visible, allowlisted
  enumeration in `coreBoundaries.js`: every import in `lib/kernel/**` + `lib/ports/**` that points at an
  upper-layer directory — `import type` included — is enumerated, folded into **(source file, upper-layer
  directory)** pairs, and must match an explicit allowlist whose only current entry is `lib/ports/engine.ts →
  resources`; any new source file or new upper-layer directory fails. Keying on the **directory** (not the
  exact specifier) is deliberate: Plan 06 rewrites that import from `resources/combinators` to
  `resources/interfaces`, and Plan 07 drops `import type` package-wide — neither changes the directory key,
  so the allowlist does not drift.
- **Root `.` barrel vs the old kernel rule (blocker — resolved by collapse):** Plan 05 (and the phase's
  "公开名零变化" rule) require the root `lib/index.ts` to keep re-exporting the value symbols moved to
  `lib/table/` (`parseFieldPath`, `applyActionsWithInverse`, `patchResourceOperation`, …). The retained
  `kernel-must-not-import-capabilities` rule still bound `lib/index.ts`, so that re-export would trip it
  (`lib/index.ts -> lib/table/…`). This plan therefore **removes `kernel-must-not-import-capabilities` and
  folds its intent into the single `bottom-layer-must-not-import-upper-layers` rule** (the research already
  recommended collapsing the two; the old rule's `to` set is a subset of the new one's, so the bottom layer
  loses no coverage). The bottom layer *is* `lib/kernel/**` + `lib/ports/**`; `lib/index.ts` is the package
  public surface and is intentionally free to re-export capability symbols.
- **Kernel interfaces (D-08) + `lib/ports/engine.ts` (Phase 5 core content):** the three kernel interfaces
  `CapabilityRegistrar`/`EditorCoreConfig`/`EditorCore` are **collected** from `lib/kernel/core.ts` into
  `lib/kernel/types.ts` (Plan 01's bottom-layer type exit); `lib/ports/engine.ts` keeps its shape, only the
  `isValidResourceId` direction changes; `lib/resources/fileResource.ts` and the `engineB` fixture stay put.

Spec-less probe: `phase_req_ids` is null for this inserted phase — the probe visibly skips; acceptance is
grounded in `05.1-CONTEXT.md` D-01..D-19.

Output: the bottom layer declared as `lib/kernel/**` + `lib/ports/**` (no move), an updated
`lib/kernel/types.ts` + `lib/index.ts` re-export source, a bottom-owned `isValidResourceId`, one updated
dependency-cruiser rule, and a new bottom-layer IO-zero + dependency-direction assertion with two-polarity
proof.
