# Phase 05.1: editor-core 接口与实现整改 - Context

**Gathered:** 2026-09-28
**Status:** Ready for planning

<domain>
## 这个阶段要做什么

把 `@motajs/editor-core` 这个包装成**两层**，并按既定的编码规范重写：

1. **底层（真正的「core 本身」）**：只提供**接口** + **管理**功能（比如登记能力、管撤销的操作栈）。它像操作系统——不读文件、不持有编辑内容、不知道上层在编辑什么。
2. **包内的默认实现（在包里，但不算底层）**：表格编辑、地图编辑、代码编辑这类「基本的上层功能」。它们**依赖底层**，**自己持有自己的内容**，是包默认提供的。

引擎那份（mota-js）在**更上面**，本阶段不动。

**一句话**：底层只定义接口、只管调度；具体编辑功能放在包里的上层，自己管自己的内容。

**范围**：`packages/libs/editor-core/**` 全部（底层 + 包内默认实现 + 测试）。
**不在范围**：`@motajs/editor`（mota-js 上层）、新增功能、对外行为变更、插件加载器。

**注意**：本阶段会**取代/改写 Phase 5 刚交付的 core 内容**（接口重划后，那些实现要跟着改）。

</domain>

<decisions>
## Implementation Decisions

### A. 结构：底层 vs 包内默认实现
- **D-01:** `editor-core` 包分两层。**底层（core 本身）** = 接口 + 管理（能力登记、撤销操作栈等）；**包内默认实现** = 表格/地图/代码编辑等基本编辑功能，依赖底层、自己持有内容。引擎实现（mota-js）在更上层，本阶段不动。 — **Reversibility:** costly —— 这是整个包的骨架，一旦定下，后面所有能力都按它组织；改它等于重组整个包。
- **D-02:** **底层不读文件**。它只**定义**「文件读写」的接口，**现阶段不调用**；数据来源完全由上层负责。
- **D-03:** **底层不知道编辑内容**。不定义任何「被编辑内容」的统一抽象；内容由包内的默认实现各自持有（表格编辑系统存表格数据，地图编辑系统存地图数据）。

### B. 撤销
- **D-04:** **底层只提供「撤销管理器」，只管操作栈**（记录先后、撤销时调该操作的撤销、重做时调重做）。**每个操作自带它怎么撤销/重做**，core 不认识操作细节、**不保存快照**。
- **D-05:** 移除现有的**快照式**撤销（现在上层状态靠 `capture()/restore(snapshot)`，并把前后快照存进历史条目）。外部系统的撤销也改为「保存操作」而非「保存快照」。

### C. 内容来源
- **D-06:** 底层不管内容从哪来；由包内默认实现自己持有内容、由使用者喂入。（与 D-03 一体两面。）

### D. 编码规范（套到 `editor-core` 包全部，含测试）
- **D-07:** 会被 `implements` 的接口统一加 **`I` 前缀**；每个类必须 `implements` 对应接口，不能有裸类。
- **D-08:** 对外导出的类型（接口/类型别名）集中到各自的 **`types.ts`**，不与实现写在同一文件。
- **D-09:** **接口本身写「它是干什么的」中文注释**；公共成员注释写在**源头（声明处）**；私有/受保护成员也要写注释；**所有成员显式声明类型**。注释只在源头出现，源头之外除非说明行为变化，否则不加注释。
- **D-10:** **文件第一行是 `import`**，禁止文件头注释；`import` 之间不得有空行或注释；想写文件说明就放在所有 import 之后。
- **D-11:** **`editor-core` 禁止 `import type`**（用普通 import；类型再导出用 `export type`）。
- **D-12:** **尽量减少裸函数**：只有「与实例无关的纯工具」可以留裸函数（如路径解析、等待工具）；有状态/可实例化的都要用类。
- **D-13:** **保留行为关键路径的 `try/catch`**（撤销回滚、持久化失败隔离、诊断订阅隔离）；只在新写/整理代码时不新增 `try/catch`。
- **D-14:** **换行符保持 LF**（不采用 dev.md 的 CRLF；仓库已是 LF）。
- **D-15:** 其余按 `E:\github\template\dev.md`（命名、注释风格、类型规则、模块无副作用、无循环引用等）。

### E. 流程
- **D-16:** **第一批计划只做接口定义**（接口 + `INTERFACE-NAME.md` 命名清单），经用户确认后，再排写实现的计划；**严禁**把「接口设计与定义」和「实现」放进同一个计划。 — **Reversibility:** costly —— 接口是后续所有实现的依据，先定后改会推翻实现。
- **D-17:** 重要命名先写入本阶段的 `INTERFACE-NAME.md`（每个 Plan 一节，说明用途），经用户确认才落盘。

### F. 改名与编辑器兼容 / 行为变化
- **D-18:** 接口改名（`I` 前缀等）后，**旧名临时保留为指向新名的别名**，直到后续阶段删除；`@motajs/editor`（mota-js 上层）**本阶段一行不改**，全仓保持可编译（typecheck/test 绿）。 — **Reversibility:** costly — 别名是过渡结构，删它需要编辑器侧同步跟上。
- **D-19:** **确认一处行为变化**：撤销一次数据改动**不再连带恢复地图视口**（旧实现靠快照连带恢复，且被测试钉住）。视口恢复改由地图编辑将来自己作为一个「操作」处理。 — **Reversibility:** costly — 这是对外可见的行为变更，需要后续阶段补上「视口恢复作为操作」。

### 待解决开放点（planner/researcher）
- 底层与包内默认实现的**目录划分**与**依赖方向**（默认实现依赖底层，不得反向）。
- 撤销管理器接口的**具体形状**（只到「能登记操作、能撤销/重做、有状态」这一步；具体签名在接口定义计划里给出并确认）。
- 包内默认实现的**内容持有方式**如何统一（各自持有，但是否有共同的约定）。
- 「文件读写」接口的**定义范围**（只定义、不调用）。

### the agent's Discretion
- 上述开放点的具体形状、文件划分、命名 —— 均须先入 `INTERFACE-NAME.md` 并经用户确认（Project Rules）。

</decisions>

<specifics>
## Specific Ideas

- **core 像操作系统**（用户原话）：「core 本身只是一个底层操作系统，上层程序干什么它管不到。」
- **两层归属**（用户原话）：「表格编辑、地图编辑等等，它们是包含在 editor-core 包里面的，但是不属于 core 本身，它们并不是底层，而是依赖于底层的默认提供的功能。」
- **底层不知道内容**（用户原话）：「core 本身不需要知道编辑的内容。」
- **撤销存操作不存快照**（用户原话）：「外部系统的撤销与重做也不是保存快照与读取，而是保存操作，系统根据操作本身来回退。」
- **责任分层**（用户原话）：「引擎本身不应该包含任何关于撤回实际操作的行为，它只负责管理现有对象的撤回与重做。」
- **表格寻址不属 core**（用户原话）：「fieldPath.ts 里面接口的存在意义，这些不应该是表格编辑才应该包含的内容吗？」
- **fs 只在顶层**（用户原话）：「fs 是最顶层的读取接口，它就不应该出现在这里。editor-core 可以提供 fs 的接口定义，但是现阶段不应该调用它。」
- **说人话**（AGENTS.md 规则）：计划、简报、评审等给人看的文字，要让完全不懂项目的人一句话看懂。

</specifics>
