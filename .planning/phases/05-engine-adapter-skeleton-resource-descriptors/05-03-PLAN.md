<objective>
Deliver the one file-backed `ResourceView` class core is allowed to own, then prove the adapter contract
is not mota-shaped by building a fake non-mota "engine B" that drives `defineEngine` → validation →
`ResourceRegistry` → get-by-id → preload order end to end.

Purpose: D-06 keeps exactly one class in core that knows about an IO address, so an adapter can build a
file-backed resource without a `path` on the generic descriptor; and PORT-08 requires a second,
non-mota implementation before the extension point can be frozen (PITFALLS Pitfall 6/14). The non-file
engine-B resource is the mechanical proof that the descriptor does not assume content comes from a file.

Output: `lib/resources/fileResource.ts` + its unit tests, `lib/__tests__/engineB.ts` +
`lib/__tests__/engineB.test.ts`, the `FileResource` barrel export, and extended
`coreApiSurface.test.ts`.

Dependencies: `depends_on: [05-01, 05-02]` (wave 3) — engine B builds on the contract 05-01 delivers, and
this plan's Task 2 verify runs the game-identifier gate `scripts/verify/coreEngineNeutral.js` that 05-02
installs, so the ordering is declared rather than implied.

Decisions implemented here — D-04: the generic descriptor stays path-free; the address lives only inside
this class. D-06: `FileResource` is bound to an id + opaque address + handler factory and uses the
per-instance `FileHandlerManager`. D-11: engine B is a core test fixture run with every core test.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| adapter-authored descriptor → `FileResource` | The IO address is adapter-supplied data; core must treat it as opaque and introduce no path interpretation that could enable traversal or engine coupling. |
| test fixture → core production source | The engine-B fixture lives under `__tests__`; a fixture that reached production source would leak non-mota vocabulary into core — guarded by the 05-02 gate. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-02 | Tampering (path traversal) | `FileResource` address handling | high | mitigate | The address is an opaque string passed straight to `FileHandlerManager.get`; the class decodes/joins nothing; core owns no path-normalisation surface (`ports/fs.ts:16-18`). Path safety remains the host's job. Canon-referral to `/gsd-secure-phase`. |
| T-05-09 | Information Disclosure | Non-file resource silently reading the filesystem | medium | mitigate | `engineB.test.ts` asserts the non-file view performs zero `FsPort` reads, making "content is not assumed to be a file" a machine check. |
| T-05-10 | Tampering | A second file/caching layer re-implementing the tested one | medium | mitigate | `FileResource` delegates to `FileHandlerManager`/`DataHandler`; it holds no cache and no persistence logic, so the tested load-lock/serialization guarantees are not duplicated. |
| T-05-11 | Elevation of Privilege (boundary erosion) | `lib/resources/fileResource.ts` | medium | mitigate | The class consumes only `FsPort` and the file layer; `coreModuleState.js` (PORT-02) stays green, proving no DOM/network capability entered core. |
| T-05-SC | Tampering | npm/pip/cargo installs | high | mitigate | This phase installs no package; the fixture uses `alien-signals` and existing core modules only. Any proposed dependency halts for the Package Legitimacy Gate. |
