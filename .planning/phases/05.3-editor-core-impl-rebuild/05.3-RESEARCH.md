# Phase 05.3: editor-core/impl 重做 - Research

**Researched:** 2026-10-04
**Domain:** TypeScript 纯接口库实现（编辑器内核：撤销 / 资源 / 面板三大系统 + Hook 桥接 + React 渲染根）
**Confidence:** HIGH（接口与代码事实）/ MEDIUM（设计取舍）

## Summary

本阶段不研究"选什么库"——技术栈已由用户与既有仓库锁定，**不需要任何新运行时依赖**。真正要回答的是：在**用户已写好的接口文件一个字都不能改**的前提下，如何新增实现文件、如何组织模块依赖不产生环、如何让资源缓存失效与 Hook 通知正确桥接到面板、如何让面板切换可撤回、如何处理生命周期与 `render()` 的 React 响应式，以及如何让 `src/index.ts` 的公开面与既有的 `scripts/verify/*.js` 门禁在新的 `src/` 源码根下自洽。

研究过程中发现**三个必须先解决的基础设施问题**，否则实现写完也跑不起来或测试假绿：

1. **`@/` 别名解析在新源码根下是坏的**。`packages/libs/config/resolvePlugin.js` 对 `packages/libs/*` 一律把 `@/` 解析到 `lib/`，但两包源码根已改为 `src/`。实测 `@/hook` → `packages/libs/editor-core/lib/hook`（不存在）。用户接口文件大量使用 `@/hook`、`@/undo`、`@/resource`、`@/panel`，所以 tsc 能过（tsconfig paths 指向 `src`），但 **vitest/Vite 一定解析失败**。
2. **editor-core 现在依赖了第二份 React**。`editor-core/package.json` 写 `react: ^19.3.0`、`@types/react: ^19.3.0`，而 catalog/编辑器应用是 `react: 19.2.3`（精确）。pnpm 已实装两份 `react@19.2.3` 与 `react@19.3.0`。一旦 editor-core 的 `render()` 用 hooks，就会出现"Invalid hook call"（两份 React 实例）。必须在实现前把版本对齐去重。
3. **门禁与 ESLint 全部硬编码 `lib`**。`coreModuleState.js`/`coreImportType.js`/`coreEngineNeutral.js`/`coreBoundaries.js`/`coreExports.js`/`implExports.js`/`corePandaClass.js`/`coreReactCompiler.js`、`.dependencyCruiser.cjs`、`eslint.config.js` 的 module-state 忽略项、`panda.config.ts` 的 include、以及 `subpathStatus.json` 都指向 `lib`。当前**八道门禁大面积变红**（详见 Environment Availability 与 Open Questions），`prettier-setup.js` 还因 `.prettierrc.json` 被改名成 `.prettierrc` 而红。

**Primary recommendation:** 先做"基础设施对齐"（别名 / React 去重 / 门禁与 ESLint 的 `lib→src` 迁移 / 测试依赖补齐），再按 INTERFACE-NAME 的 05.3-02..05 顺序实现三大系统与 `EditorCore`；实现层严格按 `hook ← resource ← panel`、`undo ← panel`、`core ← 三者` 的单向依赖，资源缓存与 Hook 桥接全部放在 `resource`/`panel` 各自层内，**`resource` 绝不 import `panel`**。

## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| 功能注册 / 请求数据 / 撤回管理 / 页面管理（接口与管理壳） | editor-core（系统层） | — | D-06：core 不预设任何需求，只提供最底层接口与管理；不含任何具体功能 |

**F. editor-core 接口框架（2026-10-03 讨论定稿）**

**核心与入口**
- **D-12:** `editor-core` 公开面只有 `IEditorCore`：`version` + 三个系统（`undoSystem` / `panelSystem` / `resourceSystem`）+ `initialize(injection)` + `dispose()`；**没有 `render()`**，渲染根由 `panelSystem.render()` 提供。
- **D-13:** 三个系统统一用 `initialize(injection)`（初始化并注入），且均为 `Promise<void>`：`IUndoSystem.initialize(IUndoInjection)`、`IResourceSystem.initialize(IResourceInjection)`、`IPanelSystem.initialize(IPanelInjection)`；原 `inject` 一律改名 `initialize`。
- **D-14:** `IEditorCoreInjection = IUndoInjection & IResourceInjection & IPanelInjection`，由 `IEditorCore.initialize` 一并下发给三个系统。
- **D-15:** `IPanelInjection` 暂为空接口占位（后续可能加内容）；注入只给 `IPanelSystem`，**面板本身不接收注入**（`IEditorPanel.initialize()` 无参）。
- **D-16:** 导出 `EditorCore` 类，构造器内部自己 new 三个系统；三个系统类也导出，但仅为接口统一、外部一般用不到。core / impl 都不提供「创建入口」，由**编辑器顶层构造 core**。

**资源**
- **D-17:** `IResourceIdentifier = { readonly type: number; readonly id: string }`；`type` 由外部枚举定义，core 不预设资源类型。
- **D-18:** `IResource<T>` 是面板持有的资源句柄：`request()` 读、`write(data)` 写；`IEditorPanelContext.requestResource(id)` 返回 `Promise<IResource<T> | null>`。
- **D-19:** 系统缓存资源列表——首次 `requestResource(id)` 触发 `requestResourceList(type)` 并缓存，命中返回句柄、未命中返回 `null`。
- **D-20:** 资源内容也缓存；`updateResource(id)` 时刷新缓存，`write(data)` 也同步更新缓存。
- **D-21:** `IResourceInjection` 是后端实现：`requestResource` / `requestResourceList` / `writeResource` / `createResource` / `deleteResource`。
- **D-22:** 创建 / 删除**只有面板能发起**（panel context 的 `createResource` / `deleteResource`），外部不需要；完成后调 `updateResourceList` 刷新列表并广播所有面板。创建 / 删除需要撤回，由面板自己 `addUndoContext` 记录。
- **D-23:** `write` **不触发** `updateResource`；`updateResource` 由外部监听触发。写入后有短暂防抖、期间不接受 `updateResource`（避免面板重复解析）——此细节用户表示**暂不重要，先不管**。
- **D-24:** `updateResource(id)` / `updateResourceList(type)` 刷新后，`onUpdateResource` / `onUpdateResourceList` **广播给所有面板**，各面板自行判断是否需要。
- **D-25:** 撤回**不触发** `updateResource`（撤销不等于保存，不触发外部监听）。

**面板**
- **D-26:** `IEditorPanel` 是功能单元：`id`、`initialize` / `dispose` / `render()`、`onFocus` / `onBlur`（浏览器窗口焦点进 / 出编辑器）、`onSwitchIn(param?)` / `onSwitchOut`（面板之间切换）、`onUpdateResource` / `onUpdateResourceList`；并 `extends IUndoable`。
- **D-27:** `EditorPanelCreator = (context: IEditorPanelContext) => Promise<IEditorPanel>`；面板创建时拿到 context（请求资源、创建 / 删除、加撤回）。
- **D-28:** `IPanelSystem`：`currentPanel`（同一时刻只有一个前台面板）、`registerPanel`（id 强制唯一）、`getPanel(id)`、`switchTo(panel, param?)`、`disposePanel`、`render()`、`dispose()`；并 `extends IUndoable`。
- **D-29:** 面板粒度为「工作区 / 模式」；多个编辑器同屏由面板 / impl 自己排布，core 只支持一个前台面板。
- **D-30:** 生命周期——未 `initialize` 时 `registerPanel` 只创建、不调 `initialize`，待 core.initialize 后一并补调；已 `initialize` 时 register 直接调 `initialize`。

**撤回**
- **D-31:** `IUndoContext<T> = { readonly type: number; readonly data: T }`；`IUndoable` = `undo` / `redo`；`addUndoContext(undoable, context)` 由编辑者主动记录；面板上下文的 `addUndoContext` 直接调 `IUndoSystem.addUndoContext`。
- **D-32:** 面板切换占撤回步——`IPanelSystem extends IUndoable`；内部 `internalSwitchTo` 不记录、公共 `switchTo` 记录，避免撤销时自证循环。
- **D-33:** `maxUndoStep` 预期 200–1000；只对撤回系统有意义，外部不需要。撤销 / 重做由撤回系统按操作者（面板或面板系统）自动确定撤谁，面板之间无需互相感知。

**流程补充**
- **D-34:** 修改接口设计前必须先向用户汇报、经确认后才可改；实现中发现接口不够用也一样，先报后加。

**G. 资源读写边界与 Hook 通知（2026-10-03 追加，更正 D-20 / D-24）**
- **D-35:** 资源**读写只对面板开放**——唯一入口是 `IEditorPanelContext` 的 `requestResource` / `requestResourceList` / `createResource` / `deleteResource`；对外暴露的 `IResourceSystem` **不含**这些读写方法。
- **D-36:** 搬入游戏引擎的 Hook 系统（`src/hook/`：`IHookBase` / `IHookController` / `IHookObject` / `IHookable` 接口 + `Hookable` 抽象类 + `HookController`）。`IResourceSystem extends IHookable<IResourceSystemHooks>`；`IResourceSystemHooks.onUpdateResource(id)` / `onUpdateResourceList(type)` **只带 id / type**，收到者自行重新申请资源获取新内容。
- **D-37:** 资源更新到面板的桥接——`PanelSystem` 为每个面板向资源系统挂 `EditorPanelHooks`（构造时传入该面板的 context），钩子重新申请资源后通知面板。据此更正 D-20 / D-24：`updateResource(id)` 负责**作废缓存并触发钩子**；由钩子重新申请并把内容交给面板（面板层 `onUpdateResource(id, data)` 不变）。`write(data)` 仍同步更新缓存且不触发 `updateResource`（D-23 不变）。

## Architecture Patterns

### System Architecture Diagram

下面的数据流展示"面板请求资源 / 资源更新广播 / 面板切换撤回"三条主链路。箭头方向即依赖与调用方向。

```text
                         编辑器顶层（未来的 @motajs/editor）
                                    │ new EditorCore()
                                    │ initialize(IEditorCoreInjection)
                                    ▼
                         ┌───────────────────────────────┐
                         │          EditorCore           │
                         │  version / 三系统引用 / dispose │
                         └───────┬───────────┬───────────┘
                                 │           │
              new + initialize   │           │  new(undoSystem, resourceSystem)
                                 ▼           ▼
        ┌──────────────────┐        ┌──────────────────┐        ┌──────────────────┐
```

### Pattern 2: Store + useSyncExternalStore（`render()` 响应式）

**What:** `PanelSystem` 内部持有 `Store<{ currentPanel: IEditorPanel | null }>`；`switchTo`/`internalSwitchTo` 调 `store.setState`；`render()` 返回一个**稳定的**组件（在构造器里创建一次并缓存），组件内用 `useSyncExternalStore(store.subscribe, () => store.state.currentPanel)` 订阅。
**When to use:** 让 core 的渲染根随 `currentPanel` 变化重渲染。
**Example:**
```tsx
// Source: https://react.dev/reference/react/useSyncExternalStore（React 官方）
// 组件必须在构造器内创建一次，避免每次 render() 返回新函数导致 React 反复卸载重挂
private readonly RootComponent: FC = () => {
  const currentPanel = useSyncExternalStore(this.store.subscribe, this.getCurrentPanel);
  if (!currentPanel) return null;
  const Panel = currentPanel.render();
  return <Panel />;
};

private readonly getCurrentPanel = (): IEditorPanel | null => this.store.state.currentPanel;
```
**关键约束（React 官方）：** `getSnapshot` 在 store 未变时必须返回同一引用，否则会死循环/报错——`[CITED: react.dev/reference/react/useSyncExternalStore]`。`this.getCurrentPanel` 作为稳定实例字段传入可避免重订阅。

### Pattern 3: 缓存 + 失效 + 广播（资源系统核心）

**What:** 列表缓存 `Map<number, readonly IResourceIdentifier[]>`、内容缓存 `Map<number, Map<string, unknown>>`（用 `type` 与 `id` 双层键，避免拼接键的歧义）。
**When to use:** D-19/D-20/D-23/D-37 的全部读写路径。
**Example:**

### Anti-Patterns to Avoid

- **`resource` import `panel`**：会让 `resource → panel → resource` 成环（`no-circular` 门禁判红），且违背 D-37 的分层。资源更新桥接必须放在 `panel` 层（`EditorPanelHooks`）。
- **模块级可变状态**：`eslint.config.js` 的 module-state 规则禁止 `Program > VariableDeclaration` 的 `let`/`var`、以及模块级 `const = new Map()/[]/{}`——`[VERIFIED: eslint.config.js:165-195]`。所有状态放实例字段（`Hookable` 自己就是实例字段）。
- **在 `render()` 里新建组件**：每次返回新的 `FC` 会让 React 卸载重挂。组件只创建一次并缓存。
- **直接 `import type`**：`coreImportType.js` 门禁禁止 `import type`（D-11 历史约束）；用普通 import，类型再导出用 `export type`。
- **在 core 源码直接触达 `window`/`document`/`fetch`/`process.env`/`import.meta.env`**：`corePort02Config` + `coreModuleStateConfig` 以 error 级拦截——`[VERIFIED: eslint.config.js:96-141]`。
- **游戏词汇进入 core**：`coreEngineNeutral.js` 以 `BANNED_TERMS = ['tower','floor',…]` 大小写敏感扫描 core 生产源码——`[VERIFIED: scripts/verify/coreEngineNeutral.js:47-49]`。

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| 一对多 Hook 广播与控制器生命周期 | 自己写 `Set<listener>` + 手动清理 | `Hookable` / `HookController`（`src/hook/`，用户已写） | 已有 `awake`/`destroy` 生命周期与 `removeHookByController`；重复实现会与门禁/命名不一致 |
| React 外部 store 订阅 | `useEffect` + `forceUpdate` 手写订阅 | `@tanstack/store` 的 `Store` + React 内置 `useSyncExternalStore` | 官方推荐、并发安全；手写订阅易漏清理、易 tearing |
| 资源缓存键 | 字符串拼接 `${type}:${id}` | 双层 `Map<number, Map<string, unknown>>` | `id` 可能含任意字符，拼接键有歧义；双层键类型安全 |
| 撤销栈裁剪 | 自己写环形缓冲 | 普通数组 + `shift()`/`splice` | `maxUndoStep` 200–1000，规模极小，朴素实现足够（D-09 朴素优先） |
| 面板切换撤回 | 每个面板互相感知对方状态 | `PanelSystem` 记录一个 `Switch` 上下文 + `internalSwitchTo` | D-32/D-33：由撤回系统按操作者自动决定撤谁，面板之间不互相依赖 |

**Key insight:** 本阶段的所有"机制"要么已在 `src/hook/` 由用户写好，要么是 React/TS 标准设施；实现的价值在于**接线正确**，不在于发明新抽象。D-09 明确要求朴素、不过度拆分。

## Common Pitfalls

### Pitfall 1: `@/` 别名在 `src/` 根下解析到 `lib/`（HIGH，必现）
**What goes wrong:** vitest/Vite 通过 `resolvePlugin` 解析 `@/hook` 得到 `packages/libs/editor-core/lib/hook`（不存在）→ 任何导入 `@/` 的测试/构建直接报 ENOENT/解析失败。
**Why it happens:** `resolvePlugin.js` 按包类型硬编码：`libs → lib`、`apps/external → src`——`[VERIFIED: packages/libs/config/resolvePlugin.js:10-20]`；两包源码根已改为 `src`。
**How to avoid:** 修 `resolvePlugin.js`（当包内存在 `src/` 时对 `libs` 也返回 `src`），或为两包在 `vitest.config.ts` 显式加 `resolve.alias['@'] = <pkg>/src`。必须经用户批准（共享配置）。
**Warning signs:** `pnpm --filter @motajs/editor-core test` 报找不到 `@/...`；`resolvePlugin.resolveId('@/hook', <src file>)` 返回 `.../lib/hook`。

### Pitfall 2: 两份 React → "Invalid hook call"（HIGH）
**What goes wrong:** editor-core 用 `useSyncExternalStore`（来自它自己的 `react@19.3.0`），而编辑器用 `react-dom@19.2.3` 渲染 → dispatcher 不匹配，运行时报 "Invalid hook call"。
**Why it happens:** editor-core 的 `react: ^19.3.0` 与 catalog/编辑器的 `19.2.3` 不兼容解析——`[VERIFIED: node_modules/.pnpm 列表; editor-core/package.json:18]`。
**How to avoid:** 把 editor-core 的 `react`/`@types/react` 改为 `catalog:default`（或精确 `19.2.3`/`19.2.9`），`pnpm install` 后确认 `react/jsx-runtime` 只解析到一个 realpath。`implExports.js` 的单例断言目前**不含 editor-core**，建议把它加入或在门禁中单独断言。
**Warning signs:** 测试/预览报 "Invalid hook call" / "Cannot read properties of null (reading 'useSyncExternalStore')"。

### Pitfall 3: `render()` 每次返回新组件 → 反复重挂（MEDIUM）
**What goes wrong:** `render()` 若 `return () => <Panel/>`，每次调用都是新函数；顶层把它当组件渲染时 React 会卸载重挂，丢失状态。
**How to avoid:** 在构造器里创建一次根组件并缓存；`Panel` 组件也要求面板返回稳定引用。

### Pitfall 4: 资源更新广播未 await / 顺序错乱（MEDIUM）
**What goes wrong:** `forEachHook` 是同步遍历、返回各钩子返回值数组，不 await——`[VERIFIED: hook/hook.ts:54-60]`。若直接忽略返回的 Promise，`updateResource` 会在面板真正拿到新数据前就 resolve。
**How to avoid:** `await Promise.all(this.forEachHook((h) => h.onUpdateResource?.(id)))`；注意 `forEachHook` 返回 `(Promise<void> | undefined)[]`，`Promise.all` 接受 undefined 元素。

### Pitfall 5: `PanelSystem` 撤回自证循环（MEDIUM）
**What goes wrong:** 若 `undo`/`redo` 内部调用公共 `switchTo`，会再次 `addUndoContext`，撤销时不断产生新历史。
**How to avoid:** `undo`/`redo` 只调 `internalSwitchTo`（不记录）；`switchTo` 先记录再 `internalSwitchTo`（D-32）。

### Pitfall 6: 门禁 `MIN_EXPECTED_SOURCES` / `MIN_EXPECTED_CORE_SOURCES` 下界（MEDIUM）
**What goes wrong:** `coreImportType.js` 的 `MIN_EXPECTED_SOURCES = 55`、`coreEngineNeutral.js`/`coreBoundaries.js` 的非空转下界，都基于旧 `lib` 的 55+ 文件数——`[VERIFIED: coreImportType.js:40]`。新 `src` 初期只有少量实现文件 + 测试，扫描数会塌到下界以下 → 即使源码合规也判红。
**How to avoid:** 把门禁扫描根改为 `src` 并重设下界（或按本阶段实际文件数保守设定）；这是"范围被静默削弱"守卫的必然调整，需在计划里显式说明。

### Pitfall 7: `prettier-setup.js` 与 `.prettierrc` 名字不符（LOW，但当前红）
**What goes wrong:** 门禁硬编码 `.prettierrc.json`——`[VERIFIED: prettier-setup.js:28]`；提交 `371b801` 把 `.prettierrc.json` 改名成了 `.prettierrc`——`[VERIFIED: git show 371b801 --stat]`。门禁找不到文件即红。
**How to avoid:** 用户拍板：改回 `.prettierrc.json`（并同步 AGENTS.md 描述），或改门禁接受 `.prettierrc`。属"重要命名"，须先确认。

### `PanelSystem.undo`/`redo` 与 `internalSwitchTo`
```ts
// 语义（非最终代码）：Switch 上下文同时记 from/to，undo 回 from、redo 去 to
interface IPanelSwitchData {
  readonly from: IEditorPanel | null;
  readonly fromParam?: Record<string, unknown>;
  readonly to: IEditorPanel;
  readonly toParam?: Record<string, unknown>;
}

async switchTo(panel: IEditorPanel, param?: Record<string, unknown>): Promise<void> {
  if (panel === this.currentPanel) return;
  this.undoSystem.addUndoContext(this, {
    type: PanelUndoType.Switch,
    data: { from: this.currentPanel, fromParam: this.currentParam, to: panel, toParam: param },
  });
  await this.internalSwitchTo(panel, param);
}

async undo<T>(context: IUndoContext<T>): Promise<void> {
  const data = context.data as IPanelSwitchData; // 撤回系统按操作者分派，data 形状由 PanelSystem 自己保证
  await this.internalSwitchTo(data.from, data.fromParam);
}

async redo<T>(context: IUndoContext<T>): Promise<void> {
  const data = context.data as IPanelSwitchData;
  await this.internalSwitchTo(data.to, data.toParam);
}
```
> ⚠️ `context.data` 在接口里是 `T`（`IUndoContext<unknown>`）；面板系统需要把它收窄为自己的数据形状。**避免连续 `as`**（`as unknown as X` 被 AGENTS 禁止）；单次 `as` 可接受，或写一个 `isPanelSwitchData(value): value is IPanelSwitchData` 判定函数。

## Open Questions (RESOLVED)

1. **`onFocus` / `onBlur`（浏览器窗口焦点）由谁触发？**
   - What we know：接口把它们列为 `IEditorPanel` 成员（`[VERIFIED: panel/types.ts:58-66]`）；`IPanelInjection` 为空占位（`[VERIFIED: panel/types.ts:96]`）。
   - What's unclear：core 源码禁止触达 `window`/`document`（PORT-02），因此 `PanelSystem` 不能自己 `addEventListener('focus')`；但接口里没有"由宿主调用焦点回调"的入口。
   - Recommendation：三条路任选并请用户拍板——(a) 用 `IPanelInjection` 注入一个焦点事件源（符合 D-15"后续可能加内容"）；(b) 由 `render()` 根组件用 React 合成事件 + 容器 `tabIndex` 近似元素焦点；(c) 本阶段先不接、由未来 impl/宿主调用。**倾向 (a) 或 (c)**，避免触碰 PORT-02 门禁。
   - **RESOLVED: D-38** —— 去掉「core 禁 `window`」旧限制，`PanelSystem` 直接监听 `window` 的 focus / blur 触发当前面板 `onFocus` / `onBlur`，不额外加接口；相应在 05.3-08 放开 PORT-02 的 `window` 一项（保留 `document`/`fetch` 等其余限制）。落地见 05.3-06 / 05.3-08。

2. **三系统是否都有 `dispose()`？`EditorCore.dispose()` 的逆序范围？**

   - What's unclear：是否给具体类加接口外的 `dispose()`。
