<objective>
把原计划 05.3-15（撤销）与 05.3-16（资源）合并为一个计划，修复评审确认的三方面底层缺陷：`undo` / `redo` 先出栈再 `await`，操作失败时该条历史从两栈同时丢失（WR-03）；`maxUndoStep <= 0` 被静默当成「无上限」，应改为「禁用撤销」（IN-04）；`ResourceSystem.dispose()` 只清缓存、不清 `injection`，释放后仍会调用后端（WR-04），且资源钩子派发不做错误隔离，一个坏钩子的异常会中断其余钩子与整个更新流程（WR-09）。

Purpose: 让撤销历史在操作失败时仍可重试、撤销步数边界语义与调用方预期一致；让释放后的资源系统真正不可用、资源更新广播对单个监听者的失败免疫（D-09 / D-20 / D-31 / D-33 / D-36 / D-37 / D-39）。

说人话：① 点「撤销」时，系统先把这条历史扔掉再执行撤销，一旦撤销报错这条历史就永久消失；正确做法是「先执行、成功了再挪走记录」。②「最大撤销步数设为 0」现在等于「不限制」，得改成「禁用撤销」。③ 资源系统被「关掉」后还会偷偷去问后端要数据；正确做法是关掉就把后端引用也清掉，之后所有请求都返回空值。④ 广播资源更新时只要有一个面板回调报错，后面的面板就收不到通知；正确做法是每个监听者单独兜底。

Output: 保留历史语义的 `undoSystem.ts`、明确禁用语义的 `undo/types.ts` jsDoc、释放后真正不可用的 `resourceSystem.ts`、隔离钩子派发的同一文件、新增 `resource.hookFailed` 消息的 `messages.ts`，以及覆盖各场景的测试与 `05.3-INTERFACE-NAME.md` 的命名记录。

⚠️ 只动本计划列出的文件；**不重做** 05.3-13 / 05.3-14 已完成的接口加宽与空守卫。新日志 id `'resource.hookFailed'` 为**提案，需用户确认**后才可写入代码。不改 `hook/` 的接口与实现（用户已判定 WR-01 / WR-02 / IN-01 不是问题）。若发现必须改行为或扩大公共接口才能修好，先停下汇报（D-34）。

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| 撤回对象 → UndoSystem | 被撤回对象的 undo/redo 可能失败；系统必须不因单次异常丢失历史 |
| 注入配置 → 撤销语义 | 调用方传入 `maxUndoStep`，其 0 / 负数取值直接决定是否记录历史 |
| 面板钩子 → ResourceSystem | 钩子是外部实现，可能同步失败或返回被拒绝的 Promise；广播必须相互隔离 |
| 已释放的系统 → 后端注入对象 | dispose 后不得再持有、调用后端引用 |
| 规划动作文本 → 负向扫描门禁 | 异常构造 / 控制台字面量只放进 `<verify>` / `<fails_when>` 的行为描述，不写进 `<action>`，避免负向门禁自我失效（#429） |
