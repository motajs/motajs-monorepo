# Phase 05.3: Code Review Report

**Reviewed:** 2026-10-08T16:55:00Z
**Depth:** standard

## Summary

本阶段把 `@motajs/editor-core` 从零重建为引擎无关的内核：hook 系统（`Hookable`/`HookController`）、资源系统（缓存 + 钩子 + 后端注入）、面板系统（注册/切换/渲染根/窗口焦点 + 撤回）、代码化 logger，以及组合根 `EditorCore`。

整体结构清晰、接口与实现分离、注释与命名大体符合仓规，测试（33 用例）实测全绿。但存在两个**会在真实运行环境崩溃/失效**的缺陷，以及若干生命周期与错误隔离问题：

1. **生产代码使用了运行时并不存在的 `Map.prototype.getOrInsertComputed`**——类型来自 TS6 的 lib 声明，运行时垫片只挂在 vitest 上，浏览器/Node 24 会直接 `TypeError`。
2. **`@motajs/editor-core` 把 React 声明成 `dependencies` 且钉死 `19.3.0`**，与编辑器实际使用的 `19.2.3` 形成两份 React，一旦编辑器挂载内核渲染根就会触发 "Invalid hook call"。

下面按严重度列出全部发现。已刻意忽略由 Prettier/ESLint 强制的格式问题；每条都给出文件、行号与可落地的修法。

## Critical Issues

### CR-01: 生产源码使用 `Map.prototype.getOrInsertComputed`，真实运行时不存在（生产必然 `TypeError`）

**File:** `packages/libs/editor-core/src/resource/resourceSystem.ts:72,85,97`
**Issue:**
`readContent` / `writeContent` / `createResource` 三处都用
`this.contentCache.getOrInsertComputed(id.type, () => new Map())` 来取默认值缓存。

这个方法**不是已发布的 JS 标准**（TC39 upsert 提案），TS6 的 `lib.esnext.collection.d.ts` 只提供了**类型**，并不提供运行时实现。实测本机 Node `v24.21.0`：

```
node -e "console.log(typeof Map.prototype.getOrInsertComputed)"  →  undefined
```

仓库自己在 `05.3-10-PLAN.md` 也写明「Node 24 尚无 `Map.prototype.getOrInsert*`」，并为此新建了 `src/__tests__/mapPolyfill.ts`（经 `vitest.config.ts` 的 `setupFiles` 加载）。但 `mapPolyfill.ts` 位于 `src/__tests__/`，被编辑器 `tsconfig.app.json` 的 `exclude` 排除，也**不会进入任何生产构建**（`package.json` 无 `build`，编辑器 Vite 配置也不加载它）。

后果：单测全绿，但任何真实消费方（今天的编辑器、未来的宿主/第三方）只要调用 `resource.request()` / `resource.write()` / `panelContext.createResource()`，就会抛
`TypeError: this.contentCache.getOrInsertComputed is not a function`。这正是「类型走 TS6 lib、运行时走浏览器」的典型缺口。

**Fix:**
不要依赖未发布的原型方法，改回显式的 get-or-create（保留惰性 `new Map()` 的意图）：

```ts
// resourceSystem.ts
private getOrCreateContentMap(type: number): Map<string, unknown> {
  let target = this.contentCache.get(type);
  if (!target) {
    target = new Map();
    this.contentCache.set(type, target);
  }
  return target;
}
```

三处调用改为 `const target = this.getOrCreateContentMap(id.type);`。
若确实想保留 `getOrInsertComputed`，必须把垫片移出 `__tests__` 并在**生产入口**（编辑器 `src/main.tsx` 与 `runtime/iframeEntry.ts`）导入，或改用 `es-toolkit` 等已打包的 upsert 实现——但显式写法最简单、零风险。

### CR-02: `editor-core` 把 React 声明为 `dependencies: 19.3.0`，与编辑器 `19.2.3` 形成两份 React（挂载内核组件时 "Invalid hook call"）

**File:** `packages/libs/editor-core/package.json:15-18`
**Issue:**
`dependencies` 里写了 `"react": "19.3.0"`（硬编码、非 catalog），而编辑器 `packages/apps/editor/package.json` 用的是 `"react": "19.2.3"`。实测两包 `node_modules` 里确实各装了一份：

```
core react 19.3.0
editor react 19.2.3
node_modules/.pnpm 同时存在 react@19.2.3 与 react@19.3.0
```

`editor-core` 的 `panelSystem.ts:2` 在生产代码里从 `react` 导入并运行 `createElement` / `useSyncExternalStore`。编辑器 Vite 配置没有任何 `resolve.dedupe`，`resolvePlugin` 也只处理 `@/`。因此编辑器打包时，内核源码里的 `react` 会解析到 `editor-core/node_modules/react`（19.3.0），而编辑器自身代码用 19.2.3。`panelSystem.render()` 返回的组件最终由编辑器的 React 渲染器调用，却调用 19.3.0 模块上的 `useSyncExternalStore`——19.3.0 的 dispatcher 从未被 19.2.3 的 reconciler 设置，直接触发 “Invalid hook call”。

这违背了仓库既有约定：`react-store` / `react-hooks` 都把 `react` 放在 `peerDependencies: catalog:default` + `devDependencies: catalog:default`，从而保证唯一副本。另 `@types/react-dom: 19.3.0` 也与编辑器 `19.2.3` 不一致。

**Fix:**
与同仓库对齐，把 React 改成 peer + dev，并通过 catalog 统一版本：

```jsonc
// packages/libs/editor-core/package.json
"dependencies": {
  "@tanstack/store": "catalog:default"
},
"peerDependencies": {
  "react": "catalog:default"
},
"devDependencies": {
  "react": "catalog:default",
  "react-dom": "catalog:default",
  "@types/react": "catalog:default",
  "@types/react-dom": "catalog:default",
  // ...
}
```

同时在编辑器 `vite.config.ts` 的 `resolve` 增加 `dedupe: ['react', 'react-dom']` 作为第二道保险。

## Warnings

### WR-01: `Hookable.addHook` 不防重复注册，同一个 hook 对象注册两次会重复派发且留下无法移除的僵尸条目

**File:** `packages/libs/editor-core/src/hook/hook.ts:23-32`
**Issue:**
`addHook(hook)` 直接用传入对象作 `hookMap` 键。若同一 `hook` 对象被注册两次：

- `hookMap.set(hook, obj2)` 覆盖第一个条目，但 `controllerMap` / `hookList` / `loadedList` 里同时留着 **两个** `obj`；
- 事件会派发两次（`forEachHook` 遍历 `loadedList`）；
- `removeHook(hook)` 只能删掉 `hookMap` 里那个（第二个）obj，第一个 obj 永远留在 `loadedList`/`controllerMap`，既会继续派发又无法再移除——内存与行为双重泄漏。

**Fix:**
注册前先判断：

```ts
addHook(hook: Partial<H>): C {
  const existing = this.hookMap.get(hook);
  if (existing) return existing.controller;
  // ...原逻辑
}
```

（同时给 `unload` 后的对象设计清楚的重注册语义。）

### WR-02: `Hookable.addHook` 在 `awake` 之后无条件加回 `loadedList`，会把「在 awake 中卸载自己」的钩子复活

**File:** `packages/libs/editor-core/src/hook/hook.ts:29-30`
**Issue:**
`hook.awake?.(obj.controller)` 在 `this.loadedList.add(obj)` 之前执行。若某个钩子在 `awake` 里调用 `controller.unload()`（`removeHookByController` 会把 obj 从 `hookList`/`loadedList`/`hookMap`/`controllerMap` 全部删除），`awake` 返回后第 30 行又把它加回 `loadedList`。结果是：它仍会收到所有派发，但 `hookMap`/`controllerMap` 里已没有它，`removeHook` / `removeHookByController` 再也删不掉——僵尸钩子。

**Fix:**
先入 `loadedList` 再调用 `awake`，并在 awake 后确认仍在 `hookList` 中：

```ts
this.hookList.add(obj);
this.loadedList.add(obj);
hook.awake?.(obj.controller);
if (!this.hookList.has(obj)) return controller; // awake 期间被卸载
```

### WR-03: `UndoSystem.undo` / `redo` 先出栈再 await，操作抛错时该条历史从两栈同时丢失

**File:** `packages/libs/editor-core/src/undo/undoSystem.ts:33-51`
**Issue:**
`const entry = this.undoStack.pop();` 之后才 `await entry.undo.undo(entry.context)`。若被撤回对象抛错，`entry` 已从 `undoStack` 移除，且第 40 行的 `redoStack.push(entry)` 不会执行——这一条历史被静默丢弃，undo/redo 链条断裂（用户无法重试该步）。

**Fix:**
先取出再看，成功后再迁移；失败时放回原位：

```ts
async undo(): Promise<void> {
  const entry = this.undoStack[this.undoStack.length - 1];
  if (!entry) return;
  await entry.undo.undo(entry.context);
  this.undoStack.pop();
  this.redoStack.push(entry);
}
```

### WR-04: `ResourceSystem.dispose()` 只清缓存、不清 `injection`，释放后仍会访问后端

**File:** `packages/libs/editor-core/src/resource/resourceSystem.ts:126-129`
**Issue:**
`dispose()` 仅 `listCache.clear()` / `contentCache.clear()`，`this.injection` 仍指向外部后端。于是 `dispose` 之后 `requestResource()` 依然绕开「未初始化」守卫去调用后端。现有测试 `src/__tests__/core.test.ts:211-213` 恰好把这个泄漏**固化为期望行为**（dispose 后再请求，`requestResourceListCount` 从 1 变 2），等于用测试背书了错误语义。资源系统已释放却仍持有并调用注入对象，属于生命周期泄漏，也会误导调用方以为释放后访问会被拒绝。

**Fix:**
`dispose()` 中 `this.injection = null;`，并同步修正 `core.test.ts` 的断言（释放后应记录 `system.notInitialized` 并返回空，而非再次请求后端）。

### WR-05: `PanelSystem.dispose()` 不重置 `initialized`，释放后系统处于半可用状态

**File:** `packages/libs/editor-core/src/panel/panelSystem.ts:156-171`
**Issue:**
`dispose()` 移除了窗口 focus/blur 监听并清空面板，但没有 `this.initialized = false`，也没重置 `currentParam`。之后若再调 `registerPanel()`，第 106 行的 `if (this.initialized)` 仍为真，会立刻 `await panel.initialize()`；但窗口监听已移除，`onFocus`/`onBlur` 永远不会触发。系统呈现「注册可用、焦点失效」的不一致状态，且没有二次 `initialize()` 的补救路径。

**Fix:**
在 `dispose()` 末尾加 `this.initialized = false; this.currentParam = {};`，并让 `initialize()` 可幂等重入（重入前先 `removeEventListener` 或加 `if (this.initialized) return;`）。

### WR-06: 多处 `void` 掉返回 Promise 的回调，rejection 无人处理

**File:** `packages/libs/editor-core/src/panel/panelSystem.ts:74-79`
**Issue:**
```ts
this.handleFocus = (): void => {
  void this.currentPanel?.onFocus();
};
this.handleBlur = (): void => {
  void this.currentPanel?.onBlur();
};
```
`onFocus`/`onBlur` 是 `Promise<void>`。用 `void` 显式丢弃后，一旦面板回调抛错，就会变成 **unhandled promise rejection**，既不冒泡也不记录。同类问题存在于 `internalSwitchTo` 等 fire-and-forget 路径之外的调用者预期（例如 `PanelRoot` 之外的挂载点）。

**Fix:**
至少捕获并记日志：
```ts
this.handleFocus = (): void => {
  void this.currentPanel?.onFocus().catch((error) => logger.error('system.notInitialized', String(error)));
};
```
或在 `PanelSystem` 内统一加一个私有 `runSafely(promise)` 包装。

### WR-07: `registerPanel` 先执行 `creator` 再做重复 id 判断，重复时面板/上下文被丢弃且不 `dispose`

**File:** `packages/libs/editor-core/src/panel/panelSystem.ts:94-101`
**Issue:**
```ts
const context = new PanelContext(...);
const panel = await creator(context);      // 先建
if (this.panels.has(panel.id)) {           // 后查重
  logger.error('panel.duplicateId', panel.id);
  return null;                              // 建好的 panel 从不 dispose
}
```
`creator` 可能已经申请资源、注册副作用或持有句柄。重复 id 时返回 `null`，但已创建的 `panel` 既不入注册表、也永不 `dispose()`，造成泄漏；且调用方拿到 `null` 时往往不知道该对象已被构造。

**Fix:**
把查重前移（能提前拿到 id 的话），或在重复分支里 `await panel.dispose()` 后再返回 `null`。若 `id` 只能在构造后得知，则至少调用 `dispose()`。

### WR-08: `switchTo` 不校验面板是否已注册，可切到「系统无法管理」的面板

**File:** `packages/libs/editor-core/src/panel/panelSystem.ts:131-140`
**Issue:**
`switchTo(panel)` 只比较 `panel === this.currentPanel`，不检查 `this.panels.has(panel.id)`。调用方（或第三方扩展）可传入一个从未 `registerPanel` 的面板对象：它会被设为 `currentPanel` 并渲染，但 `dispose()` 遍历的是 `this.panels`，永远不会释放它；其资源钩子也从未挂载，资源更新不会通知它。这与 `getPanel(id)` 的注册表语义不一致。

**Fix:**
```ts
async switchTo(panel: IEditorPanel, param: Record<string, unknown> = {}): Promise<void> {
  if (panel === this.currentPanel) return;
  if (this.panels.get(panel.id) !== panel) {
    logger.error('system.notInitialized', 'Panel');   // 或新增更贴切的消息 id
    return;
  }
  // ...
}
```

### WR-09: 资源钩子派发不做错误隔离，单个钩子抛错会中断其余钩子与整个更新流程

**File:** `packages/libs/editor-core/src/resource/resourceSystem.ts:116-124`
**Issue:**
`updateResource` / `updateResourceList` 都写成：
```ts
await Promise.all(this.forEachHook((hook) => hook.onUpdateResource?.(id)));
```
`forEachHook` 是同步 `Set.forEach`：只要某个钩子在**同步阶段**抛错，`forEachHook` 当场中断，后面的钩子根本不会进入返回数组，`Promise.all` 也就无从隔离。一个坏面板的同步异常会阻止其他面板收到资源更新。仓规中「诊断订阅隔离」的约定正是要求这类派发相互隔离。

**Fix:**
在 `forEachHook` 或调用点逐项包 `try/catch`（或 `Promise.resolve().then(() => hook.onUpdateResource?.(id)).catch(...)`），确保一个监听者失败不影响其余监听者，并记录失败。

### IN-01: `Hookable.hookList` 是只写死字段

**File:** `packages/libs/editor-core/src/hook/hook.ts:11`
**Issue:** `hookList` 只在 `addHook` 写入、在两处 `remove` 删除，**从未被读取**。实际派发走 `loadedList`（`forEachHook:56`），查表走 `hookMap`/`controllerMap`。该字段是冗余状态，两条集合同步维护还增加了 CR/ WR-02 一类的错位风险。

### IN-02: `EditorCore` 版本号与初始化无幂等/交付语义

**File:** `packages/libs/editor-core/src/core.ts:7,19-23`
**Issue:** `version` 硬编码 `'0.1.0'`（与 `package.json` 的 `0.0.0` 不一致）；`initialize` 无「已初始化」守卫，重复调用会重复 `Promise.all` 注入（资源/撤销无害，但面板若已注册会重复挂监听）；`dispose` 后再次 `initialize` 也没有明确契约。

### IN-03: `IPanelSystem.initialize` 声明了注入参数，`PanelSystem.initialize()` 却完全忽略

**File:** `packages/libs/editor-core/src/panel/types.ts:103-107`、`packages/libs/editor-core/src/panel/panelSystem.ts:82`
**Issue:** 接口 `initialize(injection: IPanelInjection): Promise<void>` 与实现 `initialize(): Promise<void>` 参数不一致（TS 允许方法少收参数，故不报错），但契约上「注入」是空的形态。`core.ts:22` 也确实把整包 injection 传了进去，实现静默丢弃。日后面板系统需要注入时会形成隐蔽误用。
**Fix:** 要么让 `IPanelSystem.initialize` 无参（并把 `IPanelInjection` 明确为占位、加注释说明「当前无注入项」），要么让实现真正读取所需字段。

### IN-04: `UndoSystem` 的 `maxUndoStep = 0` 静默表示「无上限」

**File:** `packages/libs/editor-core/src/undo/undoSystem.ts:26`
**Issue:** `if (this.maxUndoStep > 0 && ...)` 意味着 0 等于不裁剪。字段初值也是 0，所以 `initialize` 未调用时表现为无上限。若外部把 `maxUndoStep: 0` 理解为「禁用撤销」或「不保留」，会得到相反结果。
**Fix:** 在 `IUndoInjection` 的 jsDoc 里明确「0 或负数 = 无上限」，或改为 `Number.isFinite` + 显式的「禁用」语义并加校验。
