# Phase 04.2 Plan 14: 地图组件去路径与打开能力 Summary

**地图画布与图面组件不再按路径读字节，改收视图算好的图片路径键地址表；地图面板类型凭宿主解析按完整路径被认出并打开**

## Performance

- **Duration:** 11 min
- **Started:** 2026-10-28T10:46:40Z
- **Completed:** 2026-10-28T10:57:47Z
- **Tasks:** 3
- **Files modified:** 6

## Accomplishments

- `createMapPanelType` 补上 `canOpen` / `createOpenParam`：未注入 `resolveMapPath` 时恒不认领（地图不进资源管理器候选），注入后按宿主解析结果判定，命中时返回 `{ target: { mapId } }` 且每次都是新对象。
- `MapSurface` 删除 `loadBytes` / `path` / `MapImageSource` 子组件与按路径读字节的链路，改为「按图片路径查地址表 → 用 `blob:` 地址建纹理」；地址缺失时保持既有缺图占位，不抛错、不重试，`imageVersion` 变化仍清空纹理并重新加载。
- `MapCanvas` 同步把 `loadBytes` 换成 `imageSources` 并向下透传，`MapBytesLoader` 别名随最后一个使用点一起删除。
- `MapPanelView` 新增私有纯函数 `toImageSources`，按 `group.imagePath` 把 `group.id` 键的地址投影成图片路径键地址交给画布；素材区 / 底栏 / 收藏栏三处仍用 `groupUrls`（`group.id` 键）。
- 新增键空间防回归用例：同一张图，用 `group.id` 当键时一个地址都取不到（缺图），用 `imagePath` 当键时才发起加载（出图）——这条闸门保证 Plan 15 的地址 store 不会把两张表搞混。
- 验证：`src/map` 32 文件 / 602 条全绿；`pnpm --filter @motajs/editor-impl test` 89 文件 / 1069 条全绿；`typecheck` exit 0；`node scripts/verify/coreBoundaries.js` 通过。

## Decisions Made

- `canOpen` / `createOpenParam` 的调用约定按 Plan 03 声明落地：先判 `undefined` 早退，再在窄化分支里直接调用 `capabilities.resolveMapPath(path)`；不把函数赋给局部常量，也不写 `?.` 再断言抹平。
- `MapSurface` 用一个 effect 完成「按路径查表 → 建纹理」，替代原先每路径挂一个 `MapImageSource` 子组件；地址表对象每次渲染都是新引用，靠 `texturesRef` / `pendingRef` / `failedRef` 三道守卫保证不重复加载。
- 视图投影放在 `renderReadyBody` 内调用 `toImageSources(document.tileGroups, input.groupImages)`：只在就绪态投影，且投影函数本身是纯函数，没有引入新的缓存或状态。

## Deviations from Plan

### Adaptations

**1. [规则解释] 键空间用例的「出图」断言改为「是否发起图片加载」**
- **Found during:** Task 3（迁移地图测试到真实键空间）
- **Issue:** jsdom 没有 WebGL，真实 `MapSurface` 的 Pixi 初始化必然失败，因此无法从画布上观察「这一格画出了图块」；`blob:` 图片在 jsdom 里也不会真的加载完成。
- **Fix:** 用例仍渲染真实 `MapSurface`，把 `HTMLImageElement.prototype.src` 的赋值拦截下来，作为「组件拿到地址并请求加载」的可观察信号：`group.id` 当键时没有任何请求（缺图），`imagePath` 当键时请求了该地址（出图）。两条断言合起来仍然钉死「两张表不能互相查表」。
