## User Constraints (from CONTEXT.md)

### Locked Decisions

#### 分层与组件契约
- **D-01:** 面板是唯一知道路径的角色；组件不接收路径、不主动读文件。
- **D-02:** 组件接收面板传入的内容，并在挂载期间持有编辑状态。
- **D-03:** 组件通过 ref 暴露四项能力：读取当前内容、替换内容、判断是否有未保存改动、标记已保存。
- **D-04:** 组件在内部请求保存时发出保存请求，携带当前内容的快照；该请求返回一个 Promise 结果，组件据此显示保存中 / 成功 / 失败。
- **D-05:** 面板在切走时调用「读取当前内容 + 判断脏状态」并保存；保存成功后调用「标记已保存」；普通切走的保存不可取消。
- **D-06:** 组件只在挂载期间持有状态；面板负责在切走 / 关闭时把内容取回并保存，重新切入时把最新内容传给组件。
- **D-07:** 只有可编辑组件实现保存契约；预览、工具栏、导航等只读组件只接收内容 / 回调，不实现保存。

#### 关闭流程
- **D-08:** 关闭前询问返回三态：保存并关闭 / 不保存关闭 / 取消。
- **D-09:** 「保存并关闭」由面板保存；保存成功后外壳跳过普通切走的落盘，直接关闭；保存失败保持打开。
- **D-10:** 「不保存关闭」外壳跳过普通切走的落盘，直接释放；「取消」保持标签。
- **D-11:** 普通切走仍然是「必须落盘、不可取消」，不参与关闭决策。

#### 文件变化同步
- **D-12:** 宿主提供文件变化流；core 只监听这一条通道。
- **D-13:** 本期先假定宿主一定会传入文件变化流；具体宿主实现（Node 侧监听、浏览器宿主是否提供）后续再定。
- **D-14:** 资源层不在自己 write 后额外通知，避免两个来源重复触发。
- **D-15:** 宿主事件到达时照常通知，不因为资源层缓存里已经是新内容就吞掉；去重放在面板 / 组件层。
- **D-16:** 面板只处理自己打开的路径；收到通知后比较内容，真的变了才替换组件内容。
- **D-17:** 冲突规则：面板没有未保存改动时自动刷新；有未保存改动时不覆盖，提示用户选择「放弃我的改动并刷新」或「保留我的改动，下次保存覆盖」。
- **D-18:** 宿主提供的变化流需要覆盖编辑器自己的写入；旧开发宿主不在本期适配范围，新版宿主后续接入。

#### 改造范围与组件边界
- **D-19:** 04.2 内分波次全拆：通用契约 → 表格三栏 → 文件资源管理器 → 地图区 / 素材区；每波单独验收。
- **D-20:** 按现有功能区划组件；地图区、素材区、表格每栏、素材分类 / 列表 / 详情 / 预览等都可以独立复用。
- **D-21:** 表格面板保持三栏；每栏一个表格组件；本期不做「外部一次给三份内容」的模式，由面板按栏分配。
- **D-22:** 素材 / 地图的逐组件清单在接口计划中列出，沿用现有功能块，不重画界面。

#### 文件资源管理器
- **D-23:** 只做浏览 + 打开；新建 / 重命名 / 删除 / 移动后续再加。
- **D-24:** 复用同一个文件浏览器组件；单目录列表 + 面包屑；组件只渲染，面板提供「读目录」「过滤」「打开」三项输入。
- **D-25:** 表格空栏复用该浏览器；过滤规则与表格的「能否打开」判断一致（所有 `.jsonc`，包含 schema）。
- **D-26:** 面板类型提供两项可选能力：判断完整路径能否打开、把路径转成自己的打开参数；资源管理器询问所有已注册面板类型。
- **D-27:** 多个候选时每次弹窗让用户选；没有候选时提示；只有一个时直接打开。
- **D-28:** 资源管理器总是新开标签；同步做好后，重复打开同一个文件是安全的。
- **D-29:** 宿主在创建资源管理器面板类型时注入「列面板类型 / 打开面板」回调；`editor-core` 不因此扩大面板上下文。
- **D-30:** 预览组件本期不加。

#### 面板类型与打开参数
- **D-31:** 后缀列表不够，判断依据是完整路径。示例：表格接受所有 `.jsonc`，代码编辑器接受所有 `.jsonc`，地图只接受 `maps/*.jsonc`。
- **D-32:** 面板类型自己把路径转成打开参数；资源管理器不解释参数形状。
- **D-33:** 面板类型的两项能力都是可选的；没有声明的面板不会被资源管理器列为候选。

#### 接口与命名
- **D-34:** 第一波只定义接口与命名；命名在 `INTERFACE-NAME.md` 中逐项确认后才写实现。
- **D-35:** `editor-core` 需要新增 / 修改的接口：关闭三态、文件变化流、面板类型的「能否打开 / 打开参数」；具体形状在接口计划中定。
- **D-36:** 文件变化的去重与自写回声抑制放在面板 / 组件层，不在资源层。

#### 面板生命周期
- **D-37:** 非活动面板不渲染；外部更新只更新面板保存的内容，等重新切入时再传给组件。
- **D-38:** 关闭前外壳先激活目标标签（现有行为），面板自己弹三态确认框。

## Summary

Phase 04.2 要做的事，本质上是三件互相咬合的改动：

1. **内容归属反转（表格为真、地图/素材为半真）**：表格现在由 `TablePanel` 持有每栏的 `data / schema / unsaved`，`TableGrid` 只是把面板算好的行树画出来。要让「组件持有编辑状态、面板拉取保存」成立，表格必须把草稿下沉到组件；而地图 / 素材的编辑状态与撤销、剪贴板、基线、视口深度耦合，把整份文档搬进 React 组件会推翻 04/04.1 刚落地的保存与撤销模型。因此研究结论是：**契约统一、落地分层** —— 表格三栏走真正的「组件持草稿 + 面板拉取」，地图 / 素材走「面板持文档 + 功能区组件只收内容」。
2. **外壳语义扩展**：关闭三态需要外壳能「跳过普通切走落盘」，而当前 `ShellSystem.closeTab → onBeforeClose → discardTab → leaveActiveInstance → onSwitchOut` 这条链上，`onSwitchOut` 是唯一的常规落盘点，且 `TablePanel.dispose` 还会再存一次。必须同时解决「跳过 `onSwitchOut`」与「跳过 `dispose` 的兜底保存」，否则「不保存关闭」根本做不到。
3. **宿主变化流与可打开判定**：`IEditorFileSystem` 现在纯请求 / 响应，没有任何变化通知；面板类型也没有「这个完整路径我能不能开」的表达能力。两者都要以**可选成员**加入，才能让第一波「只加接口」时三包零失败。

仓库现状经本会话逐文件核对，关键事实：

- 关闭前询问只有一个实现者：`MapPanel.onBeforeClose`，返回 `Promise<boolean>`。`[VERIFIED: packages/libs/editor-impl/src/map/mapPanel.ts:715-719]`
- `ShellSystem.closeTab` 只在 `instance.onBeforeClose !== undefined` 时询问，且询问前先激活目标标签。`[VERIFIED: packages/libs/editor-core/src/shell/shellSystem.ts:609-624]`
- `ShellSystem.discardTab` 只在 `wasActive` 为真时投递 `onSwitchOut`；**关闭后台标签不会走落盘**，表格靠 `TablePanel.dispose → saveDirtyColumns` 兜底。`[VERIFIED: packages/libs/editor-core/src/shell/shellSystem.ts:776-783; packages/libs/editor-impl/src/table/tablePanel.ts:608-610]`
- 资源层写入后只更新缓存、**不通知**；唯一的通知入口是 `IResourceSystem.updateResource`。`[VERIFIED: packages/libs/editor-core/src/resource/resourceSystem.ts:81-91,141-153]`

## Q2：可编辑组件的 ref 契约（React 19）

### Q2.1 React 19 的机制（不需要 `forwardRef`）

官方文档明确：

> Starting with React 19, [`ref` is available as a prop.](https://react.dev/blog/2024/12/05/react-19#ref-as-a-prop) In React 18 and earlier, it was necessary to get the `ref` from [`forwardRef`.](https://react.dev/reference/react/forwardRef)
>
> `[CITED: react.dev/reference/react/useImperativeHandle]`

典型形态：

```tsx
function MyInput({ ref }) {
  useImperativeHandle(ref, () => {
    return {
      // ... your methods ...
    };
  }, []);
  // ...
```

`[CITED: react.dev/reference/react/useImperativeHandle]`

类型层面也已就绪：

```ts
type Ref<T> = RefCallback<T> | RefObject<T | null> | null;
function useImperativeHandle<T, R extends T>(ref: Ref<T> | undefined, init: () => R, deps?: DependencyList): void;
```

`[VERIFIED: node_modules/.pnpm/@types+react@19.2.9/node_modules/@types/react/index.d.ts:193,1791]`

> **Pitfall（官方原文）：** "**If you can express something as a prop, you should not use a ref.**" `[CITED: react.dev/reference/react/useImperativeHandle]`
> 本项目 D-03 明确要求 ref（面板要在任意时刻主动拉取），这是有意的例外；但不要顺手把「打开 / 关闭」「禁用」这类可 props 化的东西也塞进 ref。

**表格的内容类型（本轮补定）：** `ITableDocument` = `{ readonly data: unknown; readonly schema: unknown; readonly schemaMode: boolean }`，声明在 `editor-impl/src/table/types.ts`（接口波次 Plan 03）。它是**面板结构**而不是文件结构（D-39）：一栏当前呈现所需的数据、schema 与「是不是 schema 视图」一并打包，组件据此自己算行树；同一文件在不同栏可以被包装成不同文档。配套的编辑入口 `ITableEdit` / `TableEditKind` 与完整 props `ITableEditableProps` 也由 Plan 03 一次定稿，Plan 08 只引用。

**推荐的机械解法（不依赖 React 调度顺序）：** 可编辑组件用 `useLayoutEffect` 的 cleanup 把最后一份草稿同步交给面板：

```tsx
export function SomeEditable(props: IEditableContentProps<SomeContent>): ReactElement {
  const draftRef = useRef(props.content);
  const dirtyRef = useRef(false);
  // ... 编辑时更新 draftRef / dirtyRef ...

  // 面板在组件挂载期间通过 ref 拉取；卸载时 cleanup 先交回最后一份草稿
  useImperativeHandle(
    props.ref,
    () => ({
      getData: (): SomeContent => draftRef.current,
      setData: (next: SomeContent): void => {
        draftRef.current = next;
        dirtyRef.current = false;
      },
      isDirty: (): boolean => dirtyRef.current,
      markSaved: (): void => {
        dirtyRef.current = false;
      },
    }),
    [],
  );

  useLayoutEffect((): (() => void) => {
    return (): void => {
      props.onDraftChange?.(draftRef.current, dirtyRef.current);
    };
  }, [props.onDraftChange]);

  // ...
}
```

依据（官方原文）：

> Before your component is removed from the DOM, React will run your cleanup function.
>
> `[CITED: react.dev/reference/react/useLayoutEffect]`

> When Strict Mode is on, React will **run one extra development-only setup+cleanup cycle** before the first real setup. This is a stress-test that ensures that your cleanup logic "mirrors" your setup logic and that it stops or undoes whatever the setup is doing.
>
> `[CITED: react.dev/reference/react/useLayoutEffect]`

StrictMode 的额外 cleanup 只会多交一次同样的草稿，幂等。注意：**开发宿主没有用 `StrictMode`**（`packages/apps/editor-dev/src/main.tsx` 直接 `createRoot`），但旧 `editor` 应用与 `service-worker` 管理界面**都用了** `<StrictMode>`；未来把 impl 组件接到那两个宿主时，双调用一定会发生。`[VERIFIED: packages/apps/editor-dev/src/main.tsx:49-58; packages/apps/editor/src/main.tsx:16-22; packages/apps/service-worker/src/view/main.tsx:7-10]`

**建议同时做的第二个防御**：把 `ShellSystem.activateTab` / `ShellSystem.openBlankTab` / `ShellSystem.openPanelInTab` 里的「投递切出」提前到 `notify()` 之前（`switchActive` 拆成 `enqueueOut` 与 `enqueueIn` 两半），并规定面板的 `onSwitchOut` **必须在第一个 `await` 之前完成快照**。现有 `TablePanel.flushColumn` 已经是这个写法（「同步前缀完成快照与清标记」）。`[VERIFIED: .planning/STATE.md:324]`

> 为什么两件事都要做：cleanup 覆盖「React 先提交」；顺序覆盖「React 尚未提交但面板已不需要组件」；只做一件都会在某个路径上留缺口（尤其后台标签关闭不经过 `notify`）。

### Q2.4 内容重置：不要每次 render 都覆盖用户输入

如果面板把 `content` 作为普通 prop 传入、每次 store 变化都生成新对象，组件用 `useEffect(() => reset(props.content), [props.content])` 就会**在用户打字时把草稿重置**。必须用**版本号**而不是对象引用：

```ts

  useEffect((): void => {
    draftRef.current = props.content;
    dirtyRef.current = false;
  }, [props.contentVersion]);
```

`contentVersion` 的递增点（提案）：首次载入、外部变化刷新、撤销 / 重做、`setTable` 换表、保存成功后（若面板要回写规范化内容）。

### Q2.5 脏状态用显式标志，不做深比较

表格现有的 `unsaved` / `unsavedSchema` 就是标志位；`setByFieldPath` 等工具是原地修改，引用比较不可靠；深比较每次编辑都要遍历整表。因此：

- `markSaved()` 清 false；
- 面板保存前 `isDirty()` 为 false 就跳过写盘（`TablePanel.save` 已有同样守卫：`if (!column.unsaved && !column.unsavedSchema) return;`）。`[VERIFIED: packages/libs/editor-impl/src/table/tablePanel.ts:687-688]`

**副作用（必须写进计划）：** 撤销回到原值仍然显示「未保存」，这与现状一致，不是回归。

### Q2.6 `memo` + `ref` 的兼容性

`TableGrid` 是 `memo(function TableGrid(props: ITableGridProps))`。`ref` 只要写进 props 类型即可随 props 透传；`@types/react` 的 `memo<P extends object>` 返回 `NamedExoticComponent<P>`，不剥离 `ref`。`[VERIFIED: node_modules/.pnpm/@types+react@19.2.9/node_modules/@types/react/index.d.ts:1567-1572]` **但这是类型推断，不是运行时验证**；接口计划落地后用 `pnpm --filter @motajs/editor-impl typecheck` + 一条最小渲染测试确认（列为 `[ASSUMED]`，见 Assumptions Log A2）。

D-15 / D-16 / D-36 与讨论日志的「四层去重」对应关系：

| 层 | 做什么 | 放在哪 | 依据 |
|----|--------|--------|------|
| 1 | **与「上次已保存内容」相同就当作无变化** | 面板 | 讨论日志「内容相同不通知」；D-15 只禁资源层吞事件 |
| 2 | 短窗口合并同一路径的连续事件（如 50–100ms） | 面板 | 讨论日志「短窗口合并」 |
| 3 | 只处理本面板打开 / 关心的路径 | 面板 | D-16 |
| 4 | `setData` 前再比较一次 | 组件 | 讨论日志「setData 前再比」 |

**关键算法（面板）**：比较对象是「上次写盘 / 载入的基线」，**不是**当前草稿：

```
incoming = await readText(path)
if (incoming === baselineText[path]) -> 忽略（自写回声 / 空变化）
else if (isDirty(path))              -> 弹冲突（放弃并刷新 / 保留并下次覆盖）
else                                  -> 刷新（setData + 更新 baseline + contentVersion++）
```

否则会出现：面板保存 → 宿主回声 → `incoming !== 草稿`（草稿可能刚又被改）→ 误判冲突。用基线比较才能把自写回声识别为「无变化」。

**「保留我的改动，下次保存覆盖」**：只更新基线为 incoming、不 `setData`；下一次保存把草稿写回，覆盖宿主的新内容。语义上等价于「忽略这次外部变化」。

  - `candidates = listPanelTypes().filter(两个成员都存在 && canOpen(path))`
  - `0` → 提示「没有可以打开该文件的面板」
  - `1` → `openPanel(type.id, type.createOpenParam(path))`
  - `>1` → 弹候选 Modal，用户点选后打开（D-27）
- `onUpdateResource` / `onResourceChange` → `reloadToken++`（只有当前目录受影响时才需要重列；索引同步，重列很便宜，先全量重列）。

## Q9：风险与开放问题（排序）

### R1（最高）卸载早于 `onSwitchOut`

- **现象：** 切标签时 React 可能先卸载旧面板，面板拿不到组件 ref。
- **影响：** 草稿丢失 / 保存空内容。
- **缓解：** `useLayoutEffect` cleanup 交回草稿（§Q2.3）+ 外壳把切出投递提前到 `notify()` 之前 + 面板 `onSwitchOut` 同步前缀取快照。
- **验证：** `shellSwitchOrder.test.ts`（切走后读回内容）；表格 `editableContract.test.tsx` 的卸载用例。**这个顺序假设本身也要用测试钉住**（不要只靠推理）。

### R2（最高）全局撤销栈会命中未挂载的面板

`UndoSystem.undo` 只取栈顶，不看活动面板：

```ts

    const entry = this.undoStack[this.undoStack.length - 1];

    if (!entry) return false;
```

`[VERIFIED: packages/libs/editor-core/src/undo/undoSystem.ts:40-43]`

- **影响：** 用户在 B 面板按 Ctrl+Z，可能把 A 面板（未挂载）的编辑撤销掉。若 A 的草稿只存在于组件里，撤销无处可落。
- **缓解：** 面板必须持有「交回来的草稿」（§Q2.3 的 `onDraftChange`），撤销时对面板手里的草稿应用 patch 再交给组件（若挂载）或留着（若未挂载）。

### R4（高）过滤口径：`.json` 还是 `.jsonc`

D-25 / D-31 说「所有 `.jsonc`」，但：

数据流（主用例）：**外部进程改文件 → 宿主 watch → 资源层更新索引 / 缓存 → 面板按路径过滤并比较基线 → 组件 setData（或弹冲突）**。

### Pattern 1：可编辑组件（ref 契约 + 卸载交回 + 版本重置）

**What:** 组件接收 `content` 与 `contentVersion`，在内部持有草稿，通过 ref 暴露四项能力，并在卸载 cleanup 把草稿交回面板。
**When to use:** 表格每栏；素材配置表单（`TableGrid` 的 `formMode`）。
**Why not for map:** 地图的文档与撤销 / 基线 / 视口耦合，搬进组件会推翻 `MapPanel.save`。

```tsx
// 提案形态（名称待 INTERFACE-NAME.md 确认）
export function EditableTable(props: IEditableContentProps<ITableDocument>): ReactElement {
  const draftRef = useRef(props.content);
  const dirtyRef = useRef(false);

  useEffect((): void => {
    draftRef.current = props.content;
    dirtyRef.current = false;
  }, [props.contentVersion]);

  useImperativeHandle(
    props.ref,
    () => ({
      getData: (): ITableDocument => draftRef.current,
      setData: (next: ITableDocument): void => {
        draftRef.current = next;
        dirtyRef.current = false;
      },
      isDirty: (): boolean => dirtyRef.current,
      markSaved: (): void => {
        dirtyRef.current = false;
      },
    }),
    [],
  );

  useLayoutEffect((): (() => void) => {
    return (): void => {
      props.onDraftChange?.(draftRef.current, dirtyRef.current);
    };
  }, [props.onDraftChange]);

  // 每栏表格渲染；编辑回调里 draftRef.current = next; dirtyRef.current = true;
  return createElement(TableGrid, { /* ... */ });
}
```

依据：`ref` 是普通 prop、`useImperativeHandle` 语义、`useLayoutEffect` cleanup 在移除前运行。`[CITED: react.dev/reference/react/useImperativeHandle; react.dev/reference/react/useLayoutEffect]`

### Pattern 2：关闭三态（面板决策 + 外壳跳过）

```
用户点 ✕
  → ShellSystem.closeTab(tabId)
  → 若面板有 onRequestClose：先 activateTab(tabId)（既有行为）
  → await onRequestClose()
      Cancel  → return（标签保留）
      Discard → onDiscard?.(); discardTab(tabId, skipFlush=true)
      Save    → discardTab(tabId, skipFlush=true)
  → discardTab：wasActive 时【不投递 onSwitchOut】；closePanelInstance → dispose
```

**关键点：**

- `onDiscard` 只清内存脏标记；`dispose` 的兜底保存因此成为空操作。
- 注销类型 / 释放 core 不调用 `onRequestClose` / `onDiscard`（保持 04-15 的既有约定）。
- 没有 `onRequestClose` 的面板继续走旧路径（`onBeforeClose` 布尔或直接关闭 + 落盘）。

### Pattern 3：文件变化流（单通道 + 面板四层去重）

```
宿主 fs.writeFile / 外部进程
  → fs.watch 回调 { path, kind }
  → ResourceSystem：guardPath → index.insert/remove → cache.invalidate → hooks
  → ShellPanelHooks：面板实现 onResourceChange 就只传 (path, kind)，否则旧路径预读
  → 面板：路径过滤 → 与 baseline 比较 → 不脏刷新 / 脏弹冲突
  → 组件：setData 前再比较一次
```

### Anti-Patterns to Avoid

- **把地图 / 素材的文档搬进 React 组件：** 会同时推翻保存按域、基线脏判定、撤销载荷与大地图视口；D-19 的「拆分」是功能块边界，不是状态搬家。
- **在资源层比较内容 / 合并事件：** D-15 明确禁止；会让「编辑器自己的写入」与「外部写入」变得不可区分。
- **把 `.editor` 加进 `ignore`：** 地图偏好会读不到（§Q4.8）。
- **用对象引用做「内容是否变化」的判断：** 表格草稿是原地修改；必须用文本 / 基线比较。
- **把 `canOpen` 做成异步：** 资源管理器一次点击要对全部类型求值；异步会引入竞态与额外 loading。
- **在 `createOpenParam` 里做 I/O：** 违反 D-01 / D-32；它必须是纯函数。
- **改 `onBeforeClose` 的签名：** 会让 `shellClose.test.ts` 与 `MapPanel` 同时变红；用新增方法而不是改旧的。

## Common Pitfalls

### Pitfall 1：把「切走保存」写成先清标志再写盘

**What goes wrong:** 写失败后脏标记已经清掉，用户切回来看到「已保存」但磁盘还是旧内容。
**Why it happens:** `TablePanel.flushColumn` 先清 `unsaved` 再 `try` 写。`[VERIFIED: packages/libs/editor-impl/src/table/tablePanel.ts:1407-1410]`
**How to avoid:** 写成功后再清标志；失败保留脏并提示。与 D-05「保存成功后才 markSaved」一致。
**Warning signs:** 写失败用例里 `unsaved` 变 false。

### Pitfall 2：卸载后才读 ref

见 §R1。**Warning signs:** 切换标签后第一次编辑丢失；`getData()` 返回初始内容。

### Pitfall 3：撤销命中未挂载面板

见 §R2。**Warning signs:** 在 B 面板按 Ctrl+Z，A 面板重新切入后内容变了。

### Pitfall 4：`content` 作为普通 prop 触发草稿重置

见 §Q2.4。**Warning signs:** 打字打到一半被文本框自己的 `useEffect` 重置。

### Pitfall 5：删除事件走旧通知通道

**What goes wrong:** `ShellPanelHooks` 预读已删除文件 → `fs.readFile` 抛 → `resource.hookFailed` 日志；面板收不到删除通知。
**How to avoid:** 新 `onResourceChange(id, kind)` 不预读；删除只更新索引与缓存。`[VERIFIED: packages/libs/editor-core/src/shell/shellSystem.ts:902-912]`

### Pitfall 6：把 `.editor` 加进 ignore

见 §Q4.8。**Warning signs:** 地图「最近使用 / 收藏」永远为空。

### Pitfall 7：`testIdPrefix` 忘了传

**What goes wrong:** 表格约 56 处 `table-list-*` 断言全红。
**How to avoid:** `TablePicker` 包装 `FileBrowser` 时显式 `testIdPrefix="table-list"`；在 Wave 2 的第一条任务里就接上。

### Pitfall 8：过滤口径「包含 schema」漏掉删除态

`TableEmptyColumn` 的删除态也复用 `TablePicker`；D-25 的过滤变化对打开态与删除态都生效。删除态列出 schema 会让用户能直接删 schema 文件（当前删除只删数据 + 推导 schema，不删任意 schema）。**接口计划必须明确删除态是否沿用同一过滤**（建议：删除态仍只列数据文件，打开态按 canOpen）。

### Pitfall 9：`createOpenParam` 返回共享可变对象

`tablePanelType.create` 会把它交给 `setTable`；若多个资源管理器实例共享同一个对象并有人修改，会串味。**How to avoid:** 每次返回新对象。

### Pitfall 10：地图 `resolveMapPath` 与 `.jsonc` 假设

演示宿主是 `content/map/<id>.json`；D-31 的 `maps/*.jsonc` 只是示例。照抄会一个地图都打不开。**Warning signs:** 资源管理器点地图文件 → 0 候选。

### 关闭三态的外壳分支（提案）

```ts
// Source: 本仓库 packages/libs/editor-core/src/shell/shellSystem.ts:595-628 的现状改写
async closeTab(tabId: string): Promise<void> {
  const index = this.tabs.findIndex((tab) => tab.id === tabId);

  if (index === -1) {
    logger.error('shell.tabNotFound', tabId);
    return;
  }

  const tab = this.tabs[index];
  const instanceId = tab.instanceId;

  if (instanceId !== null) {
    const instance = this.instances.get(instanceId);
    const asks = instance !== undefined && (instance.onRequestClose !== undefined || instance.onBeforeClose !== undefined);

    // 只有「需要询问」时才先激活；未实现任何关闭钩子的面板仍直接关闭、前台不变（既有测试钉住）
    if (asks && this.activeTabId !== tabId) this.activateTab(tabId);

    if (instance !== undefined && instance.onRequestClose !== undefined) {
      let choice = PanelCloseChoice.Cancel;

      try {
        choice = await instance.onRequestClose();
      } catch {
        logger.error('shell.beforeCloseFailed', this.instanceTypes.get(instanceId) ?? '');
        return;
      }

      if (choice === PanelCloseChoice.Cancel) return;
      if (choice === PanelCloseChoice.Discard) instance.onDiscard?.();

      await this.discardTab(tabId, true);
      return;
    }

    if (instance !== undefined && instance.onBeforeClose !== undefined) {
      let allowed = false;

      try {
        allowed = await instance.onBeforeClose();
      } catch {
        logger.error('shell.beforeCloseFailed', this.instanceTypes.get(instanceId) ?? '');
        return;
      }

      if (!allowed) return;
    }
  }

  await this.discardTab(tabId, false);
}
```
