# Phase 04.3 Plan 10: 两栏同一张表 Summary

**同一张表开在同一个面板的两栏时，一栏确认后另一栏在 50 毫秒内跟上；两栏之间不再互相判成「外部已改」——脏草稿原样保留、按最后写盘者胜结算、永不弹冲突框，只有真正的外部写入才提示**

- **同面板写入不再误判成外部冲突**：新增私有判定 `TablePanel.isSamePanelWrite`，只比既有事实——收到的原文与本面板其它栏在同一路径上的基线原文（数据文件比 `baselineText`、由数据栏推导出的镜像 schema 比 `baselineSchemaText`）是否相同。相同就说明这是本面板另一栏刚写出去的那一份，本栏脏时保留草稿、不记冲突、直接返回。
- **没有引入任何旁路状态**：不新增「自写标记」「最近写入时间戳」「来源位」，也没有给 `writeContent` 或 50 毫秒合并通知加 `ResourceSystem.noteExternalWrite`——两栏之间因此既不会被标成「外部已改」，也不会进入「正在打字、弹窗推迟」的那条外部冲突态。
- **既有同步与写盘时机一字未动**：`refreshDependents` 仍在 `TablePanel.saveDocument` 内、写缓冲返回后立刻调用（同面板刷新仍是立即发生，不变成 5 秒）；`refresh` 的脏守卫（`unsaved || unsavedSchema || draftDirty`）没有改，脏栏仍不被覆盖——这正是「最后写盘者胜」与「脏草稿保留」成立的前提。
- **既有两栏同步 UAT 对齐新语义**：`panelSync.uat.test.tsx` 里「改 schema 后同面板其它栏同步」「写盘不刷新引用其它表的栏」「撤销新增后同步回退」都不再先点保存再断言，改由字段确认 / 新增 / 撤销本身驱动；schema 同步那条改在假定时器上推进 50 毫秒后断言，读回仍走资源层。

## Decisions Made

- **抑制只放在「本栏脏」这一支**：干净栏继续走既有「外部变化 → 正常载入」路径。若把判定提前到解析之前，一旦某栏的在途刷新与合并通知交错，干净栏可能被这条判定跳过而留在旧内容上；放在脏分支里语义等价（有脏草稿才需要保留草稿、才需要抑制冲突），但没有这个风险。
- **比较的是内容，不是来源**：判定只读其它栏的基线原文。这与 D-25 的要求一致——不猜「是谁写的」，只回答「这内容是不是本面板刚写出去的那一份」。
- **代码编辑器写回仍保留一次显式保存**：那条路径本身只改面板内容、不写缓冲，除了保存没有别的落盘入口，所以它的同步仍从保存开始；字段确认 / 新增 / 撤销三条已经由自动写缓冲驱动，因此去掉了多余的保存调用。

- **Found during:** Task 2（对照 `TablePanel.handleResourceChange` 与 `refresh` 的脏守卫时）
