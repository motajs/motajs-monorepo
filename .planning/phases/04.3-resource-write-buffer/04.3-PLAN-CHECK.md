## 4. 问题清单

### 4.1 BLOCK（不修则阶段目标不可达）

**B1 — 有待写内容时，外部工具的写入被缓冲永久遮蔽，D-16 实质失效，且两个既有测试文件无人负责**

- `required_property`：外部来源的写入必须始终能被表格面板看到并按既有冲突规则处理（D-16）；「既有测试全绿」必须由本阶段的任务负责。
- `evidence`：
  - 面板检测外部变化时读的是资源层：`packages/libs/editor-impl/src/table/tablePanel.ts:1685-1686`（`readText` → `context.requestResource`），而 `04.3-04-PLAN.md:144` 已让 `readContent` **先查缓冲**；`04.3-04-PLAN.md:146` 与 `04.3-05-PLAN.md:113` 又明确**不许改** `handleFileChange` / `updateResource` —— 于是只要该路径还有待写内容，`readContent` 永远返回缓冲值，外部内容根本读不到。
  - 计划 08 让每次字段确认都写缓冲：`04.3-08-PLAN.md:120`（`applyEdit` 成功分支追加自动写缓冲）。因此「编辑后立刻发生的外部写入」在下一次外部检测时读到的是缓冲里自己的内容 → 与基线相同 → 直接返回，不记冲突。
  - 既有用例正是这么断言的：`packages/libs/editor-impl/src/table/__tests__/externalChange.test.tsx:163-175`（脏时外部改文件必须弹冲突）、`:178-195`、`:198-221`。13 份计划的 `files_modified` **没有任何一份包含该文件**。
  - 后果不只是测试红：5 秒后缓冲会把自己的内容写盘，把外部改动**静默覆盖**，这直接违反 D-16 与 `AGENTS.md:14`（「对外功能、UI、宿主协议必须保持现状——本期为纯重构」）。
- `fix_hint`（非约束，任一路径达成上述性质即可）：在计划 04 或紧随其后的一个计划里加一条明确任务 —— 外部变化到达时缓冲不得遮蔽它（例如：先落盘再比较、或对外部变化丢弃该路径待写并让面板重读），并把 `externalChange.test.tsx` 列入该计划的 `files_modified`，补一条「有待写时外部改文件仍弹冲突」的自动化断言。

**B2 — 计划 08 无法通过自己的 verify：`isColumnDirty` 与「缓冲待写」两套口径互相排斥，`closeChoice.test.tsx` 的红例被排到后面波次**

- `required_property`：一个计划在其 verify 里引用的测试文件，必须是它自己能改绿的范围；「未保存 = 组件草稿脏 ‖ 缓冲待写」（D-11）与「自动保存后不再算脏」必须是同一条口径。
- `evidence`：
  - `04.3-08-PLAN.md:164` 的 verify 跑了 `src/table/__tests__/closeChoice.test.tsx`。
  - 但自动保存会把 `draftDirty` 清零（`packages/libs/editor-impl/src/table/tablePanel.ts:1457`），而 `isColumnDirty` 只看 `unsaved / unsavedSchema / draftDirty / 组件 isDirty`（同文件 `:1475-1480`）；计划 08 只在**发布视图**时把待写折进「未保存」（`04.3-08-PLAN.md:155`），从未把 `pendingWrite` 纳入 `isColumnDirty`，且 `:159` 明说「自动保存之后常见情况是『没有脏栏』」。
  - 于是 `closeChoice.test.tsx:225`（取消关闭后 `isColumnDirty(0) === true`）与 `:224`（`readData === {name:'a'}`）、`:262`（不保存关闭后 `readData === {name:'a'}`）在计划 08 之后都会红。
  - 该文件的迁移写在计划 11（下一波）：`04.3-11-PLAN.md:78` 只说「spy 的含义改成缓冲写入次数」「若还有『关闭后磁盘已有内容』的断言，补一次显式写盘或改成读资源层」——**没有**覆盖上面三条「编辑后读资源层仍是旧值 / 仍算脏」的反转断言。
- `fix_hint`：要么把「缓冲待写」正式纳入「脏 / 未保存」的同一判定（并说明 `onRequestClose` 的早退条件如何随之调整），要么把 `closeChoice.test.tsx` 移进计划 08 的 `files_modified` 并逐条列出要改的断言；两者必须只选一条并写清。

**B3 — 同一成员 `watchPendingChange` 在计划 02 与计划 08 里签名矛盾，计划 08 按字面会编译不过**

- `required_property`：跨计划读取的每个符号，其签名在接受方与使用方必须一致。
- `evidence`：
  - `04.3-02-PLAN.md:88`：面板要靠「订阅待写变化的回调把当前全部待写路径交出来」自己算每栏。
  - `04.3-02-PLAN.md:150`：给 `IEditorPanelContext.watchPendingChange` 声明的是「**入参无参回调**」。
  - `04.3-08-PLAN.md:153`：计划 08 要用「回调收到当前全部待写路径」来刷新每栏的待写标记。

**B4 — 「不保存关闭」只删缓冲条目、不失效缓存，丢弃后资源层仍读到未保存内容（D-08）**

- `required_property`：丢弃某路径待写之后，资源层读到的是磁盘上的旧内容，而不是被丢弃的内容。
- `evidence`：
  - `04.3-04-PLAN.md:175`：丢弃待写的动作只有「删掉条目 + 清定时器 + 通知」，**没有** `cache.invalidate`。

### 7.2 修订引入的回归（逐项回答「专门要查」）

**R-1（BLOCKER，新）— 「外部已改」是被路径记住的集合，却没有任何地方清除它；外部冲突之后该路径的缓冲读穿透被永久关闭**

- `required_property`：某路径再次发生一次正常的（非回声）写入、或被显式写盘成功 / 被丢弃之后，该路径必须重新成为「可读的待写」；`readPending` 不得因为历史上发生过一次外部冲突就永久返回 `undefined`。
- 证据：
  - `04.3-04-PLAN.md:191` 把标记做成「一个记录『已被标记外部已改的路径』的**集合**」；`04.3-02-PLAN.md:93` 规定 `readPending` 命中该集合即返回 `undefined`。
  - `schedule`（`04.3-04-PLAN.md:150`）只替换条目与定时器；`flush`（`:151`）成功后只删条目；`discardPendingContent`（`:189`）只删条目 + 清定时器——三处都没有「把该路径从集合里移除」。
  - 于是「外部冲突 → 选放弃 / 保留 → 再编辑」这条正常链路上，新写入的待写会被 `readPending` 隐藏；`readContent` 之所以还能读到新值，只是因为落到第二级 `cache.get`（`writeContent` 同时 `cache.set`），并非 `readPending` 命中。缓存一旦被外部变化失效（`updateResource` / `handleFileChange` 都会失效）或被 LRU 淘汰，读到的就是磁盘旧值。
  - `04.3-04-PLAN.md:100` 的新用例 11 在第二次写入后断言「读取仍返回待写」，但此时缓存里正是刚写的内容，即使集合未清也会绿——这条用例**不能**证明集合被清除。
- 影响：直接违反 `04.3-04-PLAN.md:26` 的 must_have「读优先命中缓冲」与 D-02 / D-09 / D-13；这是 B1「保留条目 + 读取回落」修法带出的新缺陷（RESEARCH:156 的「保留我的之后等下一次显式保存」也默认了该标记会随新写入失效，但计划没写这一步）。

### 9.3 新发现

**N-5（BLOCKER，本轮唯一阻塞）— 「回车确认」不解除延迟，弹窗在数字框回车后不会出现**

- `required_property`：**延迟中的冲突必须在「用户停手」的那一刻立刻弹出；停手既包括失焦，也包括回车确认，不能要求焦点先离开字段。**
- 证据：
  - 规格与计划自己的 must_have 都写了回车：`04.3-08-PLAN.md:34`「某栏有字段处于『已聚焦未失焦 / **未回车确认**』时……推迟；字段失焦**或确认**的那一刻立刻弹」；`04.3-01-PLAN.md:97`、`04.3-RESEARCH.md:1302` 同口径；用户定稿规格第 2 条亦为「defer until **blur/Enter**, then show immediately」。
  - 实现动作只挂 `onFocus` / `onBlur`，只在「离开容器 / 置假」时调 `showNextConflict()`：`04.3-08-PLAN.md:224`。全文没有第二处把「正在打字」置假的入口。
  - 回车确认后**不会失焦**：`04.3-09-PLAN.md:110`「按下回车时提交（**提交后不失焦**）」。数字框（`NumberInput.tsx:18-29` 目前逐键提交，Plan 09 改成回车提交）是唯一「回车确认」的字段；文本域回车是换行、不提交（`TextareaInput.tsx:78-83` 只在 `onBlur` 提交）。
  - 因此：用户在某数字框里回车确认（已产生待写）后，若外部写入到达，冲突被记下但弹窗**不出现**，直到用户点到别处让焦点离开面板——违反规格「as soon as」与 D-14 的手感要求。
  - 唯一延迟测试只覆盖 focus → blur（`04.3-08-PLAN.md:126`），没有「聚焦 → 回车 → 弹窗出现」用例；执行后自动化会全绿而该行为缺失，属**不可验证覆盖**。
- `fix_hint`（非约束，任何达成上述性质的路径均可）：让「确认」也解除延迟（例如容器上捕获 Enter 调 `setFieldEditing(false)`，或让提交路径上报一次「确认」），并补一条「聚焦 → 回车 → 弹窗出现」的红例；同时把 `04.3-09-PLAN.md:110` 的「提交后不失焦」与该机制对齐。

**N-6（WARNING）— 「正在打字」按「容器内任意焦点」计，会把面板内非输入控件也算成打字中**

- `required_property`：延迟只应在焦点落在**可编辑的格控件**上时生效；焦点在工具栏 / 空白等非输入元素上时应视为「没人打字」并立刻弹。
- 证据：`04.3-08-PLAN.md:224` 的判定是「焦点进入任一单元格控件即置真，离开即置假」+ `relatedTarget`「仍在本容器内就保持为真」。容器 `etable-columns`（`tablePanel.ts:597-600`）同时包住工具栏与表格；焦点从字段移到容器内的工具栏按钮时，`relatedTarget` 仍在容器内 → 保持为真，弹窗继续推迟。规格写的是「field focused → defer … nobody typing → show immediately」。
- `fix_hint`：判定改为「焦点在格控件上」而不是「焦点在容器内」（`onFocus` 查 `event.target`，`onBlur` 只对「新焦点仍是格控件」保持为真）。

**N-7（WARNING）— 两个定稿动作的写盘失败路径未规定，异步 reject 会变成未处理拒绝**

- `required_property`：两个动作在写盘失败时必须**确定性结算**：待写保留、弹窗 / 标记状态一致、失败进既有错误通道或日志（D-07 / O2）。
- 证据：`04.3-08-PLAN.md:214-218` 四步没有 `saveColumn` 返回 `ContentSaveStatus.Failed` 的分支，也没有 `flushResource` reject 的处理；而 `flush` 失败会继续抛给调用方（`04.3-04-PLAN.md:164`），两个入口又是 `(): void => this.keepExternalConflict()` / `(): void => this.discardExternalConflict()`（`tablePanel.ts:751-752`）。若 `flushResource` 失败，异常会从点击处理器逃逸（未处理拒绝），第④步不执行，弹窗与待写状态停在半途。
- `fix_hint`：在第②③步之间检查 `ContentSaveStatus`，并把 `flushResource` 的失败 catch 后走既有错误提示 / 日志，保持「失败保留待写」；补一条失败用例。

**N-8（WARNING）— 把两个冲突方法改成 async 后，构造器里的 `(): void =>` 箭头会 typecheck 失败，计划没点名**

- `required_property`：计划点名的每个改动点，在执行后必须能通过它自己的 verify（这里含 `typecheck`）。
- 证据：`04.3-08-PLAN.md:216-217` 要求 `await this.saveColumn(...)` / `await this.context.flushResource(...)`，`:210` 要求 `await this.context.discardPendingResource(...)`，即 `keepExternalConflict` / `discardExternalConflict` 必须变 async；但 `tablePanel.ts:751-752` 是显式 `(): void => this.discardExternalConflict()` / `(): void => this.keepExternalConflict()`。用 TypeScript 实跑最小样例确认：返回 `Promise<void>` 的表达式放进显式 `: void` 的箭头体是 `TS2322 Type 'Promise<void>' is not assignable to type 'void'`。计划 Task 3 的 read_first 只列了方法体（`04.3-08-PLAN.md:189`），没列 738–755 的映射。
- `fix_hint`：把两处箭头改成块体 `{ void this.xxx(); }`（或让方法内部 catch 后保持 `void`），并在 read_first 点名这两行。
