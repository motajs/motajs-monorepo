## 4. 缺陷详情

### 4.1 BLOCK · `resolvePath` 反函数对地图 / 素材不存在，D-26 只覆盖了四类面板里的一类

- **required_property：** 凡声明了 `IEditorPanelType.createOpenParam` 的面板类型，都必须能从自己产出的 openParam 同步还原出打开路径；做不到的类型必须被**显式**排除在 D-26 之外，并由用户确认这次缩小。
- **证据（源码，不是计划自述）：**
  - 表格：`tablePanelType.ts:63` `createOpenParam(path) → { target: { dataPath: path } }`，反推 `target.dataPath` 精确无损；`15:159` 的实现对得上。
  - 地图：`mapPanelType.ts:76-85` `→ { target: { mapId } }`；`IMapPanelTarget` 只有 `mapId`；`IMapSummary` 只有 `id / name`；能力面只有单向 `resolveMapPath(path)`（`map/types.ts:476`）。**路径不可还原。**
  - 素材：`assetPanelType.ts:104-112` 的 `createTargetOf` 只保留 `categoryId`（清单 / schema / 默认值三种文件得到同一个 openParam）或 `categoryId + assetName`（扩展名可能被 `resolveAssetName` 去掉）。**路径不可还原。**
  - 资源管理器面板类型本身没有 `createOpenParam`（`fileExplorerPanelType.ts:31-37`），不参与，属正常。
  - 计划把这件事写成了「合法降级」：`14:93`（「没有声明 `resolvePath`，或返回 `undefined` 时，不去重，照旧打开」）、`15:23`（「没有声明 `resolvePath` 时行为与现在完全一致」）。但 14 / 15 通篇没有出现 `map` / `asset` / 「地图」 / 「素材」，即**这两类面板永远不会去重**（grep 结果：`15:159` 只实现 `tablePanelType.resolvePath`）。
- **后果：** 从资源管理器把同一个 `maps/xxx.jsonc` 打开两次（或同一素材分类的两个文件）仍然得到两个标签，两个面板共用一个路径缓冲、共享「最后写盘者胜」，就是 `04.3-CONTEXT.md:162` 记录的那个真实缺陷原样保留；D-26 的「因此同一个文件不会同时以两种面板打开」与「一条路径最多一个可编辑面板」两条都不成立。
- **可执行后果：** Plan 15 的验证全绿也证明不了 D-26 达成——它只测表格。
- **修复方向（择一，不能都不做）：**
  1. 让 openParam 自己带上原始路径：地图 `→ { target: { mapId }, dataPath: path }`、素材 `→ { target: {...}, dataPath: path }`，各自实现 `resolvePath` 读这个字段。`editor-core` 仍不解释形状（层内约定，符合 04.2 D-32），`create` / `canOpen` 不动；同时为素材明确「去重单位是文件路径还是分类」——按路径去重时同一分类的两个文件仍会开出两个面板，需要用户在这一步一并拍板。
  2. 或者：明确把 D-26 缩到「只有表格」，写进 CONTEXT，并让 15 的 must_have 与 12 的威胁表如实写明地图 / 素材仍有双写者，由用户确认这次缩小。

### 4.2 WARNING · Plan 12 对 `devHostWatch` 第二条的改写，会被它自己的装配提前写盘、变成空转用例

- **required_property：** 改写后的用例必须真的验证「同一路径第二次打开只聚焦已有标签，且不触发额外写盘」；用来验证的装配本身不得先把被测状态改变掉。
- **证据：** `12:118` 要求「打开一次并留下一个未提交草稿；再打开同一路径；断言仍是同一个标签、同一个实例、**草稿还在**……；随后保存，断言磁盘等于这份草稿」。但「再打开同一路径」只能经由 `openTableTab` 这类「先 `openBlankTab()`、再 `openPanelInTab`」的辅助（现状 `devHostWatch.test.tsx:50-59`；`12:116` 也仍让辅助去找回标签，说明空白标签照建）。而 `openBlankTab` 在有挂载面板时会 `void activateTab(blank)`（`shellSystem.ts:660`），切出链 `invokeSwitchOut` 里是「面板 `onSwitchOut` 写缓冲 → 外壳立刻 `flushPendingContent()` 打盘」（`shellSystem.ts:1011,1043-1049`）。也就是说草稿在去重判定发生**之前**就已经落盘，「未提交草稿」这个前提消失，后面「保存后磁盘等于草稿」恒真。
- **修复方向：** 在 `12:116` 明确「第二次打开不新建空白标签」——直接对已打开的那个表格标签调用 `openPanelInTab(该标签 id, ...)`（命中即 `activateTab`，同标签不产生切出，见 `shellSystem.ts:675` 与 `departActiveInstance` 的同实例短路 `:632`），或直接 `activateTab`；并说明为什么不能走空白标签（切出会落盘）。同时把「草稿还在」写成可判定的断言（例如 `table-unsaved` 标记仍在 / 输入框值仍是草稿值）。

### 4.3 WARNING · 15 的「失败不留登记」用例与「替换去重」能力没被钉住

- **required_property：** 替换与失败两条生命周期路径都要有用例能真的红。
- **证据：** `15:131` 的 (vi) 是「先开 X → 再开一个不带路径的面板 → 断言登记被清」，这只覆盖「清空」；「同一个标签换成另一条路径 → 登记更新为新路径」没有用例，而 `tabPaths` 若只增不改，就会出现「标签显示 Y、却登记为 X」，之后打开 X 会聚焦到一个显示 Y 的标签（比没去重更糟）。同段「再让工厂抛错一次，断言没有留下任何登记」若发生在空标签上则恒真。
- **修复方向：** 在 (vi) 里补一条「同标签 X→Y：再次打开 X 会新建标签、再次打开 Y 只聚焦」；失败用例改为「在一个已登记 X 的标签上让工厂抛错」，断言 X 不被占用（重新打开 X 得到新实例）。

### 4.4 WARNING · 15 对 `initializeInstance` 失败分支清登记，会造出「标签还在、登记没了」的第二个面板

- **required_property：** 一条已经打开并显示某路径的标签，不得因为初始化失败而变成「同一路径的第二个可编辑面板」。
- **证据：** `15:93` 与 `15:131` 把清理也挂在 `initializeInstance` 的失败分支；但该分支发生时标签已经指向这个实例（`shellSystem.ts:683` 已写好 `tabs[index]`，`689` 才开始 initialize）。清掉登记后，同一路径会再开一个新标签，而旧标签仍带着一个 Error 状态的实例——违反 `04.3-CONTEXT.md:166` 的前提。
- **修复方向：** 初始化失败时不清登记（保留「这条路径被这个标签占用」的事实），或连标签一起处理；并在计划里写明取舍。

### 4.5 WARNING · 用 `;` 串联的验证命令会掩盖前一条失败

- **required_property：** 每条 `<automated>` 的退出码必须反映其中**所有**命令的结果。
- **证据：** `15:98`（`typecheck; vitest run`）、`15:136`、`15:166`、`14:122`（两条 `node -e`）、`12:125`、`13:84`。`cmd1; cmd2` 取最后一条的退出码，前一条失败不影响整体成败；对 15 Task 1 而言，`IEditorPanelType.resolvePath` 写错类型仍可能被 vitest 通过掩盖。
- **修复方向：** 用 `&&`（PowerShell 用 `if ($?) {}` / 分号改 `; if ($LASTEXITCODE -ne 0) { exit 1 }`）或在 `fails_when` 里要求逐条贴出退出码。

### 4.6 WARNING · 记账：INTERFACE-NAME 的旧口径被冻结，VALIDATION 没有 14 / 15 的行
