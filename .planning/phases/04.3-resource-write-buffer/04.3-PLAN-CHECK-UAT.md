## 三、源码核对（为什么这些结论成立）

### 3.1 Gap A

- `ShellSystem.rememberTabPath` 只在 `shellSystem.ts:700` 定义，唯一生产调用点是 `openPanelInTab` 的 `:810`；`openPanelInTab` 只有在调用方传入 `path` 时才登记（`:776-810`）。这与 `04.3-VERIFICATION.md` 的 O-6 一致。
- `TablePanel.setTable`（`tablePanel.ts:1076-1129`）确实是「目标赋值的唯一入口」之一：空栏选择器 `openIntoColumn`（`:1217-1219`）、空栏新建 `createIntoColumn`（`:1250`）、编辑 Schema 复用空栏 `openSchemaPanel`（`:1365`）都经过它。
- 但 `TablePanel.cancelCommentStrip`（`:1849-1864`）在用户取消「剥离注释后打开」时直接执行 `column.target = null`（`:1857`），**没有经过 `setTable`，也没有调用任何上报**。此时 `setTable` 已经上报过该路径；取消后标签还登记着那条路径，但栏里已经什么都不显示，资源管理器会切到一个空标签而不是重新打开文件。这是真实可达路径，不是理论边界。
- 集合语义是必要的：`TablePanel.openSchemaPanel` 会把 schema 路径作为一条独立 `dataPath` 放进空栏（`:1361-1366`）；D-28 也明确「数据栏 + 它的 schema 栏」合法。此时一个标签同时显示 `t.json` 与 `t.schema.json` 两条路径；只记一条会让另一条在资源管理器里再开一个标签。多栏不同表同理。
- `create-time` 空操作：`ShellSystem.createInstance`（`:950-978`）先调用工厂，工厂里的 `setTable` 会触发上报；但实例写进 `this.instances` 是在工厂返回之后（`:972`），标签记录更是在 `openPanelInTab` 的 `:805` 才写入。`registerTabResourcePaths` 按 `instanceId` 在 `tabs` 里找不到，确实为空操作。计划这条判断正确。
- 测试真实性：`04.3-23` 的表格用例通过 `openBlankTab` + `openPanelInTab`（和 `duplicatePath.test.tsx:92-96` 现有 helper 相同）驱动，不是 `FileExplorerPanel.openWith`（`fileExplorerPanel.ts:170-176`）。`main.tsx:50-57` 的 explorer 回调恰好就是这两步，所以机制同构；但 explorer 的候选判定、`createOpenParam` 调用和 `path` 传递失败不会被这组用例发现。只能算测试深度不足，不算 blocker。

### 3.2 Gap B

- **打开参数只在工厂 `create` 里解释：** `assetPanelType.ts:126-137` 在 `create` 里读取 `param.openParam` 并 `AssetPanel.setTarget`；`mapPanelType.ts:58-69` 同样在 `create` 里 `MapPanel.setMap`。如果改为「旧实例换目标」，需要另造一个异步的 `applyOpenParam` 入口，并让每个复用类型自己负责保存与冲突。计划选择重建实例，理由成立。
- **既有「标签内替换实例」的保存范围：** `openPanelInTab` 的替换分支（`shellSystem.ts:796-799`）只在 `activeTabId === current.id` 时调用 `leaveActiveInstance`（`:1104-1107`，内部 `enqueueSwitchOut` → `onSwitchOut` + `flushPendingContent`）；非活动标签直接 `closePanelInstance`（`:592-608`），不会先调用 `onSwitchOut`。因此计划为「非活动复用标签」补 `enqueueSwitchOut` 是必要的，不是可选优化。
- **顺序：** `enqueueSwitchOut` 把切出排进 `switchChain`（`:1146-1151`），`closePanelInstance` 先删实例注册、再 `await switchChain`、最后 `dispose`（`:592-608`）。计划要求 `await enqueueSwitchOut` 后再 `closePanelInstance`，确实能保证「先保存、后释放」；`invokeSwitchOut` 里的 `onSwitchOut` 在 `flushPendingContent` 之前（`:1173-1186`），也符合面板「先写缓冲、外壳再落盘」的既有契约。
- **冲突查询：** `AssetPanel.pendingConflict` 在 `assetPanel.ts:304`，`hasPendingConflict` 可以直接返回 `pendingConflict !== undefined`；地图的 `IMapPanelViewState.pendingConflict` 在 `map/types.ts:807`，`MapPanel` 的 `publish`（`mapPanel.ts:593-595`）把它放在 `store.state`。两个面板都能回答。冲突时激活 owner 标签后，素材 `onSwitchIn` 会 `publish`（`assetPanel.ts:456-465`，`publish` 在 `:1655` 根据 `active` 决定是否显示 `pendingConflict`），地图视图也会渲染 `MapPanelView.tsx:735`；用户能看到既有冲突弹窗，信号成立。
- **自动保存会被提前触发：** `editor-dev/main.tsx:51-52` 的资源管理器打开方式是 `openBlankTab()` 然后 `openPanelInTab(...)`。`openBlankTab` 在已有活动实例时会 `void this.activateTab(tabId)`（`shellSystem.ts:750-759`），`activateTab` → `departActiveInstance(null)`（`:646-659`、`:890-907`）会先调用旧活动面板的 `onSwitchOut` 并 `flushPendingContent`。因此：
  - 正常复用（owner 曾是活动标签）：在 `openPanelInTab` 执行前，A 已经被保存过一次；计划又在非活动复用分支 `enqueueSwitchOut(A)`，于是 A 的 `onSwitchOut` 与全量 flush 各发生两次。这不是数据错误，但是重复写盘 / 重复通知，且计划自己的顺序用例没有断言次数。
  - 冲突复用（owner 曾是活动标签）：在 `hasPendingConflict` 被检查之前，A 已经被 `onSwitchOut` 保存（素材 `AssetPanel.save` → `saveAll` → `writeCategory`，`assetPanel.ts:608-610`、`1719-1748`、`1825-1874`；地图 `MapPanel.onSwitchOut` → `save`，`mapPanel.ts:1874-1876`、`1783-1830`），所以「不写盘」在这条顺序下不成立。生产 explorer 流程中 owner 通常不是活动标签（explorer 才是活动标签），因此用户常见路径不触发；但计划把 D-33 写成无条件规则，且自己的冲突用例会按「先开 A、再用新空标签开 B」的顺序触发这条预保存，导致用例必红。

### 3.3 结构与门禁

- 波次：22=16（依赖 21=14；15 被 19 占用）、23=17、24=18、25=19；依赖图为 21→22→23→24→25，无环；24 同时依赖 22 与 23，和「23 / 24 都改 `panel/types.ts` 与 `shellSystem.ts`」的事实一致。
- 四份计划均有 `<automated>` 与 `<fails_when>` 一一配对；`requirements: []`；无 `prohibitions`；LF / 无 BOM；已存在的 `files_modified` 全部被 git tracked（`git ls-files --error-unmatch` 通过），三个新测试文件是计划新建。
- 没有发现计划之间对同一路径的未声明并发写：23 与 24 的共用文件通过 23→24 顺序化。

## 四、问题清单

### BLOCKER

#### BLOCKER 1 — Gap A 少一个真实的重登记路径：`cancelCommentStrip`

- **required_property：** 一个标签的路径登记必须始终等于「该标签当前实际显示的全部资源路径」；任何把栏目标从有值改为空的路径都必须重新上报或清除登记。
- **evidence：**
  - `TablePanel.cancelCommentStrip` 在 `tablePanel.ts:1849-1864` 直接执行 `column.target = null`（`:1857`），没有 `reportVisiblePaths` 调用。
  - 计划 `04.3-22-PLAN.md` 的 Gap A 行为表与 `must_haves` 只写 `TablePanel.setTable` / `TablePanel.closeColumn` 两个上报点（Plan 22 第 22、98、111-112、126 行；Plan 23 `must_haves` 第 28 行、Task 2 action 第 154-156 行）。
  - 计划 `04.3-23-PLAN.md` 的 `key_links` 声称「`TablePanel.setTable` 是目标赋值的唯一入口」（第 42 行），与源码 `:1857` 矛盾。
- **impact：** 用户从空栏选择器打开一个带注释的 JSON、在「是否剥离注释」提示上点取消后，标签仍登记着这条路径。之后在资源管理器点同一个文件，会切回这个已经空掉的标签，而不是重新打开文件；Gap A 仍有用户可触发的错误落点。
- **fix：** 在 Plan 22 的接口行为表与 Plan 23 的 Task 2 中，把「所有会改变栏目标的路径」列全：`TablePanel.setTable`、`TablePanel.closeColumn`、`TablePanel.cancelCommentStrip`（目标置空后上报剩余路径）。在 `duplicatePath.test.tsx` 的 Gap A 用例组补一条「打开带注释表格 → 取消剥离 → 从新空标签打开原路径应新开/或只登记剩余路径」的用例。Plan 22 的「setTable 是唯一入口」必须改成「setTable 是主入口，但取消剥离也直接清目标」。

#### BLOCKER 2 — Gap B 冲突用例按计划原文不可执行，且「不写盘」不是无条件成立

- **required_property：** 「被复用面板有未表态冲突时不写盘、不释放、不新建，只切前台」必须对计划自己的测试顺序成立；测试必须能区分「复用被拒」与「打开空白标签时的自动切出保存」。
- **evidence：**
  - 计划 `04.3-24-PLAN.md` 外壳用例 (c)（第 120 行）：「用新空标签开 B：只有一个标签、没有 `switchOut` / `dispose` / `create:B`」。但测试 helper 的「新空标签」来自 `openBlankTab`；`openBlankTab` 在 owner 仍是活动标签时会 `void activateTab(blank)`（`shellSystem.ts:750-759`），`activateTab` → `departActiveInstance(null)` 会先 `invokeSwitchOut(A)`（`:646-659`、`:890-907`）。所以日志里一定先出现 `switchOut:A`，用例 (c) 按原文必红。
  - 素材用例 (b)（第 162 行）与地图用例 (b)（第 201 行）同样是「打开 A → 改 → 设冲突 → 用新空标签打开 B」。`openBlankTab` 会在冲突检查前调用 A 的 `onSwitchOut`；素材 `onSwitchOut` → `save` → `saveAll` → `writeCategory`（`assetPanel.ts:467-472`、`608-610`、`1719-1748`、`1825-1874`）会把 `read: 2` 写出去；地图 `onSwitchOut` → `save` → `saveMapData`（`mapPanel.ts:1874-1876`、`1783-1830`）会调用保存。于是用例断言的「没有写盘 / 没有 switchOut」都不成立。
  - 真实 explorer 流程中 owner 通常非活动（explorer 才是活动标签），所以生产路径上冲突拒绝仍可能成立；但计划把 D-33 写成无条件规则，且测试没有把「owner 先处于非活动」写进装配步骤。
- **impact：** 这是计划自带的验收门禁；按原文执行时 `shellTabReuse.test.ts` (c)、`assetTabReuse.test.tsx` (b)、`mapTabReuse.test.tsx` (b) 会红。执行者若为了让用例变绿而改断言，会把真正的「预保存」问题藏起来。
- **fix：**
  1. 测试装配改成：先打开 A，再打开一个空白标签让 A 变为非活动（这一步允许 A 保存），然后**重置/清空顺序日志**，在非活动 A 上直接制造脏改动与 `pendingConflict`，最后在这个已存在的空白标签上调用 `openPanelInTab(B)`。这样「复用被拒」与「打开标签时的正常切出」可以区分。
  2. 或者把复用判定提前到 `openBlankTab` 之前（例如先解析复用目标，再决定是否创建 / 激活空白标签），从机制上保证「有冲突就不触发切出保存」。这需要改 `openPanelInTab` 的调用顺序或 explorer 的 open 回调，属于设计层的选择，不能只改用例。
  3. 无论选哪种，都必须补一条「owner 是活动标签时」的显式用例，写清预期：是「先保存再拒绝」（当前机制）还是「完全不保存」（需要改机制）。

#### BLOCKER 3 — 素材复用用例的工厂包装绕过了 `openParam`，第二个面板不会显示 B

- **required_property：** 复用测试必须通过真实面板类型的工厂来创建实例，否则测到的不是生产路径；第二次打开的 `openParam.target` 必须被应用，面板内容才会是 B。
- **evidence：**
  - `assetPanelType.ts:126-137` 是唯一解释 `openParam` 并调用 `AssetPanel.setTarget` 的地方。
  - 计划 `04.3-24-PLAN.md` 第 159 行要求测试注册一个包装类型：`create: (param) => { const panel = new AssetPanel(param, { categories: ASSET_TEST_CATEGORIES }); created.push(panel); return panel; }`。这里直接 `new AssetPanel`，**没有执行** `type.create`，也没有调用 `panel.setTarget(openParam.target)`。
  - 因此用例 (a) 第二次打开 B 时，新实例的 `selectedName` 不会被设成 `foe.png`；第 161 行断言「第二个面板的选中名是 `foe.png`」必红。

### WARNING

#### WARNING 1 — 正常复用会执行两次 `onSwitchOut` / 两次全量 flush

- **required_property：** 复用前的自动保存应当是可预期的一次；重复保存不能改变数据，但会让「保存一次」的契约与测试断言含混。
- **evidence：** `openBlankTab` 在 owner 活动时先 `activateTab(blank)` → `departActiveInstance(null)` → `invokeSwitchOut(A)`（`shellSystem.ts:750-759`、`646-659`、`1173-1186`）；随后 `openPanelInTab` 的复用分支又 `enqueueSwitchOut(A)`（计划第 111 行）。两条路径都会执行 `A.onSwitchOut()` 与 `flushPendingContent()`。计划外壳用例 (a) 只断言 `switchOut:A` 在 `dispose:A` / `create:B` 之前，没有断言次数。
- **impact：** 素材会多一次 `saveAll`（第二次通常因 `snapshot` 为空返回 false），地图会多一次 `save`（第二次 `saveMapData` 可能被调用但无脏数据）；多一次通知 / 写盘，不影响最终内容，但属于计划没有解释的行为。
- **fix：** 在复用分支判断 owner 是否刚刚被 `departActiveInstance` 保存过，避免重复入链；或者把用例改为明确断言「两次是允许且幂等的」，并在 D-32 里写清。至少要让测试记录 `switchOut:A` 的次数，避免执行者无意间留下重复保存。

#### WARNING 2 — 保存失败没有被复用门禁拦住，可能销毁未保存内容

- **required_property：** 复用承诺「先存后换」；如果 `onSwitchOut` 没有真正保存成功，不能静默释放旧实例。
- **evidence：** `IEditorPanel.onSwitchOut` 返回 `Promise<void>`，外壳 `invokeSwitchOut` 只捕获异常并 `flushPendingContent`（`shellSystem.ts:1173-1186`）；`flushPendingContent` 的布尔结果在 `invokeSwitchOut` 里被忽略。地图 `MapPanel.save` 在宿主保存失败时捕获错误、`publish` 提示并返回 `false`（`mapPanel.ts:1823-1829`），但 `onSwitchOut` 仍然正常 resolve（`:1874-1876`），随后 `closePanelInstance` 会 `dispose`（`:592-608`、`1844-1851`）。素材的 `saveAll` 失败时字段保留 `unsaved`，但实例同样会被释放。
- **impact：** 地图在复用切换时如果宿主保存失败，旧实例被销毁，内存里的改动可能丢失；这比普通切标签（面板还在，可重试）更严重。素材的缓冲可能还在，但已不是「保存成功后销毁」的确定行为。
- **fix：** 明确失败策略：要么在复用前检查保存结果（给 `onSwitchOut` 增加可观察的完成信号，或让面板提供保存结果），失败时保留旧实例并只切前台；要么在 D-32 中写明「保存失败仍会重建，由既有错误提示承担」，并补一条失败用例。不能把「先存后换」只建立在 `onSwitchOut` resolve 上。

#### WARNING 3 — Plan 25 的已知 flake 豁免与自动门禁不一致

- **required_property：** 计划声明的已知 flake 处理口径必须与 `<automated>` 实际实现一致，否则门禁会在已知 flake 上假红。

- **impact：** 机器负载高时，Plan 25 的门禁会在 Plan 19 已确认的已知 flake 上失败；执行者可能被迫放宽门禁或反复重跑，违反「不改用例、不放宽时限」的口径。
- **fix：** 把 editor-dev 的两条已知 flake 纳入与 editor-impl 相同的「单文件重跑 / 负载下降后连绿」分支；或在 Task 1 里明确「editor-dev 允许按既有 flake 口径重跑，但门禁脚本只接受最终连绿」。不要只写在 must_haves 里。

#### WARNING 4 — 「`create` 里的上报是空操作」没有对应测试

- **required_property：** Plan 23 的 `must_haves` 要求「这一点在 JSDoc 与测试里写明」，测试清单应包含一个工厂创建期上报的用例。
