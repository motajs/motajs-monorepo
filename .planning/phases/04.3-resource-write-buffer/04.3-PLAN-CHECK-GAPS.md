## 三、问题清单（按严重度）

### BLOCKER

**B1 `[context_compliance]` 冲突未表态时，撤销 / 重做仍会清标记并写盘**

- 失败的不变量：**在用户于冲突弹窗表态前，任何编辑器侧路径都不得清除 `externallyChanged` 标记、也不得排缓冲/写盘。**
- 证据（源码实读）：
  - `tablePanel.ts:1047-1053`（`undo` / `redo`）→ `:2322-2356` 的 `applyUndoRedo`，在 `:2351-2355` 直接 `saveDocument(..., true)`（安静模式）；
  - 17 的守卫只写在「非安静分支」（17 `:143`）与 `saveAfterEdit`（17 `:144`），`applyUndoRedo` 绕过两者；
  - `saveDocument` 安静分支 → `persist`（`:1544-1550`）→ `IResource.write` → `ResourceSystem.writeContent`（`resourceSystem.ts:126-135`）→ `WriteBuffer.schedule`（`writeBuffer.ts:47-66`），后者构造新条目 `externallyChanged: false` 并 `armTimer`；
  - 5 秒后 `runScheduledFlush → flush`（`:241-248`、`68-80`）把编辑器内容写出去——用户从未点过弹窗任何一个动作。
- 可达性：`shellSystem.ts:375-390` 的 Ctrl+Z / Ctrl+Y 监听挂在 `window`，不排除焦点在可编辑字段；冲突「停手才弹」期间（`tablePanel.ts:2467-2473`）与弹窗显示期间都拦不住。
- 后果：冲突处置定稿「冲突只由这两个动作结算」字面为假；G2 未闭合。
- 修复方向（非绑定）：把守卫做成不变量而不是两个调用点（例如在 `TablePanel.saveDocument` 入口对 `pendingConflict` 一律停手，仅给 `TablePanel.keepExternalConflict` 一个显式豁免），并补一条先红后绿：制造延后冲突 → 调 `undoSystem.undo()` → 裸磁盘仍是外部内容、`hasAnyPendingContent()` 为真、标记仍在。

**B2 `[verification_derivation]` 17 的「切标签」用例正确实现后也不可能变绿**

- 失败的不变量：**每条「先红后绿」用例在正确实现后必须能通过。**
- 证据：17 `:107` 的用例 (2) 在 `activateTab(blankTabId)` 之后仍断言 `panel-conflict-dialog` 非空；而外壳只渲染活动面板（`shellSystem.ts:350-361`），切到空白标签后表格面板被卸载，`ExternalChangeDialog` 随之卸载（它由 `tablePanel.ts:595` 在面板视图内按 `conflictStore` 渲染），DOM 里不可能还有该节点。
- 后果：17 Task 2 要求「全绿」且禁止「放宽断言」，执行器只能在「删/改断言」与「卡死」之间二选一，必然产生偏差或失败。
- 修复方向（非绑定）：切回原标签后再断言弹窗，或改为断言 `panel['columns'][0].pendingConflict` / `conflictStore`，不断言已卸载面板的 DOM。

### WARNING

**W1 `[key_links_planned]` 关闭判据是全局的：任何待写（含其它标签的未决冲突 / 持续写失败）都会让「干净标签」无提示地关不掉**

- 失败的不变量：**关闭一个自身没有待写的标签，不应因别处的未决状态而静默失败。**
- 证据：18 `:132` 用 `const flushed = await this.flushPendingContent(); if (!flushed) return;`，而 `flushPendingContent` 的判据是全局 `hasAnyPendingContent()`（`resourceSystem.ts:224-226`）。表格的「保存并关闭」在 `pendingConflict` 时被 17 改成返回 `Saved`（17 `:143`），`handleCloseChoice` 因此结算 `Save`、关闭弹窗消失；随后外壳因跳过留下的标记返回假，标签保持打开——用户看到「弹窗没了、标签还在」，且没有任何错误文案（O2 不允许新增）。背景标签收到外部变化时也会记 `pendingConflict`（`tablePanel.ts:2400-2439` 逐实例钩子），这时关闭另一个干净标签同样被静默拦住。
- 修复方向（非绑定）：把 false 的判定收敛到「本标签在本次关闭中涉及/写入的路径」，或在假值时给出既有可见状态（例如不关闭并复用「正在等待保存…」的禁用态），不新增文案。

**W2 `[nyquist_compliance]` 18 没有测到「冲突被跳过 → 仍有待写 → 不丢标签」这条分支**

- 失败的不变量：**外壳布尔的两个来源（写盘抛错 / 仍有待写）各自有会失败的用例。**
- 证据：18 `:87-94` 的 `shellFlush` 用例只用 `fs.failing`，覆盖的是「抛错」；`assetCloseChoice` 的失败同样是 `fs.failing`。没有一条「面板返回 Save、路径被 `externallyChanged` 跳过、`hasAnyPendingContent()` 仍真 → 标签保留」的用例。17 的 `flushAll` 单测只覆盖 ResourceSystem，不经过 `closeTab`。

**W3 `[context_compliance]` 一栏只有单个 `pendingConflict` 槽：data 与 schema 同时冲突时，先到的那条丢弹窗、只余一个无法从 UI 结算的标记**

- 失败的不变量：**每个被标记的待写都必须有一个用户可达的结算出口。**
- 证据：`tablePanel.ts:2484-2501` 的 `recordPendingConflict` 直接覆盖 `column.pendingConflict`（只有「同路径同原文」才去重）；`TablePanel.computeAdd` 的路径会同时置 `unsaved` 与 `unsavedSchema`（`:1427-1429`），因此 data + schema 可同时有待写；外部同时改两个文件时，第二条覆盖第一条的弹窗状态。两个动作只结算 `conflict.path` 一条（`:2529-2575`、`:2588-2628`）。17 的 `flushAll` 跳过让剩下的那条一直待写（右上角提示与 `beforeunload` 持续生效、关闭被 W1 拦住），用户只能「不保存关闭」或释放编辑器才能清掉。
- 修复方向（非绑定）：一栏按路径排队多个冲突，或两个动作结算该栏所有被标记路径；并补用例（新增一行 → 外部同时改 data/schema → 逐个结算 → `hasAnyPendingContent()` 为 false）。

**W4 `[task_completeness]` 16 的门禁要求了 action 没让写的字面量**

- 失败的不变量：**`<automated>` 要求的字面量必须能从 `<action>` 推导出来。**
- 证据：16 `:123` 的 `need` 包含 `'04.3-17'`、`'04.3-18'`、`'04.3-19'`，但 `:86-120` 的 action 只写「17 / 18」「Plan 18」「Plan 19」，没有任何地方要求写计划号字面量；`:124` 的 `fails_when` 却把「缺少 17 / 18 / 19 的引用」当失败。

**W5 `[context_compliance]` 素材 `saveAll` 的「部分成功」仍会结算 `Save`**

- 失败的不变量：**「保存并关闭」的失败判定覆盖全部脏分类，而不是「至少一份写成功」。**

**W6 `[nyquist_compliance]` 19 的门禁按 action 完成后必然失败（`已通过` 切片）+ 自己的措辞陷阱**

- 失败的不变量：**`<automated>` 在按 `<action>` 正确完成后能够通过。**

### 5.2 六项回归检查

1. **入口守卫 vs 合法保存。** “保存外部修改”走 `discardExternalConflict`，不调 `saveDocument`，因此不受守卫影响（`tablePanel.ts:2529-2575`）；自动保存另一栏时守卫按 `columnIndex` 取 `column.pendingConflict`，不会误挡其它栏。关闭流程：有冲突的栏在 `saveAllColumns → saveColumn → saveDocument` 被守卫挡下并返回 `Saved`（`tablePanel.ts:972-984`、`:1688-1695`），表格关闭弹窗因此结算 `Save`，外壳再以“仍有待写”保持标签——这是 18 `:137` 明示的取舍，不是静默失败。**但切标签往返另有一处回归，见 NEW-1。**

2. **撤销/重做用例的真实性。** `undoSystem.undo()` 会 `await entry.undo.undo(context)`（`undoSystem.ts:40-55`），`TablePanel.undo` 转调 `applyUndoRedo`（`tablePanel.ts:1047-1053`、`:2322-2356`），路径是通的；断言用的是裸磁盘 `readDisk`（`externalChange.test.tsx:108-111`），不是会命中缓冲的 `readContent`。**问题在于区分力：** `applyUndoRedo` 的 `void saveDocument` 不被 `undoSystem.undo()` 等待，且用例没有推进 5 秒定时器；修前修后“裸磁盘仍外部、待写真、冲突在、弹窗在”都成立，所以 17 `:117` 这条撤销用例**不是先红后绿**。要让它有区分力，可在 undo 后推进 5 000 ms 再断言磁盘仍是外部内容，或改断言 `readContent` 仍是外部内容（标记未清时 `readPending` 返回 undefined、回落到磁盘），或直接断言条目 `externallyChanged`。同文件用例 (4)（17 `:116`）已经用 `readContent` 钉住了安静保存路径，守卫并非完全无验证。

3. **W1 可见状态的数据源。** 成立：`editor-shell-pending` 的渲染条件是 `hasPendingWrite`（`shellSystem.ts:215-223`），值来自 `resourceSystem.hasAnyPendingContent()`（`:1002`），即 `buffer.size() > 0`（`resourceSystem.ts:224-226`）。被冲突规则跳过的条目仍留在缓冲（17 `:150` 只 `continue`，不删条目），所以提示会出现；`onPendingChange` 钩子会 `notify()`（`shellSystem.ts:507-511`），不是只在初始化时算一次。

4. **W3 的结算广度。** 两条路径确实由一次动作一起结算；但 `TablePanel.keepExternalConflict`（17 `:159`）把 `unsaved` 与 `unsavedSchema` 都置真，而 `saveDocument` 按这两个标志分别 `persist`/`persistSchema`（`tablePanel.ts:1540-1550`），因此**单路径冲突时也会写另一条从未编辑的路径**。对新增一行同时改 data/schema 的用例（17 `:118`）这是正确的；对只改了 data 的普通冲突，这是不必要写入，且若另一条路径刚好有尚未标记的外部变化，会被这次写覆盖。详见 NEW-3。

5. **W5 部分失败。** 恢复逻辑有：18 `:145` 在任一条 flush 失败时把快照里每个分类的 `unsaved` 置回真，重试仍走同一条关闭流程；`AssetPanel.writeCategory` 失败时本来就不清 `unsaved`（`assetPanel.ts:1815-1829`）。**但用例的前提有缺：** 见 5.1 的 W5，音频分类没有 seed 条目，`unregisterAsset` 不会产生第二笔脏改动；执行器需要先在 `content/audio/.list.jsonc` seed 一条音频再注销，否则该用例要么绿得没有意义、要么因“音频 `unsaved` 为真”断言失败而无法按 action 转绿。
