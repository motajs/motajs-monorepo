    - 第 3 步 `flushResource` 抛错（缓冲按 Plan 04 保留条目并已记 `resource.flushFailed` 日志）：用 `try` / `catch` 包住，`catch` 里用**同一句既有文案** `this.publishError(columnIndex, '写入失败，请重试。')` 提示一次（复用既有文案，不新增任何失败界面，符合 O2），然后同样**直接 `return`**：不清冲突、不关弹窗、不执行第 4 步、不 `showNextConflict()`、**不向外抛**（否则会变成未处理的 rejection，因为点击路径是 `(): void` 箭头）。
    - 两个失败分支的净效果统一为一句话：**待写保留、条目与「外部已改」标记不清、右上角提示常驻、弹窗不关、只有既有的错误提示与日志**。用例见 Task 1 的 (g)。

    **两个方法变成 `async` 之后，构造器里的两个箭头必须一起改（第四轮 N-8，否则 `typecheck` 报 TS2322）**：`TablePanel.keepExternalConflict` / `TablePanel.discardExternalConflict` 现在返回 `Promise<void>`，而构造器第 751…752 行是显式 `(): void => this.keepExternalConflict()` / `(): void => this.discardExternalConflict()` 的**表达式体**，把 `Promise<void>` 放进 `: void` 的箭头体里编译不过。改成块体并显式丢弃返回值：`onConflictDiscard: (): void => { void this.discardExternalConflict(); }`、`onConflictKeep: (): void => { void this.keepExternalConflict(); }`（与同文件 `onRetry` / `onOpenSchema` 的既有写法一致）。**不要**改成把方法写成同步、也**不要**改成调用点 `void this.xxx()` 之外的写法。

    「保存外部修改」见上一段（丢弃待写 + 失效缓存 + 按记下的原文换内容）。

    用户没表态之前**一个字节都不写**：不自动落盘、不提前 flush、不清条目；`TablePanel.isColumnDirty` 的待写来源保持真、右上角提示常驻、`beforeunload` 继续拦。冲突路径没有 5 秒自动落盘（Plan 04 的 `noteExternalWrite` 已把该条目的定时器清掉且不再重排），因此**不存在**「保留之后定时器装不回来」的中间态：这条路径只能由弹窗的两个动作结算。

    **弹窗不在用户打字时抢焦点（延迟规则 + 两个解除入口）**：给面板加一个「正在打字」标志与一个私有方法 `TablePanel.setFieldEditing(editing: boolean)`——它只做两件事：置标志；**由真变假的那一刻调一次 `TablePanel.showNextConflict()`**（这是「停手就弹」的唯一出口，其它地方不要再散着调；标志本来就是假时直接返回，不重复触发）。

    **入口一（失焦）**：在面板视图根 `etable-columns`（第 597…600 行）上挂 `onFocus` / `onBlur`，经 Plan 03 已声明为**可选**的 `ITablePanelViewProps.onFieldEditingChange`（本计划把它接线并传入）报到面板。**判定必须收窄到「可编辑字段」，不能按「容器内任意焦点」算（第四轮 N-6）**：容器同时包住工具栏、行、gutter 与表格，焦点落到工具栏按钮或行上并不等于有人在打字，按容器算会让弹窗被无限推迟。规则写死为：
    - `onFocus`：只有当 `event.target` 是**可编辑字段元素**时才置真。用一个模块级裸函数 `isEditableFieldElement(target: EventTarget | null): boolean` 判定（名字已在 `INTERFACE-NAME.md` 的 `## Plan 08` 登记待确认）：先 `target instanceof HTMLElement` 再 `element.matches('input, textarea, select, [contenteditable]:not([contenteditable="false"])')`；不满足就什么都不做（不置真，也不动标志）。
    - `onBlur`：看 `event.relatedTarget`——它仍是可编辑字段就**保持真**（字段 → 字段的跳转不打断）；否则（包括 `relatedTarget` 为 `null`、是工具栏按钮、是行或空白）置假。**不要**去读 `document.activeElement`（两个包的 `no-restricted-globals` 都禁 `document` / `navigator`）。

    **入口二（确认提交）**：失焦不是唯一的停手方式——数字框按回车确认后**不失焦**（Plan 09：`NumberInput` 回车提交、提交后不失焦），只靠入口一，这种情形下标志永远为真、弹窗永远不出现。所以**一次成功的确认提交也要解除推迟**：在 `TablePanel.applyEdit`（第 1230…1249 行）的成功分支里（Task 2 已经在那里加了自动写缓冲调用），紧接着调 `this.setFieldEditing(false)`。选这个信号的理由写在这里，实现时不要再改成别的：`TablePanel.applyEdit` 是 `ITablePanelViewProps.applyEdit` 注释里写明的「面板侧唯一的编辑入口」，`EditableTable` 的 `handleChange` 把每一次**确认**（失焦提交、回车提交、下拉 / 复选 / 清空的即时提交）都汇到它这里（`EditableTable.tsx:143…155` → `TablePanel.applyEdit`），因此它天然就是「用户确认了一次」的既有信号，不需要第二个焦点钩子，也不会漏掉任何一种字段。**不要**改成在容器上挂 `onKeyDown` 判回车：文本域里回车是换行而不是确认（`TextareaInput.tsx:78…83` 只在 `onBlur` 提交），按键一判就会把「换行」误当成「停手」。

    编辑被拒绝（`TablePanel.applyEdit` 返回 `null`，例如校验不过）时**不**解除推迟：那说明用户还在改这一格、面板还弹着错误提示，弹出来只会抢焦点。

    `TablePanel.recordPendingConflict` 仍然立刻把冲突记进栏状态并 `publish`（未保存标记必须马上正确），但**当这个标志为真时直接返回、不写弹窗 store**——于是正在打的字不被打断，一停手（失焦或确认）就弹。这条机制只用 React 的焦点事件、一次提交回调与一个布尔，`editor-core` / `editor-impl` 的 `no-restricted-globals` 都不红；**不要**把它挪进缓冲或资源层，也不要把 `recordPendingConflict` 改成「不记冲突」。

    **`onFieldEditingChange` 与两个焦点处理器必须是同步 `void`**：Plan 03 把它声明为 `readonly onFieldEditingChange?: (editing: boolean) => void`，所以接线写成 `onFieldEditingChange: (editing): void => this.setFieldEditing(editing)`，`onFocus` / `onBlur` 处理器同样返回 `void`。**不得**把它们写成 `async` 或让它们返回 Promise（返回 `Promise<void>` 的表达式放进 `: void` 的箭头体是 TS2322，`typecheck` 会红）。
