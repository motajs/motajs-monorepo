## User Constraints (from CONTEXT.md)

### Locked Decisions

#### 资源层写缓冲
- **D-01:** `ResourceSystem` 增加按路径的写缓冲；`writeContent` 只写缓冲 + 更新内容缓存，不再立即 `fs.writeFile` / `writeBinary`。
- **D-02:** `request` / `readContent` 优先返回缓冲内容；其他面板能立即读到最新内容，不必等磁盘。
- **D-03:** 磁盘 flush 的防抖时间为 **5 秒**（最后一次写入后重新计时）。
- **D-04:** 写入后的通知合并为 **50ms** 一次；同一路径的连续写入合并成一次通知。
- **D-05:** 资源层提供 `flush(path)` / `flushAll()` / `hasPending(path)` / `pendingPaths()` 等能力（最终名称待接口计划确认）。
- **D-06:** flush 触发点：5 秒防抖到期、手动保存、切标签、关标签、页面失焦 / `visibilitychange`、释放编辑器。
- **D-07:** flush 失败时保留 pending、不清脏、显示错误；下一次触发重试，不能静默丢内容。
- **D-08:** 关闭标签时先 flush；「不保存关闭」丢弃该路径 pending；「保存并关闭」等 flush 完成后关闭；失败保持标签与面板打开。

#### 表格自动保存
- **D-09:** 表格字段在 **blur 或回车确认**后写一次缓冲；不是每敲一个字符写一次。
- **D-10:** 表格继续保留组件草稿与撤销；不改成受控组件，也不把草稿搬进资源层。
- **D-11:** 表格保存按钮 = 立即 flush；「未保存」状态要同时覆盖「组件草稿脏」和「缓冲有 pending」。

#### 两栏同一张表
- **D-12:** 必须允许同一张表在同一表格面板的两栏同时打开（用户需要一栏看上面、一栏看下面）。
- **D-13:** 两栏共享同一个路径缓冲；一栏确认写入后，50ms 内的合并通知让另一栏更新。
- **D-14:** 输入框里正在编辑时不会触发写入，因此不会收到更新，也不会被打断；只有 blur / 回车确认后才写、才通知。
- **D-15:** 如果两边同时确认造成不同步，按**最后写盘者胜**；同面板两栏之间不弹冲突框。
- **D-16:** 外部工具 / 另一个标签页的写入仍按现有冲突规则处理（脏则提示）；同面板两栏与外部来源要能区分。

#### 等待保存提示与页面生命周期
- **D-17:** 只要任意路径有 pending，编辑器右上角显示「正在等待保存，请勿关闭页面或浏览器」。
- **D-18:** `beforeunload` 在有 pending 时返回浏览器原生确认（`preventDefault` / `returnValue`）；浏览器原生文案不可自定义。
- **D-19:** 页面失焦 / `visibilitychange` 做一次尽力 flush，降低切后台 / 关页丢失。
- **D-20:** 关闭标签的「正在保存…」复用共享 `PanelCloseDialog` 的 `saving` 态，等待 flush 完成后再关闭。

#### 范围与兼容
- **D-21:** 地图 / 素材的保存时机不变（仍按各自切走 / 手动保存规则）；它们的写入也走同一缓冲，磁盘最多晚 5 秒。
- **D-22:** `04.2-21`…`04.2-24` 被本阶段取代，不再执行；`04.2-20` / `04.2-25` 的面包屑修复保留。
- **D-23:** 先接口、后实现：接口计划先定缓冲、flush、pending、通知、来源标识、生命周期与页面提示的契约；命名须先确认。
- **D-24:** 不新增运行时依赖。
- **D-25:** 同面板两栏与外部来源的区分方式（写入来源标识 / 资源层写日志）在接口计划中定；不得用不可靠的字符串比较冒充来源。

| # | 问题 | 一句话结论 | 详见 |
|---|------|-----------|------|
| 1 | 缓冲落在哪一层、插在哪一行？ | 插在 `ResourceSystem.writeContent` 与 `readContent` 之间：`writeContent` 变成「写缓冲 + `cache.set`」不再 `await fs.writeFile`；`readContent` / `readBinary` 先查缓冲再查缓存再回源。**所有既有调用方（5 组写入点、全部签名不变）** 都能不改一行继续工作，但**约 15 处测试与 4 个面板的「保存后立刻读磁盘」语义会变**，必须逐个对齐。 | §Q1 |
| 2 | 5 秒防抖怎么实现、并发与失败怎么处理？ | 每条路径一个 `{ content, version, timer, inFlight, error }` 条目 + `setTimeout` / `clearTimeout`，零依赖；`flush` / `flushAll` 返回 `Promise<void>`，同一路径的 flush 复用同一个 `inFlight`；失败时**内容留在缓冲**、错误记录并抛给有上下文的调用方，下一次真实触发点重试。 | §Q2 |
| 3 | 50ms 合并通知怎么发、会不会和 watch 回声打架？ | 通知复用既有 `IResourceSystemHooks.onUpdateResource` / `onResourceChange` 通道，按路径 `setTimeout(50)` 合并；**回声不会打架**，因为 `TablePanel.saveDocument` 在写入返回后立刻推进 `baselineText`，而 50ms 通知一定晚于这次推进；真正要解决的是「同一次写只通知一次」与「写者自己那一栏不要弹冲突」。 | §Q3 |
| 4 | 「自己写的」和「外部写的」怎么区分？ | 现有 watch 载荷 `IEditorFileChange` 只有 `{ path, kind }`，**没有来源位**；宿主（`MemoryBackend`）也无法区分。可行且有代码支撑的是**资源层写日志（路径 → 最近一次自写内容的指纹 + 单调序号）**，由资源层在 flush 成功后登记，watch 回声到达时比对；**任何形式的字符串 / 时间戳比较都不能当作来源依据**（D-25）。 | §Q4 |
| 5 | 生命周期各处接在哪？ | 切标签 / 关标签已在 `ShellSystem` 的三个钩子上（`departActiveInstance` / `closeTab` / `discardTab`），加一行 `flushAll` 即可；页面级事件**现在一个都没有**，`beforeunload` / `visibilitychange` / `pagehide` 需在 `ShellSystem` 构造或初始化时挂到 `window`（`window` 在 `editor-core` 明确允许，`document` 被门禁禁用）；`IEditorPanel.onFocus` / `onBlur` **声明存在但外壳从不调用**，不能拿来当失焦钩子。 | §Q5 |
| 6 | 右上角 pending 提示放哪？ | 外壳 DOM 目前**没有任何右对齐区域**：`MenuRow` 是一排左起按钮、`TabRow` 是左起标签 + 末尾 `+`。最小改法是在 `MenuRow` 末尾追加一个 `margin-left: auto` 的状态元素（`icon`/文案来自 `pendingPaths().length > 0`）；`data-test-id` 沿用既有 `editor-shell-*` 前缀风格。 | §Q6 |
| 7 | 表格自动保存要改哪里？ | 提交点已经存在：`TextareaInput` 只在 `onBlur` 提交、`GutterButton` 在回车 / 失焦 / 确定提交；但 `NumberInput` / `SelectInput` / `CheckboxInput` **每次 `onChange` 就提交**（数字框会逐键提交）。真正要改的是 `TablePanel.saveDocument` 之后不再需要用户点保存——即「编辑落点 → 写缓冲」这条链已经在，缺的是「谁来触发写」；保存按钮改为 `flush`。 | §Q7 |
| 8 | 同表两栏怎么会不同步、怎么最小修？ | 现在**已经能同表两栏打开**（`setTable` 无唯一性限制），而且 `TablePanel.refreshDependents` 已在写盘后刷新同面板引用同一路径的其它栏。真正缺的是「确认即写」+「写后 50ms 合并通知」；风险是另一栏刷新会把**未 blur 的输入框**重置（D-14 的承诺并不自动成立）。 | §Q8 |
| 9 | 测试怎么组织、哪些会红？ | 三包都已有 vitest + jsdom；`vi.useFakeTimers()` 在仓库里已有先例（3 个文件）。**最大回归面是「保存后立刻读磁盘」的约 15 处断言**（`resourceSystem.test.ts`、`editableContract.test.tsx`、`devHostWatch.test.tsx`、`mapDialogs.test.tsx` 等）。`beforeunload` / `visibilitychange` 在 jsdom 里**能派发但不能验证浏览器原生确认框**。 | §Q9 |

## Summary

Phase 04.3 要做的事，本质上是把「什么时候写盘」这件事，从一个**分散在四个面板、五种触发点、两套脏判定**的现状，收回到**资源层一条路径缓冲**。

仓库现状（本会话逐文件核对）：

1. **资源层是全仓唯一的读写入口，但它现在是「直写直读」**：`ResourceSystem.writeContent` 拿到内容后**立刻** `await this.fs.writeFile(id, data)`（二进制走 `writeBinary`），然后 `cache.set`；**写完不发任何通知**。`[VERIFIED: packages/libs/editor-core/src/resource/resourceSystem.ts:101-111]`
2. **通知只有两条通道，都不是「写入通知」**：`ResourceSystem.updateResource` 先 `cache.invalidate` 再 `forEachHook(onUpdateResource)`；`ResourceSystem.handleFileChange`（宿主 watch）先改索引 / 缓存再 `forEachHook(onResourceChange)`。`[VERIFIED: packages/libs/editor-core/src/resource/resourceSystem.ts:161-173,187-213]`
3. **外壳已经有四个「该保存了」的时刻**，但都不是 flush：切标签走 `ShellSystem.departActiveInstance` → `invokeSwitchOut`，关标签走 `ShellSystem.closeTab` → `discardTab`，替换标签内面板走 `ShellSystem.openPanelInTab`，释放走 `ShellSystem.dispose` → `closePanelInstance`。**页面级事件一个都没有**（`beforeunload` / `visibilitychange` / `pagehide` 在 `editor-core` 源码里零命中）。`[VERIFIED: packages/libs/editor-core/src/shell/shellSystem.ts:569-582,605-632,634-693,722-734,840-878]`
4. **表格其实已经是「失焦提交 + 草稿留在组件」**：`EditableTable` 持 `draftRef` / `dirtyRef`，编辑经 `props.applyEdit` 落成新文档后 `setDirty(true)` 并 `onDraftChange`；`TextareaInput` 只在 `onBlur` 提交。**缺的不是提交点，是「提交之后谁去写」**——现在只有 `TablePanel.save`（按钮）、`onSwitchOut`、`dispose` 三条路。`[VERIFIED: packages/libs/editor-impl/src/table/components/EditableTable.tsx:105-154; packages/libs/editor-impl/src/shared/schemaForm/components/inputs/TextareaInput.tsx:78-83]`
5. **同表两栏今天就能开，而且已经有一套「写后刷新同面板其它栏」的实现**：`TablePanel.setTable` 没有任何唯一性检查；`TablePanel.saveDocument` 成功后会 `refreshDependents(columnIndex, path)`，后者按路径精确匹配本面板其它栏并 `void this.refresh(index)`。**因为它挂在 `saveDocument` 内、而缓冲写入是同步返回的，这条同面板同步在改造后仍然「立刻」发生**；真正被延迟到 5 秒之后的是**磁盘**与**宿主的 watch 回声**——跨面板 / 跨标签页的同步仍然要靠 D-04 的 50ms 合并通知。`[VERIFIED: packages/libs/editor-impl/src/table/tablePanel.ts:970-1000,2440-2463]`

**另一处补充（D-16 的落实机制）：** 「外部写入不得被待写内容遮蔽」不靠丢待写，而靠**读取回落**——外部变化到达时，资源层在这条待写**自己的条目上**把「外部已改」字段置真（条目保留，因此它仍是「未保存」的证据；这是条目字段而不是另开的路径集合，所以一次外部冲突不会永久关闭该路径的读穿透），取消它的 5 秒自动落盘（**不再重排**），并让读取一律回落到磁盘。这样面板一定看到外部内容、按既有规则脏则弹冲突。冲突的结算只有两条路，点哪个都立刻生效（2026-10-29 用户定稿，取代早先「保留我的 → 重新写一次缓冲、等 5 秒自动落盘」的设想）：**「保存编辑器的」**把该栏内容重新排进缓冲并立刻把该路径 flush 到磁盘（显式覆盖外部修改，条目与标记一起消失）；**「保存外部修改」**丢弃该路径待写（同时失效内容缓存）并按面板记下的外部原文重新载入。用户没表态之前一个字节都不写，因此不存在「保留之后定时器不装回来」的中间态。另有一条手感要求：弹窗**不在用户打字时抢焦点**——某栏有字段已聚焦未确认时，冲突先记进栏状态、弹窗推迟，失焦或回车确认的那一刻立刻弹（`editor-impl` 面板视图根上的 React 焦点事件 + 一个布尔，不碰 `document`）。在途写盘与外部变化共存的窄窗口：在途写盘允许完成，整条替换条目时保留 `inFlight` 与 `error`，结算时标记优先（不删条目、不重排定时器）。

### Q1.2 最小插入点（三处改写，零签名变化）

```
ResourceSystem.readContent(id)
  1. buffer.get(id)          → 命中即返回（D-02）
  2. cache.get(id)
  3. fs.readFile(id) → cache.set

ResourceSystem.readBinary(id)
  同上，且缓冲条目若为 string 而调用方要 Uint8Array（或反之）需要一次显式转换或按「同类型才命中」处理

ResourceSystem.writeContent(id, data)
  1. buffer.set(id, data)     ← 不 await fs
  2. cache.set(id, data)      ← 让既有读取路径不必每次都查缓冲
  3. scheduleNotify(id)       ← 50ms 合并，见 Q3
  4. scheduleFlush(id)        ← 5s 防抖，见 Q2
  （不 deleteResource、不改 index：文件本就存在，索引无需变动）
```

**为什么不把缓冲塞进 `ContentCache`**：`ContentCache` 的语义是「可丢弃的读缓存」（LRU 淘汰、超限不入），缓冲的语义是「绝不能丢的待写内容」。两者混在一起会同时破坏两个不变式。

## Q2：flush 机制

### Q2.1 数据结构（提案，名称待 `INTERFACE-NAME.md` 确认）

```ts
/** 一条路径的待写内容与结算状态 */
interface IWriteBufferEntry {
  /** 最近一次写入的内容；flush 成功后清空 */
  content: ResourceContent;
  /** 5 秒防抖定时器；已被 flush 取消时为空 */
  timer: ReturnType<typeof setTimeout> | null;
  /** 该路径正在进行的 flush；无在途写盘时为空 */
  inFlight: Promise<void> | null;
  /** 该路径最近一次 flush 失败的原文，供调用方 / 提示位显示；成功后清空 */
  error: string | undefined;
}
```

- 存 `Map<string, IWriteBufferEntry>`，**不设上限、不做 LRU**（见 Q1.1 的 8 MiB 陷阱）。
- `hasPending(path)` = `map.has(path)`；`pendingPaths()` = `[...map.keys()]`（返回新数组，不外泄内部引用）。
- 命名提案（**待确认**）：`ResourceSystem.flushContent` / `ResourceSystem.flushAllContent` / `ResourceSystem.hasPendingContent` / `ResourceSystem.listPendingPaths`。**不要**用 `flush` 这种与 DOM / Node 流同名的裸名，接口计划应选一个一看就知道是「把缓冲写盘」的名字。

### Q2.2 5 秒防抖（D-03）

```
scheduleFlush(id):
  entry.timer ? clearTimeout(entry.timer)
  entry.timer = setTimeout(() => { entry.timer = null; void flushOne(id) }, FLUSH_DEBOUNCE_MS)
```

- `FLUSH_DEBOUNCE_MS = 5000`（模块级不变常量，全大写 + 下划线，符合代码风格）。
- **每次写入都重排**（D-03 原文「最后一次写入后重新计时」）。
- 定时器回调里 `void` 掉 Promise，但**必须自己 catch 并把错误落进 `entry.error`**——否则会变成 unhandled rejection。

### Q2.3 `flush` / `flushAll` 可 await（D-05）

```
flushOne(id): Promise<void>
  entry = map.get(id)
  若 entry 不存在 → 直接 resolve（幂等，调用方不必先查 hasPending）
  若 entry.inFlight 存在 → return entry.inFlight      ← 并发 flush 复用在途写盘
  若 entry.timer 存在 → clearTimeout(entry.timer); entry.timer = null
  拍快照 snapshot = entry.content                     ← 关键：写盘期间又写入不能丢
  entry.inFlight = (async () => {
     try {
        typeof snapshot === 'string' ? await fs.writeFile(id, snapshot) : await fs.writeBinary(id, snapshot)
        // 写盘期间又被写入：内容已变，保留 pending，让下一次防抖继续
        if (entry.content !== snapshot) {
           entry.inFlight = null
           scheduleFlush(id)
           return
        }
        map.delete(id)
        entry.error = undefined
        markSelfWrite(id, snapshot)       ← 来源日志，见 Q4
     } catch (error) {
        entry.error = String(error)       ← D-07：保留 pending，不清脏
        throw error                        ← 让调用方（外壳 / 面板）能看见失败
     } finally {
        entry.inFlight = null
     }
  })()
  return entry.inFlight

flushAllContent(): Promise<void>
  对 [...map.keys()] 逐个 await flushOne(id)
  聚合失败：用 Promise.allSettled 的语义（全部尝试完，最后把第一个错误抛出或返回失败清单）
```

**设计要点（都是踩过坑的地方）：**

1. **快照 + 引用比较**：写盘 `await` 期间用户可能又写了一次。若写完直接 `map.delete`，新写入就被吞了。用「`entry.content !== snapshot` 就保留 pending 并重排」这一条即可，不需要编辑序号。
   > 注意 `ResourceContent = string | Uint8Array`，`!==` 对字符串是值比较、对 `Uint8Array` 是引用比较。表格 / 素材写的是新字符串，值比较成立；二进制写入若复用同一 `Uint8Array` 实例，引用比较会漏判。接口计划应明确：**二进制写入必须由调用方给出新实例，或缓冲在 set 时记录一个自增版本号**（后者更稳，建议采用）。
2. **并发写盘串行化**：同一路径同时只能有一个 `inFlight`；第二次 `flush` 直接复用。跨路径可并行。
3. **失败后的重试**：`entry.error` 只用于显示，**定时器已被清掉**，所以「下一次触发重试」必须由某个真实触发点带来（下一次写入、下一次切标签、下一次 flushAll）。D-07 的「下一次触发重试」正是这个语义，不要做成「失败后自动无限重试」——那会在磁盘满 / 权限错时变成忙循环。
4. **`dispose` 里必须 flushAll**：`ResourceSystem.dispose` 现在的顺序是 `unwatch → index.clear → cache.clear → fs = null`。缓冲 flush 必须插在 `cache.clear()` 之前、且不能因为失败而阻止释放（记日志即可）：

```ts
  async dispose(): Promise<void> {
    this.unwatch?.();
    this.unwatch = null;
    this.index.clear();
    this.cache.clear();
    this.fs = null;
  }
```

`[VERIFIED: packages/libs/editor-core/src/resource/resourceSystem.ts:175-181]`

> **顺序陷阱：** 若先 `fs = null` 再 flush，所有写盘都会命中 `system.notInitialized` 守卫、静默失败。计划里要把「dispose 先 flush 再清引用」写成一条可验证的真值。

### Q3.3 50ms 合并的正确位置与形态

### Q3.4 与 watch 回声的关系（为什么不会双发痛）

时间线（编辑器自己保存一次）：

```
t0    面板 resource.write(text)  → 缓冲 + 缓存 + scheduleNotify(50ms) + scheduleFlush(5s)
t0+ε  saveDocument 继续执行，把 baselineText = 刚写出的原文          ← 关键
t0+50ms 合并通知 → 本面板 onResourceChange(path, Change)
           → handleResourceChange 读 text（缓冲命中，内容相同）
           → (baselineText === text) → return            ← 自写回声被基线比较吞掉
t0+5s flush → fs.writeFile → 宿主 watch 回声
           → handleResourceChange 再读一次（此时缓冲已空，缓存是 flush 前设的同一内容）
           → baselineText === text → return              ← 第二次也被吞掉
```

### Q4.3 可行方案：资源层写日志（D-25 点名的「资源层写日志」）

**核心思路**：`ResourceSystem` 自己知道自己写了什么。在 flush **成功**之后，把「这条路径最近一次由本编辑器写出的内容指纹」记下来；watch 回声到达时，如果读到的内容与这条指纹相同，就标记为「自写回声」。

```
flushOne 成功后：
  selfWrites.set(id, { fingerprint: fingerprintOf(snapshot), seq: ++seqCounter })

handleFileChange(change)：
  读当前内容（缓冲优先，缓冲空则 fs）→ 算指纹
  const record = selfWrites.get(path)
  const selfWritten = record !== undefined && record.fingerprint === currentFingerprint
  if (selfWritten) selfWrites.delete(path)        ← 只用一次，避免长期误判
  通知时携带 selfWritten（或者干脆对自写回声不投递面板，只清缓存）
```

**指纹怎么算（不能用字符串比较冒充来源）**：
- D-25 禁止的是「用不可靠的字符串比较**冒充来源**」——即「内容一样所以一定是我写的」这种推理，在外部工具恰好写出同样内容时会误判。
- 写日志不靠推理，靠**登记**：只有 `ResourceSystem` 自己在 flush 时登记过的内容才算自写。外部写入同一内容时，若此刻日志里正好有同一指纹，确实会误判一次 —— 但这是**有界且可解释**的误判（一次通知被吞），不会让数据出错，且下一次写入会刷新日志。
- 更强的做法是**带序号**：日志记录 `{ seq, fingerprint }`，`handleFileChange` 只认「比上次消费过的 seq 更大的一次」，并且**每条记录只用一次**（消费即删）。这样「同一内容被外部写两次」也只会误吞第一次。
- 指纹实现：`string` 直接比字符串（**这里可以比字符串**，因为比较的是「是不是我登记的那次」，不是「猜谁写的」）；`Uint8Array` 需要一个内容比较（长度 + 逐字节或用长度 + 抽样），**不要**引入哈希库（D-24）。建议：二进制只比「引用 + 长度」，并在接口计划里明确「二进制自写回声的识别是尽力而为」。

### Q4.4 更简单、也更符合现有代码的替代方案（建议优先）

**把「自写」这件事在通知层解决，而不是在来源层解决。**

### Q5.3 `beforeunload` 的诚实限制（必须是计划里的显式真值）

- 浏览器**不允许**在 `beforeunload` 里 await 异步工作：处理函数返回后页面就会继续卸载流程，`await fs.writeFile(...)` 的 Promise 不会被等待。
- 因此 `beforeunload` 里能做到的只有两件事：`event.preventDefault()` + `event.returnValue = ''`（弹原生确认框），以及**发起**一次 flush（能不能写完看运气）。
- 结论：**5 秒防抖窗口内的最后一次编辑，在「直接关页面」这条路径上本来就可能丢**。缓解顺序（按效果排序，供 planner 选）：
  1. `beforeunload` 弹框（D-18）——用户点「留在此页」后仍可继续工作，flush 也有机会在后续的 `pagehide` / 下一次写入里完成；
  2. `pagehide` / `visibilitychange` 时 flush（D-19）——覆盖「切后台再回来」和大部分「切走」；
  3. **表格**侧把「确认即写缓冲」做实（D-09），使「已确认的编辑」在内存里已有副本，只有「缓冲区还没落盘」这一个窗口会丢，而不是「用户没点保存就全丢」。

> **这一点必须写进计划的 must_haves**，不能写成「`beforeunload` 保证不丢数据」。

### Q8.5 冲突弹窗的定稿行为（2026-10-29 用户拍板）

`04.2` 的冲突弹窗原本是「放弃我的改动并刷新 / 保留我的改动，下次保存覆盖」；缓冲落地后「保留」这一支会留下一条带「外部已改」标记、没有定时器的待写，5 秒自动落盘从此死掉。用户定稿改成两个立刻生效的动作，并补一条手感要求：

| 项 | 定稿 |
|----|------|
| 「保存编辑器的」 | 先把该栏放回「未落盘」（`TablePanel.saveDocument` 在 `wroteData / wroteSchema` 都为假时提前返回，不先放回就是空转）→ 走同一条链把内容排进缓冲 → 立刻 `flushResource` 该路径（显式覆盖外部修改）→ 条目与标记消失、右上角提示更新 |
| 「保存外部修改」 | `discardPendingResource`（同时失效内容缓存）→ 按收到变化时记下的外部原文重新载入；**不重新读磁盘**（磁盘可能已被在途写盘覆盖） |
| 没表态期间 | 一个字节都不写：条目保留、仍算未保存、提示与 `beforeunload` 继续生效、没有 5 秒自动落盘 |
| 何时弹 | 正在某格打字（**可编辑字段**已聚焦、未失焦 / 未确认提交）时推迟，**失焦或一次确认提交**的那一刻立刻弹；没人打字时立刻弹。两个解除入口：① 容器根上的 React 焦点事件（`onFocus` 只认 input / textarea / select / contenteditable，`onBlur` 看 `relatedTarget` 仍是可编辑字段就保持），② **一次成功的确认提交**由面板唯一的编辑入口 `TablePanel.applyEdit` 自己解除——数字框按回车确认后不失焦，只靠失焦事件永远等不到「停手」；文本域里回车是换行、不是确认，所以不能改用按键判定。不碰 `document` |

这与 Q8.3 的方案 A 不冲突：方案 A 说的是「另一栏写入把**内容**刷新掉」，本表说的是「弹窗**抢焦点**」，两件事分别处理。

## Q10：风险与地雷（排序）

### R1（最高）「保存后读磁盘」的既有语义反转

- **现象**：把 `writeContent` 改成只写缓冲后，约 15 处断言（§Q1.4）会红；`manualSave.uat.test.tsx` 的整条语义反转。
- **概率**：**必然发生**（100%）。
- **影响**：三包全量测试大面积红，回滚压力大；若为了「让测试绿」而给 `FakeFileSystem` 加写后落盘后门，缓冲在测试里就形同虚设、bug 会跑到生产。
- **缓解（可变成任务）**：① 接口计划**先**列出完整迁移清单（本文件 §Q1.4 可直接抄）；② 实现波次里把「补 flush」作为独立任务，**按包分批**（core → impl → dev），每批跑该包全量；③ 明确禁止给替身加后门；④ `manualSave.uat.test.tsx` 整体重写而不是逐条改。

### R2（最高）`beforeunload` 无法 await 异步写盘

- **现象**：5 秒防抖窗口内直接关页面，最后一次编辑丢失。
- **概率**：中（用户不常这么干，但一旦干了就是数据丢失投诉）。
- **影响**：数据丢失 + 对 D-18「弹原生确认」的信任被高估。
- **缓解**：① `beforeunload` 只承诺「弹框」不承诺「写完」；② `pagehide` / 切标签 / 关标签都 flush（覆盖绝大多数路径）；③ 表格「确认即写缓冲」让内存有副本；④ UAT 里明确写这条限制。

### R3（高）两栏同表刷新把未确认输入重置

- **现象**：见 §Q8.2(2)。
- **概率**：高（两栏同表正是用户的主要用例；50ms 窗口虽小，但用户打字时另一栏确认并不罕见）。
- **影响**：用户正在敲的字消失，观感上就是「编辑器吃字」——比丢磁盘数据更刺眼。
- **缓解**：§Q8.3 三选一（推荐 A + UAT 记录；若用户不接受则 B）。

### R4（高）通知与 watch 回声叠加 → 写者自己弹冲突

- **现象**：若 `baselineText` 推进晚于 50ms 通知，本栏会 `recordPendingConflict`，弹出「文件已被外部修改」。
- **概率**：中（取决于实现顺序，一行代码位置之差）。
- **影响**：每次编辑都弹冲突框，功能直接不可用。
- **缓解**：① 把「`saveDocument` 写成功 → 立即推进基线」写成 must_haves 真值；② 加一条专门测试（同栏写一次 → 断言 `conflictStore.state === undefined`）；③ 保留方案 A（不动来源标识，继续用基线比较）。

### R5（高）`dispose` 顺序错误导致 flush 全部静默失败

- **现象**：`ResourceSystem.dispose` 先 `fs = null` 再 flush → 全部命中 `system.notInitialized` 守卫 → 静默丢。
- **概率**：中（顺序很容易写错）。
- **影响**：释放编辑器时丢所有 pending。
- **缓解**：① 把顺序写成显式真值（flush → 清引用）；② 测试用例：写入 → 不 flush → `dispose` → 断言 fs 已是新内容。

### R6（中）`editor-core` 纯净性：不得 import 宿主代码

- **现象**：为接 `beforeunload` / 提示，可能顺手 import 了 `antd`、`editor-impl` 或宿主模块。
- **概率**：低（门禁会抓）。
- **影响**：`coreBoundaries` / `coreImportType` / `coreEngineNeutral` 全红。
- **缓解**：外壳的 pending 提示只用 `createElement('span', …)` + 既有 CSS，**不引入 antd**（`editor-core` 的 `package.json` 里也确实没有 antd，只有 react + `@tanstack/store`）`[VERIFIED: packages/libs/editor-core/package.json:17-20]`。

### R7（中）测试在打开的定时器上挂住 / 泄漏

- **现象**：5 秒定时器在测试结束时仍挂着，vitest 报「Test finished, but timer is still running」或整轮变慢；`fake timers` 与 `@testing-library/react` 的 `waitFor` 混用时超时。
- **概率**：中（每个资源层用例都会创建定时器）。
- **影响**：全量测试时长暴涨 / 偶发超时。
- **缓解**：① 缓冲实现提供 `dispose` 清所有定时器，测试 `afterEach` 调 `system.dispose()`；② 需要 `waitFor` 的用例用 `vi.useRealTimers()` 段或显式 `advanceTimersByTime`；③ **不要**把定时器挂在模块级（既是风格门禁也是泄漏源）。

### R8（中）5 秒延迟让「崩溃即丢」的观感变差

- **现象**：用户改完 4 秒后浏览器崩了 / 断电，磁盘没有最新内容。
- **概率**：低到中。
- **影响**：用户会认为「自动保存不可靠」。
- **缓解**：① 右上角 pending 提示（D-17 就是为这个存在）；② UAT 明确「最多 5 秒」；③ 若要更短，只能改 D-03（不擅自改）。

### R9（中）`createResource` 是否缓冲的顺手扩散

- **现象**：实现者为了「统一」，把 `createResource` 也改成缓冲 → 新建的两个文件 5 秒后才真的存在，`fileExists` / 索引 / 目录列举出现不一致。
- **概率**：中。
- **影响**：新建表格后的「打开」失败、删除时报「文件不存在」。
- **缓解**：接口计划里把「`createResource` / `deleteResource` / `moveResource` **不缓冲**」写成显式真值 + 一条测试。

### R10（低）50ms 合并导致的「最后一次通知丢失」

- **现象**：防抖式合并（每次重置定时器）在持续高频写入下永不触发通知，另一栏一直不更新。
- **概率**：低（表格写入是离散确认，不是连续流）。
- **影响**：两栏同步迟迟不发生。
- **缓解**：采用「**首次排程不重置**」的合并策略（第一次写入起 50ms 后必发一次，期间的写入合并进去），而不是「每次写入重置 50ms」。D-04 的原文「写入后的通知合并为 50ms 一次」两种读法都成立，**接口计划应选「不重置」**。

### R11（低）04.2 门禁回归

- 四条结构门禁（`coreEngineNeutral` / `coreModuleState` / `coreImportType` / `coreBoundaries`）在 04.2 收口时全部 exit 0；本阶段只要不引入宿主 import、不用 `document`、不破坏模块级无副作用，就不会回归。**`coreBoundaries` 跑得慢（1–3 分钟），放在每波合并时跑一次即可。**

### R12（低）`implExports` / `coreExports` 仍是红的

- 这两条在 04.2 就已经失效（引用已归档路径 / 旧期望），**不要**把它们列进本阶段生效门禁；若本阶段新增 subpath（预计不会），必须同时修它们。`[VERIFIED: .planning/phases/04.2-panel-content-decoupling/04.2-RESEARCH.md:1225-1237]`

### Pattern 1：按路径写缓冲 + 读穿透（D-01 / D-02 / D-05）

**What:** `writeContent` 只写缓冲 + 缓存；`readContent` / `readBinary` 先看缓冲；`flush` 才碰磁盘。
**When to use:** 所有经 `ResourceSystem` 的写入（表格 / 地图 / 素材）。
**关键不变式：**
1. 缓冲是「绝不可丢」的，**复用 `ContentCache` 会因 8 MiB 上限静默丢条目**；
2. `createResource` / `deleteResource` / `moveResource` **不缓冲**（Q1.2 / R9）；
3. `dispose` 必须先 flushAll 再清 `fs` 引用（R5）。

```ts
// 提案形态（名称待 INTERFACE-NAME.md 确认）
async writeContent(id: IResourceIdentifier, data: ResourceContent): Promise<void> {
  if (!this.fs) {
    logger.error('system.notInitialized', 'Resource');
    return;
  }

  this.buffer.set(id, data);
  this.cache.set(id, data);
  this.scheduleNotify(id);
  this.scheduleFlush(id);
}
```

### Pattern 2：5 秒防抖 + 可 await 的 flush + 失败保留（D-03 / D-05 / D-07）

```
写入 → 重排 5s 定时器
定时器到 → flushOne(path)：拍快照 → fs.write → 期间有新写入就保留 pending 并重排 → 成功才删条目
失败 → 条目留下、error 记下、抛给调用方（有面板上下文时）/ 只记日志（定时器路径）
```

**Why not 自动无限重试:** 磁盘满 / 权限错时会变成忙循环。D-07 的「下一次触发重试」= 下一个真实触发点。

### Pattern 3：生命周期统一 flush（D-06 / D-08 / D-19）

```
切标签 / 替换面板  → invokeSwitchOut(面板先写缓冲) → flushAll
关标签（保存）     → 面板保存 → flush(该面板路径) → discardTab(skipFlush)
关标签（不保存）   → onDiscard（面板清脏）→ 丢弃该面板路径的 pending → discardTab(skipFlush)
释放编辑器         → ShellSystem.dispose → … → ResourceSystem.dispose（flushAll）
页面 pagehide      → flushAll（尽力）
页面 beforeunload  → 有 pending 就 preventDefault 弹原生确认（不承诺写完）
```

**顺序铁律：面板 → 缓冲 → 磁盘。** 反过来会漏掉刚写进缓冲的内容。

### Pattern 4：表格「确认即写缓冲、保存即 flush」（D-09 / D-10 / D-11）

```
控件确认（blur / 回车 / 选中）
  → TableRow.handleValueChange（校验）
  → EditableTable.runEdit → props.applyEdit（落成新文档、登记撤销、置脏）
  → TablePanel.saveDocument（写缓冲，基线立即推进）
  → 面板 markSaved() 清组件脏 + 单独下发「本栏路径是否有缓冲 pending」
```

**工具条的「未保存」= 组件草稿脏 ‖ 该栏路径有缓冲 pending**（D-11）；**自动保存不刷「已保存」提示，手动保存才刷**。

### Pattern 5：同表两栏（D-12 / D-13 / D-15）

```
栏 A 确认 → 写缓冲 → saveDocument 内立即 refreshDependents(A 的路径)
                     → 栏 B（同路径、不脏）refresh → contentVersion++ → 组件重置草稿
                     → 50ms 合并通知兜底（跨面板同理）
两栏同时确认 → 后写者覆盖缓冲 → 先写者基线已推进、不再脏 → 收到通知后刷新成后写者内容
             → 全程不弹冲突框（同面板 D-15）
另一个标签 / 外部进程 → 走 handleResourceChange → 脏则弹冲突（D-16 保持）
```

### Anti-Patterns to Avoid

- **把缓冲塞进 `ContentCache`**：8 MiB 上限会静默丢大文件（§Q1.1）。
- **在 `beforeunload` 里 await 写盘**：浏览器不会等（§Q5.3）。
- **用字符串比较冒充「这是谁写的」**：D-25 明令禁止；比基线可以（那是「内容变没变」），比来源不行（§Q4.3）。
- **给 `IEditorFileChange` 加必选 `origin`**：会破所有宿主；加可选则等于没加（§Q4.2）。
- **把 `refreshDependents` 挪到 flush 之后**：两栏同步会被 5 秒拖死（§Q8.2(1)）。
- **用 `IEditorPanel.onBlur` 当页面失焦钩子**：外壳从不调用它（§Q5.2）。
- **在 `editor-core` 用 `document`**：`coreModuleState` 门禁直接红（含测试）。
- **在 `editor-core` 引入 antd 做提示**：包边界与 `package.json` 都不允许。
- **给 `FakeFileSystem` 加「写入即同步落盘」后门**：缓冲在测试里就失效了（R1）。

## Common Pitfalls

### Pitfall 1：把缓冲复用成 `ContentCache`
**What goes wrong:** 大文件写入后从缓存消失，随后读到旧内容。
**Why:** `ContentCache.set` 对超过 8 MiB 的内容直接不入缓存。`[VERIFIED: packages/libs/editor-core/src/resource/contentCache.ts:51-52]`
**How to avoid:** 缓冲独立 `Map`，无上限。
**Warning signs:** 改一张大地图 / 大素材后切走再切回，内容回到旧值。

### Pitfall 2：`dispose` 里先清 `fs` 再 flush
**What goes wrong:** 全部写盘命中 `system.notInitialized`，静默丢。`[VERIFIED: packages/libs/editor-core/src/resource/resourceSystem.ts:56-59,64-68]`
**How to avoid:** flush → 清引用。**Warning signs:** `dispose` 后磁盘全是旧值但没有一条错误日志（因为守卫分支只 `logger.error` 一次）。

### Pitfall 3：基线推进晚于 50ms 通知
**What goes wrong:** 每次编辑都弹「文件已被外部修改」。
**How to avoid:** 见 §Q3.4 / R4。**Warning signs:** 单栏编辑一次就弹冲突框。

### Pitfall 4：把 `refreshDependents` 挪到 flush 之后
**What goes wrong:** 两栏同表要等 5 秒才同步。
**How to avoid:** 留在 `saveDocument` 内。**Warning signs:** 用户在同一面板两栏之间来回看，另一栏一直不更新。

### Pitfall 5：给测试替身加落盘后门
**What goes wrong:** 缓冲在自动化里永不被验证，bug 全跑到生产。
**How to avoid:** 用「显式 flush」修测试，不改替身。**Warning signs:** `FakeFileSystem.writeFile` 里出现了「顺便 flush」的字样。

### Pitfall 6：`beforeunload` 里 `returnValue` 写法不对
**What goes wrong:** 现代浏览器要求 `event.preventDefault()` **和** `event.returnValue = ''`（或 `return ''`）才弹框；只写其一可能不弹。
**How to avoid:** 两者都写，并在测试里断言 `event.defaultPrevented === true`。`[ASSUMED: 浏览器实现细节来自训练知识；本会话未在真实 Chromium 里验证]`

### Pitfall 7：合并通知触发预读通道，把二进制路径读崩
**What goes wrong:** 地图 / 素材没实现 `onResourceChange`，外壳退回 `onUpdateResource` → `resource.request()` → 对二进制路径 `readFile` 抛 → `resource.hookFailed` 日志噪音。
**How to avoid:** 合并通知只投递给「声明了 `onResourceChange` 的面板」；或让地图 / 素材补一个空 `onResourceChange`。`[VERIFIED: packages/libs/editor-core/src/shell/shellSystem.ts:1002-1009]`

### Pitfall 8：数字框逐键提交被当成「每敲一个字符写一次」
**What goes wrong:** D-09 的字面被违反的错觉；实际是控件语义差异（§Q7.1）。
**How to avoid:** 由接口计划显式定（O4）。**Warning signs:** 输入「123」时 `writeContent` 被调 3 次（可控，5s 防抖会合并到一次磁盘写入）。

### Pitfall 9：pending 提示用 `queryByTestId` 恒命中
**What goes wrong:** 无 pending 时渲染一个空 `<span>`，`getByTestId` 永远拿得到，「有 pending」这条断言变成永真。
**How to avoid:** 无 pending 时返回 `null`（§Q6.3）。

### Pitfall 10：测试里用 `document` 破门禁
**What goes wrong:** `coreModuleState` 红。
**How to avoid:** 用 `window` 事件（`pagehide` / `beforeunload`）。`[VERIFIED: .planning/STATE.md:249]`

## Open Questions（仅列真正需要用户拍板的）

> 本阶段绝大多数内容已被 D-01…D-25 锁定。下面四条是**研究过程中暴露出来的、D-xx 没有覆盖到的取舍**，需要用户在安排接口计划前给一句话结论。

### O1：D-04 与 04.2 的 D-14 / D-36 直接冲突，是否确认「以 04.3 为准」？

- **背景（用人话说）：** 04.2 定过一条规矩——「编辑器自己写文件之后，资源层不要再喊一声『文件变了』」，理由是怕同一个变化被通知两次。04.3 的 D-04 要求「写入后 50ms 合并通知一次」，正好相反。这条通知是「同一张表开在两栏、一栏改完另一栏立刻看到」的必要条件。
- **两种可能：**
  - **A（建议）**：确认 04.3 取代 04.2 的 D-14（仅针对「缓冲写入」这一条路径），并保留 04.2 的基线比较去重（它仍然吞掉重复）。
  - **B**：资源层完全不通知，两栏同步只靠 `refreshDependents`（同面板可以，**跨面板不行**）→ D-13 的「跨面板 50ms」做不到。
- **影响**：选 A 才能满足 D-13；选 B 会让「同表两栏」只在同一个面板内成立。

### O2：flush 失败时，用户看得见什么？

- **背景：** D-07 说「显示错误」，但 D-17 只给了「正在等待保存」一条文案，外壳里也没有任何通知 / toast 设施（`editor-core` 只依赖 react + `@tanstack/store`）。
- **可能：**
  - **A（建议）**：失败时**不新增文案**——pending 不消失，右上角继续显示「正在等待保存」，用户能感知「还没存上」；详细错误只进 `logger`。
  - **B**：新增一条失败文案（例如「保存失败，请检查磁盘」），需要新的 UI 元素与新的 `data-test-id`。
- **影响**：选 B 会引入本阶段唯一的「新视觉」，与「不出 UI-SPEC」的前提有张力。

### O3：页面生命周期用 `pagehide` 代替 `visibilitychange`，可否？

- **背景：** D-19 原文写「页面失焦 / `visibilitychange`」，但判断页面是否隐藏最直接要读 `document.hidden`，而 `document` 在 `editor-core`（含测试）被结构门禁禁掉。`pagehide` 是 `window` 上的等价事件（覆盖「离开页面 / 进 bfcache」），不破门禁。
- **建议**：用 `pagehide`（+ 可选 `window` 的 `blur`），并在接口计划里把 D-19 的落实形态记成「`pagehide` 为主」。
- **影响**：若坚持 `visibilitychange`，要么破门禁、要么给门禁加白名单（不推荐）。

### O4：数字输入框逐键提交，算不算违反 D-09？

- **背景：** 文本域是「失焦才提交」，但数字框是**每敲一个键就提交一次**（`NumberInput` 的 `onChange` 直连提交）。D-09 说「字段确认后写一次缓冲，不是每敲一个字符写一次」。
- **可能：**
  - **A（建议）**：接受——把「数字框的一次 onChange」当作一次「字段确认」（它是离散值变更，不是自由文本），缓冲写入受 5 秒防抖与 50ms 合并约束，磁盘仍只写一次。
  - **B**：改 `NumberInput` 为「失焦 / 回车才提交」，与文本域对齐——**这会改变既有输入体验与撤销粒度**，属于交互变更，风险更大。
- **影响**：选 A 只是语义澄清；选 B 会动 `NumberInput` 并可能影响既有数字输入测试。

### O5（不阻塞）：`createResource` 明确不缓冲，确认即可

- 研究建议「新建文件立刻落盘」（§Q1.2 / R9）。若用户希望新建也延迟，需要额外处理索引与目录列举的一致性——**不建议**。
