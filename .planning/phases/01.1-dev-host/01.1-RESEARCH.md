## User Constraints (from CONTEXT.md)

### Locked Decisions

- **D-01:** 新建一个 **dev-only 工作区包**（放在 `packages/apps/`，拟名 `editor-dev`），独立 **Vite** 应用。装配流程：构造 `EditorCore` → 注册面板类型 → `initialize(injection)`（注入内存后端 + 外壳注入）→ 渲染 `shellSystem.render()`。 — **Reversibility:** reversible — 纯新增 dev 包，删除即可。
- **D-02:** 使用**内存假数据**后端（in-memory 资源后端 + 少量示例数据）。
- **D-03:** **不读 `mota-js` 外部工程**——本改造面向**新引擎**（旧引擎只顺带适配，`packages/external/mota-js` 不作为宿主数据源）。本地 fs 后端**推迟**到**新引擎的数据存储部分完工后**再接入（后续阶段）。
- **D-04:** 起步注册**一个占位 / 演示面板**（证明外壳可注册 / 开实例 / 关闭）。
- **D-05:** 接入机制——**每个能力 subpath 导出一个「安装函数」**（installer / register），宿主统一调用它们完成注册。解耦、可复用，也贴合未来真实宿主的做法。
- **D-06:** 该包 **`private: true`**、**仅本地 `dev`**、不接入任何产品构建 / 发布链路；依赖放 devDependencies，不随产品发布。

## Summary

本阶段要交付的东西很小、也很确定：一个独立的、只在本地跑的开发用 Vite 应用，把 `editor-core` 的外壳真正渲染到浏览器里。**外壳本身（`ShellSystem`）已经写完并自带订阅**，所以宿主不需要维护任何状态，只需要三件事：造一个内存后端对象、把它交给 `EditorCore.initialize(...)`、把 `shellSystem.render()` 返回的组件挂到 DOM。真正的未知点只有两个：**注入对象到底长什么样**、以及**「安装函数」这个跨阶段约定该定成什么形状**。这两点本文件已从源码里查清并给出可直接落地的形状。

关键结论：`initialize()` 的注入对象是 `IEditorCoreInjection = IUndoInjection & IResourceInjection & IShellInjection`；其中只有 `maxUndoStep`（撤销）和五个资源方法（读/列/写/建/删）是非空内容，`IShellInjection` 是空接口。资源后端是一个「按类型分桶的内存 Map」，而且**必须同时维护『列表』**——因为 `ResourceSystem.requestResource` 会先查列表、不在列表里就直接返回 `null`。仓库里已有一份现成的参考实现（`core.test.ts` 里的 `FakeEditorInjection`），开发宿主直接照搬它的形状即可，无需发明新东西。

另一个重要事实：`@motajs/editor-impl` 现在是**空壳**（`src/index.ts` 只有一行 `export {};`，`./table` 等子路径目标文件都还不存在）。所以本阶段的演示面板只能放在开发宿主自己内部；D-05 的「安装函数」约定本阶段先以「宿主本地函数」形式立起来，等到 Phase 2 有了 `editor-impl/table` 再按同一形状接进去。

**Primary recommendation:** 新建 `packages/apps/editor-dev`（`private: true`、无 `build` 脚本、只加 `dev`/`typecheck`），照搬 `core.test.ts:20-68` 的 `FakeEditorInjection` 做内存后端，`main.tsx` 里 `new EditorCore()` → 调用本地安装函数注册演示面板 → `await core.initialize(backend)` → `createRoot(...).render(createElement(core.shellSystem.render()))`。

        │
 ③ createRoot(root).render(createElement(core.shellSystem.render()))
        │
        ▼  ShellRoot (useSyncExternalStore 自订阅)
   ┌──────────────────────────────────────────────┐
   │ MenuRow      （菜单项按钮）                    │

        ▼
   ShellSystem.openPanelInTab(tabId, typeId)
        → createInstance → factory({context, instanceId}) → IEditorPanel
        → instance.initialize()  →  context.requestResource(id).request()  读内存后端

数据流要点：数据只从**注入的后端**流进 `ResourceSystem`，再经 `PanelContext` 到面板；外壳只持有状态并订阅，不碰后端。引擎无关性由此保持。

### Pattern 1: 注入与装配（本阶段的核心未知已解）

**What:** `EditorCore.initialize(injection)` 接收的 `IEditorCoreInjection` 是三者的交叉：

- `IUndoInjection`：仅一个成员 `readonly maxUndoStep: number` `[VERIFIED: packages/libs/editor-core/src/undo/types.ts:22-25]`
- `IResourceInjection`：五个方法 `[VERIFIED: packages/libs/editor-core/src/resource/types.ts:68-100]`：
  - `requestResource<T>(id): Promise<T>`
  - `requestResourceList(type: number): Promise<readonly IResourceIdentifier[]>`
  - `writeResource(id, content: unknown): Promise<void>`
  - `createResource(id, content: unknown): Promise<void>`
  - `deleteResource(id): Promise<void>`
- `IShellInjection`：**空接口**（`export interface IShellInjection {}`）`[VERIFIED: packages/libs/editor-core/src/shell/types.ts:4]`

合并声明：`export interface IEditorCoreInjection extends IUndoInjection, IResourceInjection, IShellInjection {}` `[VERIFIED: packages/libs/editor-core/src/types.ts:5]`

`EditorCore.initialize` 的下发顺序 `[VERIFIED: packages/libs/editor-core/src/core.ts:38-40]`：
```
const arr = [this.undoSystem.initialize(injection), this.resourceSystem.initialize(injection)];
await Promise.all(arr);
await this.shellSystem.initialize(injection);
```

**When to use:** 宿主装配时的唯一入口。注入对象可以是一个普通 class 实例（推荐 `implements IEditorCoreInjection`，符合项目风格）。

### Pattern 2: 内存后端设计（照搬现成参考）

**What:** 最简单可行的后端 = 两个嵌套 Map（按 `type` 分桶）。**关键约束：必须在 `requestResourceList` 里返回该 `id`，否则面板拿不到资源。**

`ResourceSystem.requestResource` 先查列表、不在列表直接返回 `null` `[VERIFIED: packages/libs/editor-core/src/resource/resourceSystem.ts:51-56]`：
```
const list = await this.requestResourceList(id.type);
const found = list.some((item) => item.type === id.type && item.id === id.id);
if (!found) return null;
```

仓库已有**完全可用**的参考实现：`packages/libs/editor-core/src/__tests__/core.test.ts:20-68` 的 `class FakeEditorInjection implements IEditorCoreInjection`（`seed()` 同时写内容与列表；`content: Map<number, Map<string, unknown>>`；`list: Map<number, IResourceIdentifier[]>`）。开发宿主直接照这个形状实现即可（**不要 import 测试文件**，只照抄结构）。

**When to use:** 本阶段所有依赖数据的面板（成功验收 ③）。

### Pattern 3: 面板注册 + 挂载（外壳是自订阅的）

**What:** 
- 注册：`shellSystem.registerPanelType(type: IEditorPanelType): boolean` `[VERIFIED: packages/libs/editor-core/src/shell/types.ts:40]`。`IEditorPanelType` 成员：`id` / `name` / `icon: ReactNode` / `create: EditorPanelFactory` `[VERIFIED: packages/libs/editor-core/src/panel/types.ts:106-118]`。
- 工厂签名：`export type EditorPanelFactory = (param: IEditorPanelFactoryParam) => IEditorPanel;` `[VERIFIED: packages/libs/editor-core/src/panel/types.ts:104]`；入参 `{ context: IEditorPanelContext; instanceId: string }` `[VERIFIED: packages/libs/editor-core/src/panel/types.ts:95-101]`，**同步返回**。
- 面板上下文读资源：`IEditorPanelContext.requestResource<T>(id): Promise<IResource<T> | null>` `[VERIFIED: packages/libs/editor-core/src/panel/types.ts:10]`，随后 `IResource.request(): Promise<T | undefined>` 取内容。注意与注入层的 `requestResource`（直接返回 `T`）**签名不同**。
- 面板实例接口 `IEditorPanel extends IUndoable` 要求实现：`id`、`initialize`、`dispose`、`render(): FC`、`onFocus`、`onBlur`、`onSwitchIn`、`onSwitchOut`、`onUpdateResource`、`onUpdateResourceList`、`undo`、`redo` `[VERIFIED: packages/libs/editor-core/src/panel/types.ts:39-92]`。
- 挂载：`shellSystem.render(): FC` `[VERIFIED: packages/libs/editor-core/src/shell/types.ts:122]`，实现是返回**缓存的一次性根组件** `[VERIFIED: packages/libs/editor-core/src/shell/shellSystem.ts:540-542]`。
- **不需要宿主驱动 store**：`ShellRoot` 内部 `useSyncExternalStore(props.subscribe, props.getSnapshot)` 自订阅 `[VERIFIED: packages/libs/editor-core/src/shell/shellSystem.ts:291]`；`ShellSystem` 用内部 `versionStore` 通知 `[VERIFIED: packages/libs/editor-core/src/shell/shellSystem.ts:344]`。
- `initialize()` 会在没有任何标签时自动开一个空白标签页 `[VERIFIED: packages/libs/editor-core/src/shell/shellSystem.ts:371]`，因此「打开即见默认空白标签页」是免费的（成功验收 ①）。

**When to use:** 宿主 `main.tsx`。顺序：构造 → 注册（可在 initialize 前）→ initialize → render。`registerPanelType` 不依赖 initialized 状态。

### Pattern 4: 「安装函数」（installer）约定（D-05，跨阶段契约）

**What:** 每个能力 subpath 导出一个纯函数，宿主集中收集并调用它完成注册。基于本仓库类型，最贴合的形状是：

```ts
// 形状提案（名称需 INTERFACE-NAME.md 确认）
export type EditorCapabilityInstaller = (core: IEditorCore) => void;
export function installTable(core: IEditorCore): void { /* 注册面板类型/菜单项 */ }
```

**Why `(core: IEditorCore)`:** 安装函数要能拿到 `core.shellSystem`（`registerPanelType`/`registerMenuItem`）与（如需要）`core.resourceSystem`/`core.undoSystem`；传整个 `IEditorCore` 最灵活，真实宿主将来照抄同一约定。

**本阶段如何落地:** `@motajs/editor-impl` 当前是空壳——所有 `./table`/`./map`/`./asset`/`./shell`/`./react` 子路径的目标文件都不存在（实测 6 个 `index.ts` 均不存在）`[VERIFIED: packages/libs/editor-impl/package.json:8-16 + 实测目标文件不存在]`，`src/index.ts` 只有 `export {};` `[VERIFIED: packages/libs/editor-impl/src/index.ts:1]`。因此：
- **本阶段演示面板的安装函数放在开发宿主内**（`src/installers/`），由 `main.tsx` 统一调用，先把「宿主集中调用安装函数」的机制立起来。
- **Phase 2 起**：`editor-impl/table` 等按同一形状导出 `installXxx`，宿主只需在装配处多加一次调用。
- **跨阶段协调提醒（见 Open Question 2）**：Phase 2 已锁定的 D-01 说 `editor-impl/table` 导出「①一个可注册的面板类型 ②底层 React 表格」。该 D-01 与 D-05 并不冲突——`installTable(core)` 内部即调用 `core.shellSystem.registerPanelType(...)`，同时 `./table` 仍可另行导出面板类型供第三方定制。规划 Phase 1.1 时**不要**与 Phase 2 的 D-01 冲突。

**Anti-Patterns:**
- **宿主手工逐条注册每个面板/菜单项**：违背 D-05；应集中调用安装函数。
- **把状态搬进宿主**：外壳已自订阅，宿主不应复制标签/面板状态。
- **面板工厂返回 Promise**：`EditorPanelFactory` 是同步的；异步初始化放 `IEditorPanel.initialize()`。
- **依赖 `requestResource` 拿到句柄却忘了列表**：后端不维护列表 → 返回 `null`（见 Pitfall 2）。

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |

## Common Pitfalls

### Pitfall 1: 两份 React（Invalid hook call）

**What goes wrong:** 开发宿主 `import 'react'` 解析到一份 React，而 `editor-core` 源码里的 `import 'react'` 解析到另一份（`react@19.3.0`），出现两份 React 实例，hooks 报错或渲染异常。
**Why it happens:** `@motajs/editor-core` 的 `package.json` 精确 pin `react: 19.3.0` `[VERIFIED: packages/libs/editor-core/package.json:19]`，而仓库 catalog 是 `react: ^19.2.3`（解析到 `19.2.3`）。若开发宿主用 `catalog:default`，两者版本不同 → pnpm 生成两个不同 realpath → 双 React。
**How to avoid:** 开发宿主把 `react` / `react-dom` 声明为**精确 `19.3.0`**（与 editor-core 相同），使 pnpm 复用同一 store 路径；或（可选加固）在 `vite.config.ts` 加 `resolve.dedupe: ['react', 'react-dom']`。
**Warning signs:** 浏览器控制台 "Invalid hook call" / "two copies of React"；`pnpm why react` 出现两个版本。

### Pitfall 2: 面板读不到资源（返回 null / undefined）

**What goes wrong:** 面板调用 `context.requestResource(id)` 得到 `null`，空白页/内容为空。
**Why it happens:** `ResourceSystem.requestResource` 先查 `requestResourceList(id.type)` 并校验 `id` 在列表中 `[VERIFIED: packages/libs/editor-core/src/resource/resourceSystem.ts:51-56]`；若内存后端只写了 content、没写 list，就直接 `null`。
**How to avoid:** 内存后端 `seed()` 必须**同时**写 content 与该 `type` 的 list（照抄 `core.test.ts`）。另注意 `writeContent` 只更新 content、`createResource`/`deleteResource` 才会刷新列表。
**Warning signs:** 面板显示空态；`requestResource` 返回 `null`。

### Pitfall 3: 类型检查报 `*.css` 找不到

**What goes wrong:** `tsc -b` 报 `Cannot find module './shell.css'`（来自 `editor-core/src/shell/shellSystem.ts` 的 `import './shell.css'` `[VERIFIED: packages/libs/editor-core/src/shell/shellSystem.ts:1]`）。
**Why it happens:** `editor-core` 有自己的 `global.d.ts`（`declare module '*.css';` `[VERIFIED: packages/libs/editor-core/src/global.d.ts:1]`），但当开发宿主的 program 通过 exports 拉入 editor-core 源码时，该 `.d.ts` 不一定被纳入。
**How to avoid:** 开发宿主的 `tsconfig.json` 设 `"types": ["vite/client"]`（`vite/client` 声明了 `*.css` 模块），或加一个本地 `declare module '*.css';`。
**Warning signs:** `tsc -b` 在 editor-core 文件上报 css 模块错误。

### Pitfall 4: 面板接口面很大，容易漏实现

**What goes wrong:** 演示面板编译不过，或运行期 `PanelHost` 调用缺失方法。
**Why it happens:** `IEditorPanel extends IUndoable` 要求 12 个成员 `[VERIFIED: packages/libs/editor-core/src/panel/types.ts:39-92]`。
**How to avoid:** 演示面板完整实现全部成员；不需要的（`onFocus`/`onBlur`/`onSwitchIn`/`onSwitchOut`/`undo`/`redo`）实现为 `async` 空操作。项目风格要求 class 先有 `interface` 再 `implements`（此处直接 `implements IEditorPanel` 即可）。

### Pitfall 5: 误以为开发宿主要被产品构建

**What goes wrong:** 担心 `pnpm build` / CI build 会把开发宿主打进产品产物。
**Why it happens:** 根脚本 `build: "pnpm -r run build"` 会遍历所有包。
**How to avoid:** 开发宿主**不提供 `build` 脚本**（只有 `dev` / 可选 `typecheck` / `test`）。pnpm 递归运行会跳过没有该脚本的包；服务端 staging/发布链路也没有任何对它的引用。D-06 要求 `private: true`。
**Warning signs:** `packages/apps/editor-dev` 出现在 `dist`/staging 产物里。

### Pitfall 6: 把 `editor-impl` 当成已实现

**What goes wrong:** 开发宿主 `import '@motajs/editor-impl/table'` 直接解析失败。
**Why it happens:** `editor-impl` 的子路径在 `package.json` 里已声明，但目标文件不存在（本阶段实测 6 个子路径目标均不存在）。
**How to avoid:** 本阶段只依赖 `@motajs/editor-core`；演示面板放宿主本地。Phase 2 起再按 D-05 接 `editor-impl`。

import { IEditorCoreInjection, IResourceIdentifier } from '@motajs/editor-core';

export class MemoryBackend implements IEditorCoreInjection {

    return this.content.get(id.type)?.get(id.id) as T;
  }
  async requestResourceList(type: number): Promise<readonly IResourceIdentifier[]> {
    return this.list.get(type) ?? [];
  }
  async writeResource(id: IResourceIdentifier, content: unknown): Promise<void> { /* 写 content */ }
  async createResource(id: IResourceIdentifier, content: unknown): Promise<void> { /* seed */ }
  async deleteResource(id: IResourceIdentifier): Promise<void> { /* 删 content 与 list */ }
}
