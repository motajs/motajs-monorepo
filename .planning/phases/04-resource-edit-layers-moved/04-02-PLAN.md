<objective>
Move the injection seam into core: `FileHandler` becomes constructor-injected, `FileHandlerManager`
becomes a per-instance service, `DataHandler`/`JsonDataHandler`/`BinaryFileHandler` and the resource
combinators follow, and every editor call site keeps working through forward-only shims.

Purpose: this plan carries the phase's real architectural change. Until `FileHandler` stops reading a
module singleton and a nested `Fs`, core cannot be instantiated twice and cannot be driven by an
injected `FsPort` (PORT-02/D-05). It also re-homes the resource combinators that `ResourceRegistry`
will consume in 04-04.

Output: six core resource modules plus one flat `FsPort` test double, three editor fixture
adaptations, six editor shims, and a `FileHandlerManager` that is constructed exactly once — in
`packages/apps/editor/src/appInstances.ts`.

Decisions implemented here — D-01: core's `lib/resources` takes only the generic `DataHandler` base
and `JsonDataHandler`; `Json2xDataHandler`/`ScriptDataHandler` stay in the editor and keep inheriting
through the shim, with no `@motajs/file2x` dependency added to core. D-05: every moved call site reads
through the flat `FsPort` (`fs.readFile`, never `fs.promises.readFile`) and no default implementation
exists. D-06: `FileHandlerManager` is de-singletonised into a per-instance class. D-07:
`FileHandler` takes its `PersistenceMonitor` by constructor injection via `FileHandlerDependencies`,
and the editor's single `FileHandlerManager` instance is constructed in `src/appInstances.ts`. D-09:
the moved modules are internal files exported from the root `.` barrel. D-12: `BinaryFileHandler` and
`JsonDataHandler` are moved literally, with `BinaryFileHandler`'s `Fs` replaced by an injected
`FsPort` and no default. D-13: the pure in-memory `FileHandler`/`FileHandlerManager`/`resources` tests
move to core while `persistNoRollback.invariants` stays in the editor behind shims. D-14: core builds
its own minimal flat `FsPort` test double while the editor keeps its nested `MemoryFileSystem`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| host file system → `FsPort` → core | Every read/write in the moved resource layer crosses the injected port. Core treats paths as opaque strings; path validation and escaping prevention stay in the host (service-worker `fsApi.ts`). |
| editor fixture → core resource | Editor test fixtures reach into a core instance's `handlers` map and rewrite its private `fs` field. A field rename silently breaks them at runtime only (tests are outside the typed program). |
| consumer call site → shim → core | 78 editor production files import the moving paths; a shim that renames or drops a symbol is a compile-time break, but a shim that widens the surface is a silent contract change. |

| T-04-03 | Integrity (silent data loss) | `FileHandler.commit` / `FileHandler.delete` ordering through `this.persistenceMonitor` | high | mitigate | `FileHandler.commit` keeps `this._content({status:'loaded',value})` immediately before `PersistenceMonitor.schedule`; the delete path keeps swallowing only `isFileNotFoundError`; both are covered by the moved core suites and the editor's `persistNoRollback.invariants.test.ts`. |
